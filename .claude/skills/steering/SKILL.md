# Steering スキル

ステアリングファイル(`.steering/`)による作業計画と進捗記録のスキル。**tasklist.md が進捗の正**であり、ユーザーはこのファイルで進捗を把握する(TodoWrite は補助メモで、ユーザーには見えない)。

## モード1: 作業計画(ステアリングファイル作成)

1. `.steering/[YYYYMMDD]-[タスク名]/` を作成する(日付は当日)
2. 関連する永続ドキュメント(`docs/`)の該当節を読む(チケット Issue の「根拠」に挙がった節を起点にする。全ファイル読みはしない)
3. テンプレート(`.claude/skills/steering/templates/`)の requirements.md / design.md / tasklist.md を元に 3 ファイルを作成する
4. tasklist.md は requirements / design に基づき、実装順にフェーズ分けした具体的なタスクへ詳細化する
5. **`design.md` を書き切ったら、冒頭の完成マーカーを `<!-- status: draft -->` から `<!-- status: ready -->` に変える**

**完成マーカーの意味:** 実装への委譲(`implement-ticket` の fork / 外部 CLI への委託)は、このマーカーを**入口検査**に使う。`draft` のまま渡されたものは「計画未完成」として差し戻される(実装の失敗とは別扱い。回復手段が「司令塔が設計を書き切る」で違うため)。**マーカーが無い `design.md` は検査対象外**(マーカー導入以前に作られたものを止めないため)。

**`ready` に変えてよい条件は 1 つだけ:「実装者が設計判断を一切せずに実装できる状態か」。** 実装者は会話履歴を引き継がず `design.md` / `tasklist.md` しか読まないため、ここに書かれていない判断は必ず差し戻しになる。計画途中でセッションが切れても、この印があるので**状態がファイルに残る**。

## モード2: 実装(進捗記録)

tasklist.md に従って実装し、進捗をリアルタイムに反映する。**このモードは `implement-ticket`(`context: fork` / Sonnet)の中で実行される。** 司令塔が直接このモードで実装することはない(モード1 の design.md を、実装者が設計判断なしで進められる粒度まで書き切るのが司令塔の仕事)。

**条件ペア(when X, do Y):**

- タスクに着手するとき → tasklist.md の次の未完了タスク(`[ ]`)を特定してから実装を始める
- タスクが完了したとき → **その場で** Edit で該当行を `[ ]` → `[x]` に更新する(複数タスクのまとめ更新はしない。完了していないタスクに `[x]` を付けない)
- タスクが大きすぎると分かったとき → サブタスクに分割して tasklist.md に追記し、1 つずつ完了させる
- 設計変更等の技術的理由でタスクが不要になったとき → `- [x] ~~タスク名~~(不要になった技術的理由)` と記録する。「時間の都合」「難しいから後回し」は不要化の理由にならない
- 計画と実装が乖離したとき → tasklist.md に注釈・追加タスクを記録し、設計変更が大きい場合は design.md も更新する
- 5 タスク進むごと → tasklist.md を読み直し、記録漏れがあれば直ちに反映する

**完了の定義:** 全タスクが `[x]`(不要化したものは理由付き)になるまで作業を終了しない。未完了タスク(`[ ]`)を残したまま振り返りを書かない。

## モード3: 振り返り

全タスク完了を確認した後、tasklist.md の「実装後の振り返り」セクションに記録する:

- 実装完了日
- 計画と実績の差分(計画と異なった点とその理由)
- 学んだこと・次回への改善提案(次の作業への申し送り)

記録後、ユーザーに内容の確認を依頼する。
