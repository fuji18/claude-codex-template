Project 同期 手順書

README の開発サイクル(着手 → 実装 → レビュー → マージ)を GitHub Projects の board で追えるようにする仕組み。board は表示専用で、チケットの状態の正は Issue のラベルと PR のまま。

早見 — 何が起きるか

1. 人間(1 回だけ) GitHub で Project を作り、Status に 4 つの列を用意する
→
2. 人間(1 回だけ) PAT を PROJECT_SYNC_TOKEN、board の URL を PROJECT_URL に登録する
→
3. あとは自動 Issue / PR が動くたび Actions が board の Status を合わせる

人間がやること(初回のみ・約 10 分) 以降は GitHub Actions が自動で回す

未設定の間は何も起きない。 PROJECT_SYNC_TOKEN が登録されるまで、ワークフローは notice を 1 行出して skip するだけ。CI が赤くなることはないので、Projects を使わないプロジェクトはこのページを無視してよい。

この変更で入ったもの

ファイル 役割
.claude/scripts/project-sync.sh 同期の唯一の経路。Status の決定もここに集約してある
.github/workflows/project-sync.yml Issue / PR のイベントと手動実行(初回投入)で上のスクリプトを呼ぶ
.claude/project-sync.json ラベル名と Status / Priority の列名の候補(board ごとに違うので設定で持つ)
.claude/scripts/test-project-sync.sh GitHub に触らない部分の検査 20 件。ci.yml から呼ばれる

既存の自動進行(autopilot-next.sh / autopilot-loop.sh / autopilot-board.sh)は 1 行も変えていない。 理由はしくみの節にある。

やること(初回だけ)

画面とボタンまで書いた手順は別紙にある。 .claude/docs/project-sync-setup.html —— すでに開発が進んでいるリポジトリに後から入れる場合は、下の要約ではなくそちらを開く。
  1. Project を作り、Status に 4 つの列を用意する

    https://github.com/users/<自分のログイン名>/projects → New project → Board。 Board テンプレートの既定は Todo / In Progress / Done の 3 つなので、In Review を自分で足す。

    任意: Priority という single select フィールドを作り P0 / P1 / P2 を入れると、チケットの優先度ラベルがそこに入る。作らなくてもよい(無いときは何も警告せず優先度だけ飛ばす)。
  2. classic PAT(project + repo scope)を作る

    Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token。 scope は project(board の読み書き)と repo(Issue / PR の読み取り)の 2 つ。

    GITHUB_TOKEN では動かない。 GitHub の docs に「GITHUB_TOKEN is scoped to the repository level and cannot access projects」と明記されている。この手順は省略できない。
  3. リポジトリに登録する

    Settings → Secrets and variables → Actions で 2 つ登録する。

    タブ 名前 値
    Secrets PROJECT_SYNC_TOKEN 手順 2 で作った PAT
    Variables PROJECT_URL https://github.com/users/<login>/projects/3

    board の URL は秘密ではないので、リポジトリに固定でよければ .claude/project-sync.json の projectUrl に書いてコミットしてもよい(variable が優先する)。organization の Project なら URL は .../orgs/<org>/projects/3 の形で、スクリプトが自動で切り替える。

  4. 列名が既定と違うなら候補を足す(日本語の board など)

    照合は候補の順に、大小文字と前後の空白を無視して行う。既定で用意してある候補は次のとおり。 

    # .claude/project-sync.json(抜粋)
"statusField": ["Status", "ステータス"],
"status": {
  "todo":       ["Todo", "To do", "未着手"],
  "inProgress": ["In Progress", "In progress", "進行中"],
  "inReview":   ["In Review", "In review", "レビュー中"],
  "done":       ["Done", "完了"]
}

    見つからない列はその 1 項目だけ飛ばして警告する(In Review 列が無い board でも残り 3 つは動く)。Status フィールド自体が見つからないときだけ失敗する —— board の指定間違いを黙って通さないため。

  5. 既存のチケットをまとめて board に載せる

    Actions タブ → Project Sync → Run workflow。include_closed にチェックを入れると closed の Issue も載る(過去分を Done 列に並べたいとき)。

    手元から回すこともできる(jq と gh が要る。devcontainer には入っている)。

    bash .claude/scripts/project-sync.sh backfill

Status が動く条件

board の Status そうなる条件 きっかけ
Todo ticket ラベルがあり、まだ着手していない /setup-tickets が Issue を発行したとき
In Progress in-progress ラベルがある /next-ticket が着手時にラベルを付けたとき
In Review Closes #N で紐づく open PR がある(draft も含む) PR を作ったとき
Done Issue が closed PR マージで Issue が自動クローズされたとき

判定の順番

上の表は上から順に当てる。複数の条件に当たる Issue(着手済みで PR もある、など)でも結果が 1 つに決まるのは、この順番があるから。

イベント種別ではなく「Issue の現在の状態」から毎回決め直す。 ラベルが付いた・PR が開いたという出来事を追うのではなく、呼ばれた時点の Issue(open/closed・ラベル・紐づく open PR)を見て図 2 を上から当てる。だからイベントを取りこぼしても、順序が入れ替わっても board がずれないし、同じ Issue に何度流しても結果が変わらない。

draft PR も In Review に入れているのは、econ(節約)モードが draft で積んで枠の回復後にまとめてレビューする運用だから。draft を In Progress に残すと、実装中のものと区別できなくなる。

確認とつまずき

まず --check を回す。board には何も書き込まず、設定・権限・列名の対応だけを表示する。 

bash .claude/scripts/project-sync.sh --check

うまくいっているときの出力(例):

project-sync.sh: repo: owner/repo
project-sync.sh: project: https://github.com/users/owner/projects/3(user=owner / number=3)
project-sync.sh: token: PROJECT_SYNC_TOKEN を使う
project-sync.sh: project id: PVT_xxxx / title: 開発サイクル
project-sync.sh: Status フィールド: Status
project-sync.sh:   todo → Todo
project-sync.sh:   inProgress → In Progress
project-sync.sh:   inReview → In Review
project-sync.sh:   done → Done
project-sync.sh: Priority フィールドは board に無い(優先度は反映しない)
project-sync.sh: ラベル: ticket=ticket / in-progress=in-progress
症状 原因 直し方
Actions が notice だけ出して終わる PROJECT_SYNC_TOKEN が未登録 手順 2・3 を行う(これは設計どおりの挙動。失敗ではない)
PROJECT_URL が未設定のため何もしない variable も projectUrl も空 手順 3 で登録する
Project を取得できない PAT に project scope が無い / 別アカウントの board を指している PAT の scope を見直す。URL のログイン名が board の持ち主と一致しているか確認する
Status フィールドが board に無い 列名が候補と一致しない .claude/project-sync.json の statusField に board の実際の名前を足す
Status 'inReview' に対応する列が board に無い In Review 列を作っていない 列を足す。または放置してよい(残り 3 つは動き続ける)
fork からの PR で board が動かない 仕様(信頼境界) 直さない。しくみの節を参照
手元で jq が見つからない ホストに jq が無い devcontainer の中で回す。または Actions の手動実行で済ませる

しくみ(なぜこの形か)

board を「表示専用」に留めた理由

GitHub Projects(v2)の API は GraphQL しか無い。いっぽう、次に何をするかを決める autopilot-next.sh は REST だけで書かれている —— Claude Code on the web のリモート環境では GraphQL が 403 になり、gh issue list すら使えないからだ。 board を判定の入力に入れると、この前提ごと壊れてクラウドで自動進行が動かなくなる。

そこで、情報は左から右へ片方向にしか流れないようにしてある。board は終着点で、そこから誰も読み返さない。

役割で言うと 3 層に分かれている。同じ状態を 2 箇所で持たないのが要点。

層 実体 役割
状態の正 Issue のラベル / PR ここだけが真実。board を手で動かしても状態は変わらない
判定 autopilot-next.sh(REST) 次に何をするかを決める。board を読まない
表示 Project board / 全体管理 Issue 人間が眺めるための面。片方向に書き込まれるだけ

これは既存の全体管理 Issue(autopilot ラベル)と同じ方針で、board はその「もう 1 つの面」にあたる。二重管理にはならない。

何度流しても壊れない理由

item の追加に使う addProjectV2ItemById は、既に board にある内容を渡すと既存の item の ID を返す(重複を作らない)。 そこに図 2 の「Status は現在の状態から毎回決め直す」を重ねているので、再同期は常に安全。取りこぼしが疑わしいときは backfill を回し直せばよい。

信頼の境界

入口は ticket ラベル。書き込み権限が無いと Issue 作成時にラベルを付けられないので、ラベル自体が境界になる(外部からの Issue が勝手に board に載ることはない)。 そのうえで、fork からの PR は 2 段で止めてある —— 本文に Closes #N と書くだけで外部の人が board を動かせてはならないからだ。

Closes #N の正規表現は autopilot-next.sh と同じものを使っている。同じ概念に 2 つの実装を持たせると、判定と board が食い違う。

コマンド一覧

コマンド 何をするか
project-sync.sh --check 設定・権限・列名の対応を表示する(書き込まない)。困ったら最初にこれ
project-sync.sh backfill ticket ラベルの open Issue をまとめて board に載せる
project-sync.sh backfill --all closed の Issue も含める(過去分を Done 列に並べたいとき)
project-sync.sh sync-issue N Issue 1 件だけ同期する
project-sync.sh sync-pr N PR の本文の Closes #N を辿って、紐づく Issue を同期する
project-sync.sh --resolve-status --issue F フィクスチャで Status の決定だけを出す(テスト用。GitHub に触らない)

終了コードは 0 = 成功または未設定でスキップ / 2 = 設定・取得・更新の失敗。 ワークフローは未設定なら notice で skip し、設定済みで失敗したときは赤くする —— board が黙って古くなる方が困るため。

制約と注意

baseBranch を develop にしている構成では Done が遅れる。 GitHub の Closes #N は既定ブランチへのマージでしか Issue を自動クローズしない。feature → develop のマージ時点では Issue が open のままなので、board は In Progress に戻る(in-progress ラベルが残っている限り)。Done はリリース PR が main に入った時点で付く。テンプレート既定(GitHub Flow / baseBranch: main)では起きない。
  • board に載るのは Issue だけ。PR 自体は item にしない(PR は Issue の Status を動かすための材料として読む)
  • board への書き込みは PAT の持ち主として記録される。板の更新履歴はその人の名前になる
  • 手元から回すには jq と gh が要る。無い環境では Actions の手動実行(backfill)で代替する
  • Project 自体は作らない。board とフィールドの用意は人間の担当(API で作ると列の ID が毎回変わり、手順が追えなくなる)
  • organization の Project では GitHub App が推奨される。GitHub の docs は org の Projects に対して PAT ではなく App の installation token を勧めている。URL が /orgs/ 形式ならスクリプトは対応しているが、権限は「organization projects の読み書き」が要る(repository projects では足りない)

よくある質問

もう走っているプロジェクトに後から入れられる?

入れられる。この同期は「今までに何が起きたか」を一切見ない —— 図 2 のとおり Issue の現在の状態(open / closed・ラベル・紐づく PR)から Status を毎回決め直すので、途中から載せても いまの姿がそのまま board に出る。過去のイベントを再生する必要はない。

  1. ファイルを取り込む。このテンプレートから作ったプロジェクトなら /sync-template で入る (.github/workflows/project-sync.yml と .claude/scripts/project-sync.sh は owned = 上書き、.claude/project-sync.json は merge = 手動統合。 ci.yml も merge なので Test project sync ステップは提示に従って足す)
  2. 上の「やること(初回だけ)」を踏む。board の用意 → PAT → PROJECT_URL → 列名の照合
  3. closed も含めて投入する。Actions の手動実行で include_closed にチェックを入れる(= backfill --all)。 これを省くと open のチケットしか載らず、終わった分が Done 列に並ばない
1 件も載らないときは、まずラベルの有無を疑う。 /setup-tickets を通さずに育ったリポジトリ(既存プロジェクトをあとからテンプレートのハーネスへ 移行した場合など)には、ticket ラベルがそもそも存在しない。 backfill は「ticket ラベルの Issue が無い」と言って正常終了するので、 失敗に見えないのがたちが悪い。確かめ方: 
gh label list --limit 50 | grep -E 'ticket|in-progress'
無ければ作って、board に載せたい Issue に付ける。in-progress も作らないと In Progress 列が永久に空になる(着手中でも Todo に入る)。 
gh label create ticket --color 0E8A16 --description "実装チケット"
gh label create in-progress --color 1D76DB --description "着手中"
for n in 12 34 56; do gh issue edit "$n" --add-label ticket; done
ラベルを付けた時点で同期が走る(issues: labeled)。手動実行を待たなくてよい。
一部だけ載らないとき。拾う条件は ticket ラベルが付いていることだけ。 別のラベル名で運用しているなら .claude/project-sync.json の ticketLabel / inProgressLabel を書き換える (指定できるのは 1 つだけなので、bug と enhancement のような 2 系統を同時には拾えない。ticket を足すほうが素直)。 すでに着手済みのチケットは、in-progress ラベルが付いていなければ Todo に入る (PR が開いていれば In Review になる)。ラベルを足せば次の同期で動く。

件数は気にしなくてよい。backfill は REST を全ページ辿るので 100 件を超えても全部載り、 addProjectV2ItemById が冪等なので何度流し直しても重複しない。

Projects を使わない。消せる?

消せる。.github/workflows/project-sync.yml と ci.yml の Test project sync ステップを落とすだけでよい。 消さずに放置してもよい —— PROJECT_SYNC_TOKEN が無い間は notice を 1 行出すだけで、CI も赤くならない。

既存の「全体管理 Issue」はどうなる?

そのまま残る。全体管理 Issue は一時停止の操作と人手が要る停止の通知先を持っていて、board にはその機能が無い。どちらも図 3 の「表示」層で、状態の正はラベルと PR のまま —— だから二重管理にはならない。

board のカードを動かして autopilot を操作したい

いまはできない(意図的)。図 3 の赤い点線を実線にするということなので、先に autopilot-next.sh の REST 限定という前提(Claude Code on the web で GraphQL が 403)を解く必要がある。board を判定に入れた時点で、クラウドのリモート環境では自動進行が動かなくなる。

手で board のカードを動かしてしまった

次にその Issue にイベントが起きた時点で、Status はラベルと PR から決め直された値に戻る(図 2)。すぐ揃えたいなら project-sync.sh sync-issue N か backfill を回す。

fine-grained PAT でもよい?

動く可能性はあるが、GitHub の docs が Projects 用の権限名を示していないため、このページでは classic PAT(project + repo)を案内している。fine-grained を使うなら、まず --check で疎通を確かめてから登録すること。
