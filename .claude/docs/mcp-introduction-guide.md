# MCP 導入の判断ガイド

> **このファイルはプロジェクト開始後も残す価値がある**(プロジェクトの成長に応じて MCP を足し引きする際に参照するため)。
> `/kickoff` フェーズ1.5 がこのガイドを読み、プロジェクト特性に合った MCP の導入を提案する。

## 判断の枠組み(2つの基準)

MCP サーバーのツールスキーマは**使う・使わないに関わらず毎セッション固定費としてコンテキストにロードされる**。導入は以下の両方を満たす場合のみ:

1. **組み込み機能・CLI で代替できない**: Claude Code は WebSearch / WebFetch / Grep / Bash を持ち、GitHub は devcontainer では `gh` CLI、web リモートでは GitHub MCP が自動で入る
2. **固定費に対してリターンが上回る**: ツール数が多い MCP ほど高い頻度・大きい節約が必要

**導入時の必須ルール**: 使いどころを CLAUDE.md の「プロジェクト固有ルール」節に 1〜2 行で明記する(指示なしで置くと司令塔が使いどころを判断できず固定費だけ払う)。**`.claude/rules/*.md` には書かない** — テンプレート所有のため `/sync-template` で上書きされる。

## 導入済み(テンプレート既定)

### Context7(最新ライブラリドキュメント参照)

- **用途**: 知識カットオフ以降に変わったフレームワーク API の最新ドキュメントをバージョン指定で取得し、「古い API で実装 → エラー → 修正」のループを防ぐ
- **固定費**: ツール 2 つのみ(ライブラリ解決+ドキュメント取得)で最小クラス
- **設定**: `.mcp.json` に stdio 接続(`npx -y @upstash/context7-mcp`)で登録済み。OAuth 不要・API キーなしで動作する(**HTTP 版 `https://mcp.context7.com/mcp` は OAuth 認証を要求するため、非対話の web リモートセッションでは使えない**。stdio 版を維持すること)。レート制限の緩和が必要なら context7.com でキーを取得し、`args` に `--api-key <キー>` を追加
- **使いどころ**: 共通ルール `.claude/rules/spec-driven.md`「実装前の確認」に明記済み(テンプレート既定のため rules 側にある)
- **外してよいケース**: 依存が枯れたライブラリ中心で、API 仕様の照会がほぼ発生しないプロジェクト
- **注意**: セッション初回に npx がパッケージを取得するため、ネットワークポリシーで npm レジストリが塞がれている環境では起動に失敗する(失敗は無視してよい。その間は WebSearch / WebFetch で代替)

## 条件付き(プロジェクト特性が確定してから導入を判断)

| MCP                                   | 導入トリガー                                                             | 備考                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| **Playwright MCP / Chrome DevTools MCP** | Web フロントエンドがあり、実装後の動作確認・スクリーンショット・コンソールエラー確認を Claude 自身にさせたい | ツール数 20 超と固定費が大きい。E2E 検証フェーズが定常化してから           |
| **DB 系(Supabase / Neon / Postgres)** | DB を持ち、スキーマ確認・マイグレーション検証・クエリの動作確認をさせたい | 読み取り専用モードにできるものを選ぶ(書き込みは migration ファイル経由に限定) |
| **Sentry / PostHog 等の運用系**       | 本番運用が始まり、エラー調査・メトリクス確認タスクが発生するようになった   | 開発初期には不要                                                           |
| **Figma MCP**                         | デザインファイル起点で UI を実装するフローがある                          | デザイナーとの協業プロジェクトのみ                                         |
| **serena(LSP セマンティック検索)**   | コード規模がしきい値超過(SessionStart hook が自動検知)                   | 詳細は `serena-reintroduction.md` を参照                                   |

## 導入しない(組み込み・既存構成と重複)

- **filesystem / fetch / git 系**: Read / Write / Grep / Bash / WebFetch と完全に重複
- **memory / knowledge graph 系**: `docs/`(北極星)+ `.steering/`(作業記録)+ GitHub Issues で永続化を設計済み
- **Notion / Linear / Slack 等のタスク管理系**: チケット運用は GitHub Issues に一本化済み
- **GitHub MCP のローカル追加**: devcontainer では `gh` CLI(認証済み)で足りる。web リモートでは自動で提供される

## 導入・削除の手順

1. `.mcp.json` の `mcpServers` にエントリを追加(削除は逆)
2. CLAUDE.md の「プロジェクト固有ルール」節に使いどころを 1〜2 行追記(削除時は該当行も消す)
3. Claude Code を再起動する(`.mcp.json` はセッション起動時に読まれる)
4. プロジェクトスコープの MCP サーバーは初回セッションで承認プロンプトが出る(仕様)
5. ローカルバイナリが必要なもの(serena 等)は `post_create.sh` にインストール処理も追加する
