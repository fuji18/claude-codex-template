# スポーク開発構成ルールのセットアップ

ハブ&スポーク構成のプロジェクト（一覧する**ハブ**と、そこから飛ぶ個別の独立サイト/ゲーム=**スポーク**）で、各スポークが **開発段階で満たすべき構成** を定めたルール `docs/playbook/spoke-development-standards.md` を生成し、`CLAUDE.md` から参照させるコマンドです。

`/setup-project` で永続ドキュメントを作成した **後**、かつ `/setup-tickets` でチケットを発行する **前** に実行することを想定しています(MUST 項目がチケットの受け入れ条件になるため)。

**実行する場所はハブ側リポジトリ**(ハブのレジストリスキーマ・ドメイン規約・既存 `_headers` を読んでルールを具体化するため)。スポーク側の独立リポジトリでは実行せず、ここで生成したルールを読んで従わせる。

**引数:** なし（任意でハブ名・本番ドメインのヒントを渡してよい。例: `/setup-spoke-standards game,hokkaido fujioha.com`）

---

## 前提

- ハブ&スポーク型のプロジェクトであること（一覧ハブ + 個別の独立サイト/ゲーム）。当てはまらない場合はユーザーに確認し、不要なら中止する。
- `/setup-project` 済みで `docs/` に永続ドキュメントがあると望ましい（無くても対話とコード調査で補う）。

## 手順

### ステップ0: プロジェクト情報の収集

ルールはプロジェクト固有の値で具体化する。次を読み、実体を特定する。

1. `CLAUDE.md` と `docs/`（`product-requirements.md` / `architecture.md` / `repository-structure.md` など）を読む。
2. Grep / ディレクトリ調査で以下を特定する:
   - **ハブの場所**（例: `apps/*`）と、対象ハブの名前。
   - **スポーク登録レジストリのスキーマ**（例: `apps/<hub>/src/content/<collection>/config.ts` の zod 定義）と必須フィールド。
   - **本番ドメイン / サブドメイン規約**（例: `<spoke>.<domain>`）。
   - 既存のセキュリティヘッダ（`_headers`）、Service Worker、SEO（sitemap/robots/OGP）、ビルド出力ディレクトリの**現行パターン**。
   - スポーク追加の既存 playbook（例: `docs/playbook/add-new-spoke.md`）があれば参照・相互リンクする。
3. **不明な点（対象ハブ、ドメイン規約、SW 方針など）は勝手に決めず、ユーザーに確認する。**

### ステップ1: ルールドキュメントの生成

`docs/playbook/spoke-development-standards.md` を作成する。**下記テンプレートの `<...>` プレースホルダをステップ0で得たプロジェクト固有の値に置換**し、各 MUST はプロジェクト内の実ファイルパスを根拠として参照する。

作成後はユーザーに提示し、**承認を得てから次へ進む**（ドキュメント作成の基本ルールに従う）。

#### 生成テンプレート

````markdown
# スポーク開発構成ルール — 公開前に満たすべき開発段階の構成

<ハブ群（例: game / hokkaido）> の **ハブ** に登録して公開するスポーク（個別のサイト・ゲーム）が、**開発段階で必ず備えるべき構成**を定義するルールです。「どう登録・デプロイするか」は <登録 playbook（例: add-new-spoke.md）>、「公開後に何を確認するか」は <公開後チェックリスト> を参照。本書はその **手前（リポジトリ作成〜レジストリ登録前）** を対象とします。

## 適用範囲

- <各ハブ> に登録するスポーク。
- スポークは **独立リポジトリ・独立サブドメイン**（`<spoke>.<domain>`）。本書はスポーク側リポジトリの構成に適用する。

## Claude への指示（最重要）

1. スポーク開発を始める前に、**本書と <登録 playbook> を必ず読む**。
2. **MUST** 項目を満たさないスポークは公開不可。実装は MUST を前提に進める。
3. 末尾の「公開前セルフチェックリスト」を **開発完了の定義 (DoD)** とし、登録 PR を出す前に自己検証する。
4. 本書と矛盾する判断が必要なとき、または MUST を満たせない事情があるときは、**勝手に決めずユーザーに確認する**。

凡例: **MUST** = 必須（未達なら公開不可） / **SHOULD** = 強く推奨（外す場合は理由を残す） / 参考 = 任意。

## 1. リポジトリ・ビルド構成（MUST）

- <ランタイムのサポートバージョン> で <クリーンインストール+ビルドのコマンド（例: `npm ci && npm run build`）> が成功する。
- ビルド出力は <出力ディレクトリ（例: dist/）>。
- スタックは自由だが **静的出力**を原則とする（SSR・サーバ状態・ユーザ生成コンテンツを持たない前提。この前提が CSP とブラスト半径の判断の土台）。
- <フレームワーク> を使う場合は本リポジトリの <ハブ実装パス> に倣う（canonical/sitemap 用の `site` 設定、static 出力など）。

## 2. ドメイン・オリジン構成（MUST）

- **1スポーク = 1リポジトリ = 1サブドメイン**（`<spoke>.<domain>`）。
- パスベース相乗り（`<hub-domain>/<spoke>`）**禁止**。
- ネストサブドメイン（`<spoke>.<hub>.<domain>`）**禁止**（理由はプロジェクトの SSL/運用方針に従う）。

## 3. セキュリティヘッダ（MUST）

<出力に含めるヘッダ設定ファイル（例: public/_headers）> に、本リポジトリ <既存ヘッダ実例パス> と同等のヘッダを設定する。

- 全パスに最低限: `X-Content-Type-Options: nosniff` / `Referrer-Policy` / `X-Frame-Options: DENY` / `Permissions-Policy`（不要機能は全無効） / `Strict-Transport-Security`。
- **CSP は `default-src 'self'` を基点**にし、`object-src 'none'` / `frame-ancestors 'none'` / `base-uri 'self'` を含める。外部許可元は **実際に使うものだけ** 最小で追加。
- 外部スクリプトを読む場合は **SRI** を検討。
- アセットは長期キャッシュ（`max-age=31536000, immutable`）可。

## 4. Service Worker 方針（MUST）

- <プロジェクトの SW 方針を記述（例: 新スポークは原則 SW を登録しない）>。
- どうしても必要なら **スコープ・キャッシュ戦略・更新方法を明記**し、レビューで合意を取る。SW スクリプト本体は `Cache-Control: no-cache` で配信する。

## 5. SEO 構成（MUST）

- `<html lang="...">`、`<meta name="viewport">`。
- **ページ固有の `<title>` と `description`**。
- **canonical** を絶対URLで出力（`site` 設定から生成）。
- **OGP**: `og.png`（1200×630 推奨）と `og:title` / `og:description` / `og:image`。共有 UI があれば流用する（例: <SeoHead 等>）。
- `favicon`、`robots.txt`（`Allow: /` と `Sitemap` 行）、`sitemap.xml` の生成・配信。
- 更新型コンテンツがあるスポークのみ RSS/Atom（任意）。

## 6. ブランド一貫性（SHOULD）

- 共有 UI / デザイントークン（例: <共有パッケージ名>）を取り込み、配色・タイポグラフィを揃える。

## 7. アクセシビリティ・モバイル（MUST）

- レスポンシブ（モバイル幅で崩れない、タップ領域・コントラスト確保）。
- 画像 `alt`、フォーカス可視、キーボード操作可能。
- **Lighthouse の Performance / Accessibility / Best Practices / SEO すべて 90+**。

## 8. プライバシー・計測（MUST）

- **localStorage / Cookie に PII を保存しない**。
- 計測は cookieless を推奨。導入時は CSP の `script-src` / `connect-src` を最小限で許可。
- secrets・トークンをフロントエンドやリポジトリに含めない。

## 9. 品質・テスト（SHOULD）

- 型チェック・lint・ビルドが通る。
- 壊れると致命的な中核ロジックに最低限のテストを置く。

## 10. レジストリ整合（MUST）

公開時に <登録 playbook の手順> でハブへ登録するため、**開発段階で次のメタデータを先に確定**する。スキーマは <レジストリの config.ts パス> に準拠。

- <共通フィールドと制約（id 規約、表示名、アクセント色、url、公開日 など）>。
- <ハブ固有フィールド（例: ゲームの genre/icon、地域の area など）>。

## 公開前セルフチェックリスト（開発完了の定義）

登録 PR を出す前に、すべて満たすこと。

### 構成
- [ ] <クリーンインストール+ビルドのコマンド> が成功し、<出力ディレクトリ> を出力する
- [ ] サブドメイン構成が設計原則どおり（フラットな `<spoke>.<domain>`）
- [ ] セキュリティヘッダ一式（CSP 含む）があり、外部許可元が最小
- [ ] SW 方針に従っている（必要な場合はスコープ・戦略を明記し合意済み）

### SEO / メタ
- [ ] lang / viewport / ページ固有の title・description
- [ ] canonical が正しい絶対URL
- [ ] OGP（og.png と og:* メタ）と favicon
- [ ] robots.txt と sitemap.xml が配信される

### 品質 / プライバシー
- [ ] Lighthouse の 4 カテゴリすべて 90+
- [ ] モバイル/デスクトップ両方でレイアウトが崩れない
- [ ] localStorage / Cookie に PII を保存していない、secrets を露出していない
- [ ] 中核ロジックに最低限のテスト（該当する場合）

### レジストリ
- [ ] config.ts のスキーマに合うメタデータが確定している
- [ ] ハブ固有の前提（例: 新規アイコンの実装など）を満たしている

## 参考

- 登録・デプロイ手順: <登録 playbook>
- 公開後の確認: <公開後チェックリスト>
````

### ステップ2: CLAUDE.md への参照追記

`CLAUDE.md` の「**プロジェクト固有ルール**」セクション（無ければ開発プロセス付近）に、次の趣旨の一行を追加する。**`.claude/rules/*.md` には書かない**（テンプレート所有のため `/sync-template` で失われる）:

> ハブに公開するスポークを開発するときは、必ず `docs/playbook/spoke-development-standards.md`（開発段階で満たすべき構成ルール）と <登録 playbook> を読み、MUST 項目とセルフチェックリストに従う。

## 完了条件

- `docs/playbook/spoke-development-standards.md` がプロジェクト固有の値で生成・**承認**されている。
- `CLAUDE.md` から本ルールが参照されている。

完了時のメッセージ例:

```
スポーク開発構成ルールのセットアップが完了しました。

✅ docs/playbook/spoke-development-standards.md（開発段階で満たすべき構成ルール）
✅ CLAUDE.md から参照を追記

今後スポーク（個別サイト/ゲーム）を開発する際は、このルールの MUST 項目と
公開前セルフチェックリストに従って実装します。
```
