# 変更のコミット

現在の変更内容を分析し、論理的な単位に分割してConventional Commits形式でコミットするコマンドです。

**引数:** なし（任意でコミット方針を渡してよい。例: `/commit ドキュメントだけ先に`）

---

## 手順

### ステップ1: 変更内容の把握（差分全文は読まない）

以下を並列で実行する。**この段階では差分全文を取得しない。**

```bash
git status
git diff HEAD --stat
git log --oneline -5
```

- 変更が1つもない場合は「コミット対象の変更がありません」と伝えて終了する。
- 直近のコミットメッセージのスタイル（言語・プレフィックス）を確認し、それに合わせる。

> **なぜ `--stat` か:** `git diff HEAD` の全文はこのリポジトリの実測で `--stat` の約 200〜280 倍（67KB 対 241B）。しかもコミット分割で数ターン回る間、その結果が毎ターン再送されキャッシュ書き込み単価で課金され続ける。ファイル名・パス・増減行数だけでコミット単位の大半は判断できる。

### ステップ2: コミット単位の設計

ステップ1の `--stat` の結果（ファイルパスと増減行数）だけで、変更ファイルを**論理的な単位**にグループ化する。

- 1コミット = 1つの意図（機能追加・バグ修正・ドキュメント更新などを混ぜない）
- 無関係な変更が混ざっている場合は複数コミットに分割する
- `.steering/` の更新は、対応する実装と同じコミットに含めてよい

### ステップ2.5: 必要な差分だけを読む

パスと増減行数だけでは type や要約が決まらないファイルに限り、**そのファイルだけ**差分を読む。

```bash
git diff HEAD -- [ファイルパス]
```

**差分を開かないもの（stat の増減行数だけで書ける）:**

- ロックファイル（`package-lock.json` 等）— 常に `chore` 扱い。全文を読む価値がない
- 新規追加ファイル — 差分＝全文になるため丸ごと読み込まれる。パスと行数、必要なら冒頭数十行（`head`）で足りる
- 大量の機械的変更（一括リネーム・フォーマット適用など）— 数ファイル分のサンプルを見れば足りる

**差分を読むもの:** 実装ロジックの変更。意図がパスから読み取れず、要約の質に直結するため。

### ステップ3: コミットの実行

各グループについて以下を実行する。

1. 対象ファイルのみを `git add [ファイルパス]` でステージする（`git add .` は複数グループがある場合は使わない）
2. 以下の形式でコミットする:

```
[type]: [変更内容の要約（日本語・50文字以内）]

[必要な場合のみ: 変更の理由や背景]
```

**type一覧:**

| type | 用途 |
|---|---|
| feat | 新機能 |
| fix | バグ修正 |
| docs | ドキュメントのみの変更 |
| refactor | 機能変更を伴わないコード整理 |
| test | テストの追加・修正 |
| chore | ビルド設定・依存関係・その他 |

### ステップ4: 結果報告

- 作成したコミットの一覧（ハッシュとメッセージ）を報告する
- **pushはユーザーから明示的に指示された場合のみ実行する**

## 注意事項

- `git commit --amend` や `git rebase` など履歴を書き換える操作は行わない
- **秘密情報の検出は自前で走査しない。** pre-commit フック（husky → lint-staged）で **secretlint が全ステージファイルに対して自動実行される**（`package.json` の `lint-staged` の `"*"` エントリ）。差分全文を読まない運用でも検出は担保されているため、目視や grep による二重チェックは行わない（誤検出の判断コストが増えるだけで、精度は secretlint に劣る）。
  - secretlint が検出した場合は **`git commit` 自体が失敗する**。その出力をユーザーに提示し、勝手に `--no-verify` で回避せず、対処を確認する
  - `.env` や鍵ファイルがステージ対象に含まれていることに気付いた場合は、secretlint の結果によらず警告する（`.gitignore` 漏れの可能性）
