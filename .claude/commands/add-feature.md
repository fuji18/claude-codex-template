# 新機能の追加 (完全自動実行モード)

**重要:** このワークフローは、ユーザーの介入なしに、開始から完了まで完全に自動で実行されるように設計されています。各ステップは完了後、ただちに次のステップへ移行し、途中でユーザーに確認を求めないでください(この指示は全ステップに適用される)。

**引数:** 機能名 (例: `/add-feature ユーザープロフィール編集`)

---

## ステップ1: 準備とコンテキスト設定

1. 現在のタスクコンテキストを確立する:
  - 機能名: `[引数で与えられた機能名]`
  - 日付: `[現在の日付をYYYYMMDD形式で取得]`
  - ステアリングディレクトリパス: `.steering/[日付]-[機能名]/`
2. 上記ステアリングディレクトリを作成する。
3. 以下の3つの空ファイルを作成する:
  - `[ステアリングディレクトリパス]/requirements.md`
  - `[ステアリングディレクトリパス]/design.md`
  - `[ステアリングディレクトリパス]/tasklist.md`

## ステップ1.5: GitHubブランチの準備

**まず `.claude/branch-policy.json` を読む**(`baseBranch` / `allowedPrefixes` / `remoteSessionPrefix`)。ブランチ戦略の判断は推測せず、常にこのファイルを根拠にする。

1. 現在のブランチを `git branch --show-current` で確認し、次のどちらかを選ぶ:

   **(a) すでに作業ブランチ上にいる場合**(`allowedPrefixes` のいずれかに一致。アプリのリモートセッションが生成した `claude/*` を含む)
   - **新しいブランチを作らず、そのブランチで作業する**
   - `claude/*` は**リネームしない**(セッションとブランチの紐付けが壊れる)。ポリシー上 `feature/*` と同格の正規ブランチとして扱う
   - ベースへの追従だけ行う: `git merge origin/[baseBranch]`(未取り込みの場合)

   **(b) 保護ブランチ(`protectedBranches`)上にいる場合**
   - 機能名をケバブケース(半角英数字とハイフン)に変換する(例: `ユーザープロフィール編集` → `user-profile-edit`)
   - ブランチ名形式: `feature/[YYYYMMDD]-[ケバブケース機能名]`
   - ポリシーの `baseBranch` から切る:
     ```bash
     git fetch origin [baseBranch]
     git checkout -b [ブランチ名] origin/[baseBranch]
     git push -u origin [ブランチ名]
     ```

2. 作業ブランチ上にいることを確認してからステップ2に進む。

## ステップ2: プロジェクト理解

1. `CLAUDE.md`を読み、プロジェクトの全体像を把握する。
2. 関連する永続ドキュメントの**該当節のみ**を読み、関連する設計思想やアーキテクチャを理解する(チケット Issue 起点の場合は Issue の「根拠」に挙がった節から辿る。`docs/` の6ファイル全読みはしない)。

## ステップ3: 既存パターンの調査

1. 既存の類似実装を検索する:
  - ピンポイントな検索(キーワードが明確な場合)は Grep ツールを直接使う
  - 複数ディレクトリ・命名規則をまたぐ広範囲の探索は **Explore subagent に委譲し、結論だけを受け取る**(司令塔のコンテキスト節約)
2. 検索結果を分析し、既存の実装パターン、命名規則、コンポーネントの利用方法を特定する。

## ステップ4: 計画フェーズ (ステアリングファイルの自動生成)

1. `Skill('steering')`を**計画モード**で実行し、ステップ1で作成した3つのファイル (`requirements.md`, `design.md`, `tasklist.md`) の内容を生成する。

## ステップ5: 実装 (Codex 委託 → Sonnet fork フォールバック)

**司令塔は実装コードを書かない。** 実装フェーズは委託する。**既定は Codex**(`delegate-codex.sh impl`)、使えなければ `implement-ticket` スキル(`context: fork` / Sonnet)。委託先が変わっても**司令塔の分岐ロジックは同じ**(完了 / 判断待ち / 失敗)であることが設計要件。司令塔は Opus のまま維持され、モデルの切り替えは不要。

1. **委譲前に作業ツリーをクリーンにする**(`git status` で確認)。fork の編集はチェックポイント(`/rewind`)で戻せない可能性があり、Codex の編集は原理的に戻せない。git を退避手段として確保しておく。
2. **このセッションで既に `exit 3` を受け取っている場合は 3 を飛ばし、4(Sonnet fork)へ直行する**(恒久フォールバック。同じ環境欠落を毎回試さない)。
3. `bash .claude/scripts/delegate-codex.sh impl .steering/[dir]` を実行し、**終了コードだけを見て分岐する**(サマリー本文から成否を推測しない):

| exit | 意味 | 司令塔の動き |
| --- | --- | --- |
| `0` | 完了 | ステップ6(検証)へ進む |
| `1` | 判断待ち | 判断を下し、**`design.md` に追記してから**再委託する(tasklist の途中から再開される) |
| `2` | 失敗(タスク起因) | 原因を分析する。設計起因なら `design.md` を修正して再委託。**2 回連続で失敗したら委託を打ち切り**、`Skill('implement-ticket')` に引き継ぐ |
| `3` | Codex 利用不可 | **このセッションは以降ずっと `Skill('implement-ticket')` を使う**(恒久フォールバック)。`delegate-codex.sh` を呼び直さない |
| `4` | Codex 側のレート上限 | 一時フォールバック。`tasklist.md` と `git diff --stat` を根拠に**ユーザーへ 3 択を提示する**: (a) 待つ(残タスクが多いとき) (b) `Skill('implement-ticket')` に引き継ぐ(残り 1〜2 タスク) (c) 部分成果を破棄(ビルドが壊れていて進捗が 1 タスク以下)。**司令塔が自分で引き取るのを既定にしない** |
| `5` | 計画が未完成 | `design.md` を書き切り、冒頭の印を `<!-- status: ready -->` に変えてから再委託する。**追記だけでは同じところで止まる** |

4. **Sonnet fork 経路**(`exit 3` を受けた場合、または Codex を使わない判断をした場合): `Skill('implement-ticket')` にステアリングディレクトリのパスを渡して実行し、戻り値の `判定` で分岐する:

| 判定 | 司令塔の対応 |
| --- | --- |
| `完了` | ステップ6(検証)へ進む |
| `判断待ち` | 判断を下し、**`design.md` に追記してから**再実行する。**差し戻しの理由が「計画未完成(`<!-- status: draft -->`)」の場合は、`design.md` を書き切ったうえで印を `<!-- status: ready -->` に変えてから再実行すること** |
| `失敗` | 原因を分析する。設計起因なら `design.md` を修正して再実行、根本原因が不明なら `/model fable` への一時切替をユーザーに提案する |

5. `判断待ち` の往復が 2 回を超えた場合、`design.md` の粒度が不足している。判断を個別に足し続けるのをやめ、`design.md` を書き直してから再開する。

6. **委託が中断したとき**(exit 4、または `bash .claude/scripts/codex-run.sh list` に `status=running(プロセス不在)` が出るとき)は、サマリーが存在しない。`tasklist.md` → `git diff --stat` → 型チェック の順に実態を確かめ、上の 3 択に進む。処理後に `bash .claude/scripts/codex-run.sh set-status [id] [interrupted|discarded|failed]` で record を実態に合わせる。

- **❌ 絶対禁止の行為:**
  - 司令塔が自分で `tasklist.md` を消化すること(委譲を迂回すること)。
  - 未完了タスクを「後でやる」などの理由で意図的にスキップすること。
  - `判断待ち` に対して `design.md` を更新せずに再委託・再実行すること(同じところで再び止まる)。
  - **終了コードを見ずにサマリーの文面で成否を判断すること**(`codex exec` の `exit 0` はタスクの成否を表さない)。

---

## ステップ6: 検証 (レビューと品質チェックを並列実行)

1. `tasklist.md`の全タスクが完了したことを最終確認する。
2. 以下の 2 つのサブエージェントを**同一メッセージ内で並列起動**する(互いに独立しているため直列にしない):
  - `code-reviewer`(Sonnet): prompt: "今回実装した `[機能名]` の変更差分をレビューしてください。対象ファイルは `[実装したファイルのパスリスト]` です。docs/ のスペック(機能設計・開発ガイドライン)との整合性も確認し、確信が持てない指摘も含めて全て報告してください。"
  - `test-runner`(Haiku): 全品質チェック(lint・型チェック・テスト・フォーマット)の実行と機械的なエラーの自動修正を依頼する。E2E 基盤(playwright 等)がありローカルサーバーが起動可能な場合は E2E 実行も依頼する(環境未整備ならスキップし、その旨を PR ボディに記載する)。
3. 以下の**両方**に該当する場合のみ、`implementation-validator` サブエージェントも追加で起動する(トークン最適化のため通常はスキップ):
  - 変更が 200 行以上
  - 認証・決済・データ永続化・外部 API 連携など、スペック整合が特に重要な機能
4. 両方の結果が返ったら、司令塔が対応する:
  - code-reviewer の `[Critical]` / `[Major]` の指摘は修正する。`[Minor]` は tasklist.md の申し送り事項に記録する
  - test-runner の「未解決の問題」(設計判断を伴うテスト失敗・型エラー)は司令塔が分析して修正する
5. 修正した場合は test-runner を再起動して失敗したチェックのみ再実行させる(**修正サイクルは最大3周まで**)。テストの期待値をテストを通すためだけに書き換える、`@ts-ignore` や `eslint-disable` で隠蔽する、といった対処は禁止。3周で解消しない場合は申し送り事項に記録して次に進む。
6. Codex に委託した場合、検収が通った時点で `bash .claude/scripts/codex-run.sh accept [run-id]` を実行し、run record の `accepted` を立てる(run-id は委託時の出力に出ている)。立て忘れると未検収の記録が残り続ける。

## ステップ7: 振り返りとドキュメント更新

1. `Skill('steering')`を**振り返りモード**で実行し、`tasklist.md`に申し送り事項を記載する。
  - 実装完了日
  - 計画と実績の差分
  - 学んだこと
  - 次回への改善提案

2. 今回の変更がプロジェクトの基本設計やアーキテクチャに影響を与えるか判断する。

3. 影響がある場合、`docs/`内の関連する永続ドキュメントを`Edit`ツールで更新する。

## ステップ8: GitHubへのコミット・PR作成

**このステップはステップ7完了直後に自動で実行すること。**

1. **変更をコミットする**: `Skill('commit')` を実行する(変更の分析と適切な粒度での Conventional Commits はスキルが担う)。コミット完了後、`git push` を実行する(このフローでは push まで行うことをユーザーが `/add-feature` 起動時に許可している)。

2. **GitHub PRを作成する**:
   - タイトル: `feat: [機能名]`
   - ベースブランチ: **`.claude/branch-policy.json` の `baseBranch` を使う**(推測しない。人間向けの説明は `docs/development-guidelines.md`、機械が読む値はポリシーファイルが正)。ポリシーファイルが無い場合のみデフォルトブランチ `main`。**リポジトリに存在しないブランチをベースに指定しないこと**(`--base` の指定漏れ・ポリシー外の値は PreToolUse hook と CI の `branch-policy` ジョブがブロックする)
   - ボディ: `.github/pull_request_template.md` の構成に従う(セクション構成を変えない)
   ```bash
   gh pr create \
     --title "feat: [機能名]" \
     --base [ブランチ戦略に従ったベースブランチ] \
     --body "## 概要
   [実装内容の概要と主な変更ファイル]

   ## 関連 Issue

   Closes #[チケットIssue番号]

   ## ステアリング

   [.steering/ ディレクトリ名]

   ## 検証
   - [x] /check(lint・型チェック・テスト・フォーマット)がパス
   - [x] 動作確認済み: [実施内容。E2E 等の未実施項目があれば理由を明記]

   🤖 Generated with [Claude Code](https://claude.com/claude-code)"
   ```

   - 「関連 Issue」節は、チケット Issue が起点の場合(`/next-ticket` / `/fix-issue` 経由、または起動時に Issue 番号が与えられた場合)のみ記載する。Issue が存在しない単発の `/add-feature` では **Issue を新規作成せず**、節ごと削除する。
   - 「検証」のチェックは実際に実施・パスしたものだけに付ける。未解決の残課題(tasklist.md の未完了項目等)がある場合は概要に明記する。

3. PRのURLをユーザーに通知する。あわせて、次の作業に移る前の `/clear` を推奨する(作業状態は Issue・`.steering/`・git に永続化済み)。

## 完了条件

このワークフローは、以下の全ての条件を満たした時点で自動的に完了となる。
- ステップ1.5: ポリシー準拠の作業ブランチ上にいる(新規作成、または既存の `claude/*` 等をそのまま使用)。
- ステップ5: `implement-ticket` が `完了` を返し、`tasklist.md`の全てのタスクが完了状態（`[x]`または正当な理由でスキップ）になっている。
- ステップ6: code-reviewer の `[Critical]` / `[Major]` 指摘が解消し、test-runner の全チェック(`test`, `lint`, `typecheck` 等)がエラーなく成功している。
- ステップ7: `tasklist.md`に申し送り事項が記載されている。
- ステップ8: コミット・PRが作成され、PRのURLがユーザーに通知されている。

この完了条件を満たすまで、自律的に思考し、問題解決を行い、作業を継続すること。
