## 計画フェーズ(司令塔の担当)

### 基本フロー

1. **ドキュメント作成**: 永続ドキュメント(`docs/`)で「何を作るか」を定義する
2. **作業計画**: ステアリングファイル(`.steering/`)で「今回何をするか」を計画する
3. **実装**: `implement-ticket` に委譲する(司令塔は実装しない)
4. **検証**: `code-reviewer` + `test-runner` に委譲し、指摘の判断だけ司令塔が行う
5. **更新**: 必要に応じて `docs/` を更新する

### ドキュメント作成時の承認

**1 ファイルずつ作成し、必ずユーザーの承認を得てから次に進む。** 承認待ちであることを明確に伝える:

```
「[ドキュメント名]の作成が完了しました。内容を確認してください。
承認いただけたら次のドキュメントに進みます。」
```

### ステアリングファイルの作成(steering スキル)

作業ごとに `.steering/[YYYYMMDD]-[タスク名]/`(例: `20250115-add-user-profile`)を作成し、`steering` スキルを使う。

- **モード1(計画)**: `requirements.md` / `design.md` / `tasklist.md` の作成 — 司令塔(Opus)
- **モード2(実装)**: tasklist の消化と更新 — **`implement-ticket` の fork(Sonnet)が担当する**
- **モード3(振り返り)**: 申し送りの記載 — 司令塔(Opus)

**モード1 の `design.md` は、実装者が設計判断を一切せずに実装できる粒度まで書き切る。** fork は会話履歴を引き継がず `design.md` / `tasklist.md` だけを読むため、ここに書かれていない判断は必ず「判断待ち」で戻ってくる。粒度の不足がそのまま往復コストになる。

### プロジェクト開始時(技術スタック整合)

`docs/ideas/` の技術選定がテンプレート既定(Node.js / TypeScript)と異なる場合、実装を始める前に検証コマンド・devcontainer・ツールチェーンの置換をタスク化し、`CLAUDE.md` の技術スタック節を更新する(`/kickoff` フェーズ1 が担当)。
