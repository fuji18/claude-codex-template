# 共通ルール: スペック駆動開発(実装)

> このファイルは `CLAUDE.md` からインポートされ、**メインセッションと全サブエージェントに読み込まれる**。
> 司令塔だけが使うルール(モデル運用・コンテキスト管理・レビュー起動・ブランチ/チケット運用・計画フェーズ)は
> `.claude/rules/lead/` にあり、SessionStart hook がメインセッションにのみ注入する。
> **ここに追記するときは「実装者やレビュアーにも要る内容か」を基準にする。** 司令塔だけが使うものは `lead/` に置く。

## 実装前の確認

1. 関連する永続ドキュメント(`docs/`)の**該当節のみ**読む(チケット Issue の「根拠」に挙がった節を起点にする。6 ファイル全読みはしない)
2. 既存の類似実装を検索する(ピンポイントな検索は Grep、複数ディレクトリ・命名規則をまたぐ広範囲の探索は Explore subagent に委譲し結論だけ受け取る)
3. ライブラリの API 仕様が不確かなとき(メジャーバージョン更新直後・知識カットオフ以降のリリース等)は Context7(`mcp__context7__*`)で最新ドキュメントを引く。確信があるなら引かない
4. `CLAUDE.md` の「プロジェクト固有ルール」節を確認する(MCP の使いどころ・スポーク構成ルール等、このプロジェクト固有の制約はそこに集約されている)
5. 既存パターンを理解してから実装を始める

## スコープガード

優先度(P0/P1/P2)がある場合、**P0 以外を実装しない**。P1/P2 の前倒しはユーザー承認を得てから行う。チケット・`design.md` に書かれていない機能を足さない。

## 完了報告と回復のルール(when X, do Y)

- 完了と報告する前に品質チェック(lint・型チェック・テスト・フォーマット)を通す。失敗が残る場合は「完了」と報告せず、**残課題として明示する**
- PR 作成前に `.steering/*/tasklist.md` の未完了項目を確認し、残がある場合は PR ボディに明記する
- **同じエラーの修正に 2 回連続で失敗したら、同じアプローチを繰り返さない。** 原因の仮説を書き出してから別のアプローチを取る
- **`design.md` に書かれていない設計判断が必要になったら、推測で進めない**

上の 2 つに当たったときの動きは立場で変わる:

| 立場 | 動き |
| --- | --- |
| サブエージェント(実装・レビュー等) | **その場で停止して報告する。** 自力で解決を試みない。設計判断は司令塔の仕事 |
| メインセッション(司令塔) | 判断を下して `design.md` に追記してから続行する。根本原因が不明なら `/model fable` への一時切替を検討する |

## ステアリングファイル

作業単位で `.steering/[YYYYMMDD]-[タスク名]/` に `requirements.md` / `design.md` / `tasklist.md` を置く。実装中は `tasklist.md` の進捗を随時更新する(`- [ ]` → `- [x]`)。タスクが大きすぎる場合はサブタスクに分割して差し替えてよい。技術的理由で不要になったタスクは `- [x] ~~タスク名~~ (理由: ...)` の形で残す。**理由なくスキップしない。**
