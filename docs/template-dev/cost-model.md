# コストモデル: なぜこの運用なのか

`.claude/rules/` には「何をするか」だけを置き、根拠はここに退避している。ルールファイルは**サブエージェントを起動するたびに全量が課金対象になる**ため、背景説明を置く場所として適さない(この判断自体もここに書いてある理由)。

このファイルは `docs/template-dev/` にあるため、Claude Code の自動読み込み対象外。プロダクト開発を始めたら削除してよい。

---

## 1. 消費の主因はコンテキストの大きさ

`/usage` の実測で得られた内訳:

- 消費の **72%** が 150k を超えるコンテキストで発生していた
- コストの約 **6 割**がキャッシュの**書き込み**だった

キャッシュが効いていても、書き込みは基本入力の 1.25〜2 倍の単価がかかる。そしてコンテキストが大きいほど毎ターンの書き込み量が増える。つまり **「キャッシュを効かせる」よりも「キャッシュ対象を小さく保つ」方が効く**。

ここから導かれる運用:

- チケットの区切りで `/clear`(前チケットのツール結果を次チケットで再送し続けるのが最大の浪費)
- 調査ログと実装ログを同じセッションに混ぜない
- 重いスキルを目的外でロードしない

## 2. なぜ実装フェーズだけモデルを分けるのか

トークン消費が最も大きいのは「実装 → テスト → エラーを読む → 修正」のループ。ツール呼び出しが多く、エラーログと差分が積み上がり、それが毎ターン再送されるため加速度的に高くつく。**この区間だけ安いモデルで回す**のが、上限消費を減らす最も効果の大きい手段になる。

一方で設計判断を安いモデルに任せると、誤った設計のまま実装が進み、やり直しでかえって高くつく。そのため「設計 = Opus / 実装 = Sonnet」で分ける。

## 3. なぜ手動切替をやめて fork にしたのか

当初は `/clear` → `/model sonnet` → 完了後 `/model opus` という手動運用だった。これには 2 つの問題があった。

1. **手間**: 毎チケット発生する
2. **失敗モードが致命的**: 切替前の `/clear` を忘れると、膨らんだコンテキスト全体が切替先でキャッシュミスとなり全額課金される。しかも計画フェーズ直後はコンテキストが最も膨らんでいる

`context: fork` + `model: sonnet` のスキルに委譲すると、両方が構造的に解決する。

| | 実装ループの単価 | 司令塔に残る実装ログ | 人の規律への依存 |
| --- | --- | --- | --- |
| 全部 Opus | Opus | 全部 | — |
| 手動切替 | Sonnet | `/clear` すればゼロ | **高**(忘れると全額) |
| fork 委譲 | Sonnet | サマリーのみ | **なし** |

うまくいったときのコストは手動切替と fork でほぼ同じ。差は**失敗したときにどうなるか**にある。fork は忘れようがなく、さらに PreToolUse hook が司令塔による実装を機械的に止めるため、最悪ケースが構造的に消える。

### fork の固定費(トレードオフ)

fork は会話履歴を引き継がないため、spawn のたびに以下を払う。

- システムプロンプト
- **CLAUDE.md と `@` インポートしている `.claude/rules/*.md` の全量**
- ツールスキーマ
- `design.md` / `tasklist.md` の読み込み

1 spawn あたりおおむね 15〜20k トークン規模の「冷えた」書き込みになる。したがって:

- **spawn 回数を無闇に増やさない**(既定は 1 チケット 1 fork。tasklist が大きいときだけ分割する)
- **共通ルールを太らせない**(次節)

## 4. なぜ rules を lead/ と共通に分けたのか

カスタムサブエージェントは CLAUDE.md と `@` インポートを**必ず**読み込む。エージェント単位で除外する設定は存在しない(除外されるのは組み込みの Explore / Plan だけ)。

分割前の `.claude/rules/*.md` は 10,286 文字あり、その全量が `code-reviewer` / `test-runner` / `doc-reviewer` / `implementation-validator` を起動するたびにロードされていた。`/check` を 1 回回すだけで 10k 文字を積んでいたことになる。

しかも内容の多くはサブエージェントにとって**無意味か、実行不能**だった。

- モデル運用方針: サブエージェントはモデルを選べない
- コンテキスト管理: `/clear` `/compact` `/usage` はサブエージェントから実行できない
- ブランチ・チケット運用: 実装者はブランチを切らず Issue も触らない
- レビューの使い分け: レビューを起動するのは司令塔

`SessionStart` フックは**メインセッションでのみ発火**し、`additionalContext` を注入できる(サブエージェント起動時に発火するのは `SubagentStart` で、そちらは context を注入できない)。この非対称性を使って、司令塔専用ルールを `.claude/rules/lead/` に置き、フックから注入する構成にした。

結果として、サブエージェントに載る共通ルールは約 4,000 文字まで縮む。

### 4.1 訂正(2026-10-21): `.claude/rules/` はサブディレクトリまで自動ロードされる

上の構成は「`lead/` は `@` インポートしなければ載らない」を前提にしていたが、Claude Code は `.claude/rules/` 配下の `.md` を**サブディレクトリまで再帰的に自動ロードする**。実測で、`lead/` の 6 ファイルと `mode/econ.md`・`mode/degraded.md` が全セッション(サブエージェントを含む)に載っていた。帰結は 3 つ:

- サブエージェントに `lead/` + `mode/` の約 36KB が毎回載り、上の削減が成立していなかった
- normal モードでも「現在のハーネスモード: B」と「同: C」の両方が載り、指示が矛盾していた
- SessionStart hook の出力(14.8KB)が上限(約 10,000 文字)を超え、先頭 2KB のプレビューに切り詰められていた = フック注入は実際には届いていなかった

対処: 各ファイルの先頭に frontmatter `paths: [".claude/rules/<dir>/**"]` を付け、自動ロードを「そのディレクトリ自体を扱うとき」に限定した。フックは本文を貼らず Read すべきパスを出す(`mode/<mode>.md` は約 4KB なので従来どおり本文を注入)。ディレクトリを移動しなかったのは、参照 40 箇所超・委託禁止領域の 2 系統・`template-manifest.json` を同時に動かすことになり、下流の `/sync-template` で旧ディレクトリが残るため。

## 5. 権限方針(A: allowed-tools のみ)

fork が未承認のコマンドを実行しようとすると承認待ちで止まる。これを避けるには `settings.json` の allow を広げればよいが、通常セッションでも権限が広がる。

現状は方針 A(`settings.json` を広げない)を採っている。実装に要る npm / npx / git status・diff は既に allow 済みで、追加の恒久的な拡大なしに大半が動くため。**止まったコマンドを記録してから、必要なぶんだけ足す**のが、権限を無駄に広げない順序になる。
