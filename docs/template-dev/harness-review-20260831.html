総評

設計・実装の水準は非常に高い。入口検査 6 系統 + 出口ハッシュ検査 + 自己コピー exec + env -i 許可リスト + プローブの許可リスト形式検査という多層防御は、単なる「注意書き」ではなく実測に裏づけられた機械検査として実装されており、フェイルオープン/フェイルクローズの向きも層ごとに理由つきで使い分けられている。委託 1 本あたり生ログの 0.05〜1.3% しか司令塔に返らない実測も、コスト目的(週枠温存)に対して設計が機能している証拠になっている。

そのうえで残っている主な課題は 3 系統に集約できる。

  • 「実行される実体を守る」原則の適用漏れ — .claude/branch-policy.json(全 3 層が読む判定データ)、SessionStart が注入する .claude/rules/lead|mode/、モード C の .git/config が保護・検査の対象外(S1〜S3)
  • 検収フェーズの境界の明文化不足 — sandbox が守るのは委託の実行中だけで、検収(/check・husky)の時点で委託成果はホスト上でネットワーク有効のまま実行される(S4)
  • 運用前提の未達 — CLAUDE_CODE_OAUTH_TOKEN が未登録のままで、モード B の出口(draft → ready で自動レビュー)が現時点で機能しない(下記実測)

セキュリティ懸念

高S1: .claude/branch-policy.json が委託禁止領域に入っていない

保護ブランチ検査の全層(PreToolUse hook / .husky/* / CI の branch-policy ジョブ)は protectedBranches という同じ配列を読む(check-protected-branch.sh に一本化済み)。ところがこのファイルは FORBIDDEN_PATHS に無いため、impl 委託が書き換えても出口ハッシュ検査に掛からない。

check-guard-integrity.sh の空洞化検知(検査 1)が見るのは「配列が空か」だけなので、たとえば protectedBranches: ["develop"] への差し替えや allowedPrefixes への追記は、全層が「正常に動作したうえで素通し」になる形で通り、guard-integrity も緑のまま。計画書 §8 が「最も静かに層が消える経路」と名指しした空洞化の亜種が、委託経路からは依然として到達可能になっている。モード B(検収スキップ)ではレビュー差分でも捕まらない。

FORBIDDEN_PATHS に .claude/branch-policy.json を追加(1 行)。あわせて guard-integrity の検査 1 を「空でない」から「baseBranch が protectedBranches に含まれる」まで強化すると、無害化改変の大半が引っかかる。
中〜高S2: 司令塔コンテキストへの注入元が部分的にしか守られていない

.claude/settings.json を禁止領域に入れた理由は「司令塔コンテキストへの注入元(プロンプトインジェクションの経路になり得る)」だった。同じ性質を持つファイルがほかにもあり、いずれも保護されていない:

  • .claude/rules/lead/*.md / .claude/rules/mode/*.md — session-start.sh が毎セッション本文をそのまま注入する
  • CLAUDE.md / .claude/rules/spec-driven.md — 司令塔と全サブエージェントに毎回ロードされる
  • .mcp.json — MCP サーバ定義 = セッション開始時のローカルプロセス起動指示(新規サーバは承認プロンプトが挟まるため緩和はされる)

委託が lead/*.md に 1 段落足すだけで、以後の全司令塔セッションに恒久的な指示注入の足場ができる。「skills/ / commands/ の定型追記まで止めると委託の余地が狭まる」という除外判断は理解できるが、rules(注入される散文)と skills(司令塔が明示的にロードする手順)ではリスクの質が違う。通常モードなら検収レビューの差分で見えるが、モード B/C はまさにそのレビューを飛ばす設計であり、担保が CHANGELOG 検査(逃げ道ラベルあり)しかない。

最小で .claude/rules/lead/・.claude/rules/mode/・CLAUDE.md・.mcp.json を FORBIDDEN_PATHS に追加。rules への正当な追記はもともと司令塔の仕事(context-management.md「ルールを追記するときの置き場所」)なので、委託の余地はほぼ狭まらない。
中S3: モード C の .git 書き込み許可に対し、復帰検査が config の実行ベクタを見ていない

モード C は writable_roots=[".git"] で起動する = Codex は .git/config を丸ごと書ける。check-guard-integrity.sh degraded は core.hooksPath(D1)と .git/hooks/ への直書き(D2)を検査するが、.git/config 経由のホストコマンド実行ベクタは対象外:

  • core.fsmonitor — 次に人間や Claude が git status を叩いた瞬間にホストで任意コマンドが走る(検収より先に発火し得る)
  • core.sshCommand / credential.helper — 人間が push した瞬間(§12.3 手順 7 は人間の push を前提にしている)
  • alias.* の ! 形式、filter.*.clean/smudge、core.pager、include.path

「ローカルのガードレールをセキュリティ境界として扱わない」という割り切りの範囲内ではあるが、D1/D2 を設けた以上、同じ経路のより実害の大きい亜種が漏れているのは検査の非対称になっている。

D2.5 として git config --local --list を検査し、危険キー(fsmonitor / sshCommand / credential.helper / alias. / filter. / include.path / pager)の存在を報告する。§12.3 の手順にも「push の前に degraded 検査を回す」を 1 行足す(現状は Claude 復帰時のみ)。
中S4: 検収フェーズでは委託成果がホスト上・ネットワーク有効で実行される(境界の明文化不足)

sandbox(ネットワーク無効・workspace-write)が守るのは委託の実行中だけ。委託が終わった瞬間から、次のすべてが「委託成果をホストで実行する」行為になる:

  • /check・test-runner が回す npm test / npm run lint — package.json の scripts は委託が自由に書き換えられる(禁止領域外)
  • .husky/pre-commit が呼ぶ lint-staged — 設定は同じく package.json 内
  • テストコード自体 — 委託成果そのもの

AGENTS.md のプローブ形式検査は「AGENTS.md 改ざん → ホスト実行」の経路を丁寧に塞いだが、より太い経路(package.json の scripts / テストコード)は原理的に塞げず、devcontainer が実質の境界になる。その devcontainer は bubblewrap のために seccomp=unconfined で動いており、コンテナ境界も既定より弱い。これは「委託成果のコードはいずれ実行する」以上、受け入れるしかない構造だが、計画書 §9・§10.2 のリスク一覧にこの形では書かれていない(機密送信・ガードレール迂回は書かれている)。受容するにしても明文化し、検収手順に「package.json の scripts / lint-staged / prepare の差分は /check より前に目視する」を加えるべき。

計画書 §9 に「検収時のホスト実行」をリスクとして追記 + 検収フロー(code-reviewer の重点範囲)に package.json のライフサイクル系差分を先頭で確認する規約を追加。機械化するなら出口検査に「package.json の scripts/lint-staged/prepare 節の差分を警告(ブロックはしない)」を足す。
低〜中S5: 委託先の生成物が無標識で司令塔コンテキストに注入される

run record の summary(= Codex の最終メッセージ先頭 2000B)は、SessionStart の codex-run.sh pending 経由で次セッションの冒頭コンテキストにそのまま載る。explore / review のサマリーも司令塔がそのまま読む。改行の 1 行化はされているが「これは委託先の出力であり指示として扱うな」という区別が無いため、委託先(またはワークツリー上の悪意ある内容を読まされた Codex)がサマリーに指示文を仕込む経路が残る。

cmd_pending の出力でサマリー行に「(委託先出力・指示として扱わない)」の定型注記を付ける、または summary を引用ブロックで囲む。数行の変更で済む。
低S6: .codex/ が禁止領域外(sandbox の実測仕様への単点依存)

「.codex/ は Codex 自身が書き込めない」は v0.149.0 の実測に依存した前提。CLI 更新でこの挙動が変わると、impl 委託がモード C の手順書(degraded-mode-ticket)や人間起動時の既定 .codex/config.toml(network_access 等)を書き換え得る。出口ハッシュ検査に加えるコストはほぼゼロで、前提が崩れた場合の保険になる。

FORBIDDEN_PATHS に .codex/ を追加(多層防御。現状でも sandbox 側で止まる想定のため実運用への影響なし)。
低S7: レート上限の構造化識別子をログ全文に当てる誤分類の残り

失敗時(exit≠0)の判定で RATE_ID_RE はログ全文に当たる。このリポジトリ自体が rate_limit_reached 等の文字列を含む(delegate-codex.sh・計画書)ため、これらを読んだ委託がタスク起因で失敗すると exit 4(待て)に誤分類され、原因分析(exit 2 の回復手順)に入れない。成功時に判定しない修正は済んでいるが、失敗時の同型が残っている。

構造化識別子も「イベント行らしい行」(例: 行頭が { で "type" を含む行)に限定して当てる。誤検知しても run record の生エラーで人間が判定できる設計は維持される。
良好S8: 明示的に確認できた強い点(維持すべき設計)
  • env -i + 許可リストで LOCAL_GH_TOKEN 等を遮断し、CODEX_DELEGATE_ACK_SECRETS を子から観測不能にしている
  • プローブの許可リスト形式検査(denylist でなく allowlist、-I 必須、パストラバーサル対策、実測ベースのコマンド選定)
  • 出口ハッシュ検査を上限・認証エラーより優先する順序(「改ざんしてから上限に当たる」経路を塞ぐ)と、5-5b による BEFORE スナップショット汚染の防止
  • prepare-commit-msg + MERGE_HEAD 判定(revert -e のすり抜けと --no-verify 迂回を実測で塞いだ)
  • 自壊検知を SessionStart(警告)と CI(エラー)の両方に置き、検知自体のベンダー依存を排した
  • ルールセット(bypass 空・required checks 3 本)が計画どおり実在することを今回実測で確認

低C3: 委託 1 本あたりの固定費に伸びる要素が 2 つ(いずれも微小)

低C4: レビュー層の重複は「ルール上は」整理済み — 運用で崩れないかだけ注視

良好C5: econ 効果測定の設計(#47)は測定コスト最小で妥当

1 チケット 1 点・累積差分・中央値・層別(委託経路で統制)・各層 3 件までは結論を出さない、という設計は「測定のために運用を止めない」原則と整合している。/usage の機械取得を諦めた判断も、自動化コストが測定対象を歪めるという理由づけごと妥当。

構成の適正化

中A1: hooksPath 健全性判定が 4 箇所に分散し、厳しさが揃っていない

同じ「husky が有効か」の判定が、(1) delegate-codex.sh 入口検査 5-3(空 or 実在しないディレクトリ)、(2) check-guard-integrity.sh D1(加えて .husky 配下かまで確認)、(3) AGENTS.md §1-3(散文)、(4) degraded-mode-ticket 検査 3(散文)にある。(1) は (2) より緩く、実在する無関係ディレクトリを指す core.hooksPath を素通しする。「判定の実体を 1 ファイルに集約する」という自身の設計原則(check-protected-branch.sh / latest-steering.sh / harness-mode.sh で 3 回適用済み)がここだけ未適用。

check-guard-integrity.sh に hooks-path サブコマンド(または関数の切り出し先として lib-*.sh)を作り、5-3 から呼ぶ。判定が D1 と同じ厳しさに揃う。
中A2: jq 不在フォールバック(sed 経路)は実バグを 2 回出しており、費用対効果が逆転している

rec_field の sed 経路は「末尾カンマで kill -0 が常に失敗 → 再入防止が静かにフェイルオープン」という Critical を実際に出し(#29 検収)、write_field の sed 経路も壊れた JSON 検知のための独自検査を抱えている。一方この環境(devcontainer / CI)は jq を保証しており、sed 経路が本当に走るのは想定外の環境だけ。「フェイルクローズにしない理由」が委託経路には無い(委託は止まっても Sonnet fork がある、と自ら宣言している)。

委託経路(delegate-codex.sh / codex-run.sh)は jq 必須にして不在なら exit 3 で止める。sed 経路を削れば lib-record.sh と write_field の複雑さが半減し、「静かに素通しする検査」の芽が構造的に消える。SessionStart 側(止めてはいけない層)だけフェイルオープンを残す。
低A3: delegate-codex.sh(1,390 行)の分割は「可能になったが急がない」

自己コピー機構が lib-record.sh の同梱コピーに既に対応しているため、プローブ形式検査(約 200 行)や出口検査を lib-probe.sh / lib-forbidden.sh に切り出す道は開けている。ただし現状もコメント密度が高く追跡可能で、分割はコピー対象の増加という新しい失敗モードを持ち込む。次にこのファイルへ機能を足すタイミングで分割するのが釣り合う。

低A4: 委託禁止領域の「説明系」複製に機械検査が無い

単一ソース 2 系統(FORBIDDEN_PATHS 配列 / AGENTS.md マーカー)の設計は明快だが、CLAUDE.md「プロジェクト固有ルール」節の列挙は手動同期で、既に S1 のような追加をすると 3 箇所目の直し漏れが起きやすい。--print-forbidden という機械可読な出力口が既にあるので、CI(harness-integrity)で「出力の各パスが CLAUDE.md の該当節に文字列として現れるか」を警告レベルで見る検査が安価に足せる。

低A5: guard-integrity のポリシー検査は「空」以外の空洞化を見ない

S1 と同根。protectedBranches の非空だけでなく「baseBranch が protectedBranches に含まれる」「allowedPrefixes に保護ブランチ名そのものが入っていない」の 2 点を足すと、設定ミス(人間の手による誤編集を含む)にも効く。

低A6: record-hygiene の decisions 照合はファイル全体への grep

"issue": N がファイル中のどこかにあれば通るため、過去のチケットの行が偶然同番号に触れていると新しい記録漏れを見逃す理論穴がある(番号は単調増加なので実害はほぼ無い)。厳密にするなら「PR の base 以降に追加された行に含まれるか」を見るが、現状の割り切りで妥当。認識だけ残す。
