04セキュリティ懸念

前提: 良くできている点委託経路はフェイルクローズ(denylist 不在・空・find/grep 不在で委託拒否)、ガードレールはフェイルオープン + 消失検知という非対称が一貫している。ruleset は bypass 空、push protection 有効、claude.yml は author_association で第三者起動を遮断、claude-code-review.yml の draft 条件も記載どおり。S1〜S6・S8 は残余リスクであり、設計の破綻ではない。ただし S7 は例外(設計ではなく設定の欠落で、レビュー層そのものが機能していない)なので、番号順ではなく先頭に置く。

S7 · 高Claude レビュー層はこのリポジトリで一度も動いていない — それでもジョブは緑

.github/workflows/claude-code-review.yml:43 / claude.yml:44 / Actions secrets

どちらのワークフローも本体ステップが if: env.CLAUDE_TOKEN != '' で守られているが、このリポジトリの Actions シークレットは 0 件で CLAUDE_CODE_OAUTH_TOKEN が無い。結果、ステップは skipped のままジョブは success を返す。@claude メンション経路(claude.yml)も同じシークレットに依存するので同様に不発。PR #10・#11 にレビュー投稿が 1 件も無いのは、レビューが「異常なし」だったからではなく、走っていないからである。

影響は運用の根幹に及ぶ。review-policy.md の「PR 時の最終ゲート(自動 1 回)」も、モード B の「draft で積んで枠が戻ったらまとめてレビュー」も、受け皿が存在しない。緑のチェックが「レビュー済み」と読めてしまう点で、これは本ハーネスが delegate-codex.sh で自ら潰した「exit 0 がタスク成否を表さない」問題と同型だ — 委託経路には成果の実在確認を入れたのに、レビュー経路には同じ検査が無い。

緩和案: (1) シークレットを登録する(本丸)。(2) ガード自体はテンプレート配布先(シークレット未設定の新リポジトリ)のために正しいので、消すのではなく沈黙をやめる — スキップ時に ::notice か $GITHUB_STEP_SUMMARY で「レビューは実行されていない」を PR 上に出す。(3) README のセットアップ手順にシークレット登録の項を立てる(現状どこにも無い)。

証跡gh api repos/<owner>/<repo>/actions/secrets --jq .total_count → 0。claude-code-review.yml の直近 5 実行はすべて本体ステップ skipped。

対応(2026-08-24): 緩和案 (2)(スキップの可視化)を Issue #12 として起票した。::warning + job summary で「レビュー未実行 / この success はレビュー通過を意味しない」を run に残し、ガード自体は外さない(シークレット未設定の配布先を赤くしないため)。claude.yml の @claude 経路と README のシークレット登録手順も同スコープ。(1) のシークレット登録は人間の作業として残る。

S1 · 中Codex はワークツリーの外も読める — denylist の走査範囲外に資格情報がある

delegate-codex.sh 入口検査1 / post_create.sh / ~/.config/gh/hosts.yml

sandbox が制限するのは書き込みで、読み取りにはパス除外が無い(ドキュメント §13 #7 で確定済み)。一方 denylist の走査は find . — つまりリポジトリ内だけで、このコンテナには ~/.config/gh/hosts.yml(gh auth login --with-token が保存した GitHub トークン)と ~/.codex/auth.json(OpenAI OAuth)が常在する。委託プロンプトは読むよう指示しないが、リポジトリ内のファイルに仕込まれた指示(プロンプトインジェクション)経由で読み出されれば、その内容はモデル API 経由で OpenAI 側に渡る。ネットワーク無効はコマンドによる直接送信を塞ぐだけで、この経路は塞がない。

緩和案: (1) 委託を「このテンプレート自身のコード」に限る現運用を続ける限り実害の入口は狭い(外部由来コンテンツを扱うプロジェクトに配られたときが本番のリスク)。(2) delegate-codex.sh の実行時に GH_TOKEN / GITHUB_TOKEN を unset するのは 1 行で入る。(3) ホーム配下の資格情報はスクリプトでは守れない、という限界を denylist のコメントか計画書 §10.2 に明記しておく(「denylist が唯一の層」という現記述は範囲がワークツリーに限られることを言っていない)。

S2 · 中denylist のパターン網羅性 — ドキュメント自身が挙げた .npmrc が入っていない

.claude/codex-denylist.txt

§12.4「機密パターンの確定」は「トークン入り .npmrc は素通りする」と自己指摘していたが、確定版の denylist に .npmrc は無い。ほかに一般的な候補で漏れているもの: .netrc、.git-credentials、*.tfstate、*service-account*.json、.aws/ 配下。このリポジトリ(OSS テンプレート・トラッキング対象は全て送信可の判断済み)では実害は無いが、denylist はテンプレート所有(owned)で全プロジェクトに配られる既定値であり、「唯一の層」を自認する以上、既定は厚くしておく価値がある。深さ制限の撤廃(-maxdepth 廃止 + prune)と *.key 追加は §12.4 の指摘どおり実装済みだった。

S3 · 低〜中seccomp=unconfined のトレードオフ

.devcontainer/devcontainer.json:25

Docker 既定の seccomp プロファイルを外すことで、コンテナ内プロセスが使えるシステムコール面が広がる(カーネル脆弱性経由のコンテナエスケープの攻撃面が増える)。bwrap の user namespace のためという理由は妥当で、--dangerously-bypass-approvals-and-sandbox を採らずに済ませた判断は正しい。開発用コンテナとして許容範囲というドキュメントの評価に同意するが、D4(理由の未文書化)とセットで残すべきリスク。より狭い代替(既定プロファイルに unshare/clone(CLONE_NEWUSER) だけ許可するカスタム seccomp JSON)も存在するので、気になるなら #7 あたりで検討余地。

S4 · 低CODEX_DELEGATE_ACK_SECRETS=1 は包括承認

delegate-codex.sh 入口検査1

機密検出時の承認が「環境変数 1 個」なので、シェルの rc ファイルに export され続けると以後すべての検出が無言で素通しになる(検出メッセージ自体は出るが停止しない)。1 回の委託ごとに前置きで渡す想定なら問題ないが、その想定を usage かメッセージに明記しておくと堅い。

S5 · 情報verify-probe は AGENTS.md 由来の任意コマンド実行

O6 · 低date -u -d は GNU date 専用

codex-run.sh:169

未検収 run の「7 日以上前 = 古い記録」判定に GNU 拡張を使っている。非 GNU 環境(macOS 標準 / BusyBox)では _start_epoch が空になり、古さの表示が静かに消える(委託自体は動く)。検収時の Minor 指摘としてコメント明示に留めた判断が入っており、devcontainer 前提のテンプレートなので現状は妥当。ホスト直実行を想定に入れるなら、record 側に epoch を持たせるのが確実(date 実装への依存が消える)。
