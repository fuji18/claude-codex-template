1. 総評

全体として計画(codex-delegation-plan.md)への忠実度が高く、防衛層の設計品質は同種の自作ハーネスとしてはかなり高い水準。ただし「機械検査の網の外にある経路」が 3 つ残っており、そこが今後の主要リスク。

強み
  • フェイルオープン / フェイルクローズの使い分けが層ごとに理由つきで選択されている(委託 = クローズ、保護ブランチ = オープン)
  • env -i + 許可リストによる環境変数の遮断、出口の内容ハッシュ検査、判定順序(出口検査 > レート上限)など、細部の詰めが実測に裏づけられている
  • 単一ソース原則の徹底(branch-policy.json / check-protected-branch.sh / harness-mode.sh / latest-steering.sh)
  • 実測記録(decisions.jsonl)→ CI 強制(record-hygiene)という改善ループが機械化されている
主要な残存リスク
  • モード C(縮退)は機械検査ゼロの経路(S-2)
  • CI が呼ぶ判定スクリプトが委託禁止領域に入っていない(S-3 / 今回のレビューで最重要)
  • verify-probe のホスト実行に形式検査がない(S-4)

2. セキュリティ懸念

深刻度は「攻撃・事故が成立したときの影響 × 成立しやすさ」で付けた。既に文書化済みの受容リスクは、その旨を明記した。

高S-3: CI の判定実体スクリプトが委託禁止領域に入っていない

FORBIDDEN_PATHS は .github/workflows/ を守っているが、そのワークフローが bash で呼ぶ判定スクリプト本体は守っていない:

  • .claude/scripts/check-record-hygiene.sh — record-hygiene.yml が呼ぶ判定の実体。冒頭に exit 0 を 1 行足すだけで記録漏れ検査が全 PR で無効化される
  • .claude/scripts/check-guard-integrity.sh — ci.yml の harness-integrity と SessionStart の自壊検知の実体。骨抜きにすると「husky 層が消えたことに気づけない」という、このハーネスが最も恐れている状態が静かに成立する
  • .claude/scripts/codex-run.sh — 検収状態(accepted)の書き換えツール。委託先がここに「自分の record を accept する」処理を仕込めると、.harness/codex-runs/ を直接守っている意味が半減する
  • .claude/settings.json / .claude/hooks/session-start.sh — PreToolUse hook の定義そのものと、司令塔コンテキストへの注入元(プロンプトインジェクションの経路になり得る)

「workflows/ を守るなら、workflows が実行するスクリプトも同等に守る」が一貫した線。個別列挙よりも .claude/scripts/ / .claude/hooks/ / .claude/settings.json をディレクトリ単位で FORBIDDEN_PATHS に足す方が漏れがない(ハーネス改修はもともと委託しない方針なので、運用への影響はない)。

該当: .claude/scripts/delegate-codex.sh の FORBIDDEN_PATHS 配列 / AGENTS.md §4 / CLAUDE.md 委託禁止領域の節(3 箇所同時更新)

中S-2: モード C(縮退)は機械検査を一切通らない

縮退モードは人間が codex を直接起動するため、delegate-codex.sh の入口検査(denylist・依存導通)も出口検査(禁止領域ハッシュ)も掛からない。守りは AGENTS.md / SKILL.md の散文と git hook・CI のみ。さらに:

  • writable_roots=[".git"] を渡す設計のため、.git/config の core.hooksPath 書き換えや .git/hooks/ 直書きで husky 層(ベンダー中立ガードレールの本体)を委託先自身が無効化できる
  • 禁止領域(AGENTS.md の verify-probe を含む)への変更もコミットに紛れ込ませられる

復帰時検収(§2.3)が唯一の砦だが、現在の手順は「codex-log.md を読む・/check・code-reviewer」で、ガードレール自体の無事を確かめるステップがない。

提案: .claude/rules/mode/degraded.md の復帰手順に機械化された 1 コマンドを足す — 例: check-guard-integrity.sh を拡張して「core.hooksPath が .husky/_ 系を指すか」「.git/hooks/ に実行可能ファイルが増えていないか」「縮退中コミットの diff が禁止領域に触れていないか(git log --grep Codex-authored の範囲で git diff --stat を禁止領域に当てる)」を検査する。

該当: .claude/rules/mode/degraded.md / .codex/skills/degraded-mode-ticket/SKILL.md / .claude/scripts/check-guard-integrity.sh

中S-4: verify-probe がホスト上で無検査実行される

入口検査3 は AGENTS.md から抽出した文字列をそのまま bash -c でホスト実行する(delegate-codex.sh:255 付近)。AGENTS.md は出口ハッシュ検査で守られているが、検査が効かない改ざん経路が 3 つ残る:

  • モード C 経由(S-2 のとおり機械検査なし)
  • SIGINT / SIGTERM で出口検査に到達せず死んだ委託(スクリプト自身がコメントで認めている空振り条件 — 次回の BEFORE スナップショットが改ざん後を基準に取るため、以後検出不能)
  • 人間の誤マージ・手動編集

提案(いずれも安価): ① プローブの形式を制限する(例: npx --no-install / --version 系のみ許可する正規表現検査。外れたら警告してスキップ)。② 実行前にプローブ内容を必ず stderr に表示する(現状は失敗時のみ)。③ env -i PATH=... bash -c で実行して環境変数への到達を断つ。

該当: .claude/scripts/delegate-codex.sh 入口検査3

中S-1: ホーム配下の資格情報は委託先から読める(文書化済みの受容リスク)

denylist の走査はワークツリー内のみで、~/.config/gh/hosts.yml・~/.claude/・~/.codex/auth.json 等は読み放題。ネットワーク無効で直接送信は塞がれているが、「ワークツリー内のファイルに書き出す → コミット / PR に紛れて公開される」という持ち出し経路は残る。denylist コメント・計画書 §13 とも限界として明記しており判断は妥当。ただし最後の防衛線が「検収レビューと CI の secretlint」であることは認識しておくべき(secretlint は既知パターンしか捕まえない)。

提案: 恒久対応は専用ユーザー / 別コンテナ実行(計画書も言及)。安価な緩和として、impl 委託の出口で「新規・変更ファイルに高エントロピー文字列がないか」を secretlint(ローカルに導入済み)で変更ファイルだけに当てる手はある。

該当: .claude/codex-denylist.txt / delegate-codex.sh 入口検査1

低S-5: その他(受容可能と判断)

  • CODEX_DELEGATE_ACK_SECRETS=1 は司令塔自身が付けて再実行できる — スクリプト内コメントで自認済み。permission prompt 設定に依存する旨も明記されており、扱いは誠実
  • 再入防止(5-5)の TOCTOU — 2 本の impl を同時起動すると両方が検査を通過し得るが、運用上司令塔は 1 人で、実害は作業ツリーの競合止まり
  • pid 再利用による誤検知は「止める側」に倒れる(フェイルセーフ)。回復手順 §12.6 も用意済み
  • record-hygiene.yml は pull_request(target ではない)+ read 権限のみで、fork PR からのシークレット窃取経路なし。PR_BODY の env 渡しでスクリプトインジェクションも回避 — 良い実装
  • claude.yml の author_association 絞り込みは action 側の検証と二重化されており適切

良特筆すべき良い実装

  • 出口検査の優先順位: 禁止領域の差分検査をレート上限・認証失敗の判定より前に置き、「改ざんしてから上限に当たった」セッションが rate-limited として静かに記録される最悪ケースを潰している
  • 自己コピー exec: 実行中の自己書き換えハザードを起動直後のコピーで遮断し、かつマーカー変数を子プロセスから隠している
  • 環境変数の許可リスト(env -i)+ CODEX_DELEGATE_ENV_ALLOW は加算のみで全バイパスを用意していない
  • prepare-commit-msg の MERGE_HEAD 判定: git revert -e が $2=merge を渡してくる実測に基づく、引数だけでは防げない穴の閉じ方
  • .codex/config.toml を防衛線と見なさない宣言と、sandbox を CLI フラグで常時明示する実装の一致

3. コストパフォーマンス

設計目標「実装ループのログを司令塔のコンテキストから排除する」は実測で機能している。decisions.jsonl の記録では、生ログ 66,347 B に対し司令塔へ返ったのは約 60 B(0.09%)。チケット丸ごと委託(#8)でも 92 KB → 50 B。

観点評価根拠
委託の往復コスト 良 実測 2 件とも差し戻し 0 回。design.md を書き切る運用と exit code 契約(0〜5)が効いている
セッション状態の外部化 良 run record + SessionStart 注入で「委託を挟んで /clear」が成立。read-only 委託の自動 accept(Issue #22)で注入の肥大も抑止済み
CI の分割 良 record-hygiene を ci.yml から分離し、ラベル操作のたびに npm ci + テストが再実行される無駄を回避。Claude レビューは main 向け PR の opened / ready のみ + draft 除外で、モード B(draft 積み)と整合
編集ごとの品質チェック 改善余地 下記 C-1
効果測定のループ 未完 下記 C-2

改善余地C-1: lint-on-edit.sh が編集のたびに全体 lint + 全体 tsc を回す

PostToolUse(async)で npm run lint(eslint 全体)と npm run typecheck(tsc 全体)を実行し、それぞれ tail 20 行がコンテキストに載る。現在の規模では軽微だが、コードが育つと CPU とコンテキストの両方で線形に高くなる。またロック方式が「実行中はスキップ」のため、連続編集の最後の編集が検査されない穴がある(先行プロセスは古い状態を lint している)。

提案: eslint は編集ファイル単体に絞る(npx eslint "$f")。tsc は単体不可なので --incremental を検討するか、fork 側の「変更ファイルの型チェック」と役割が重複している分は削る選択肢もある。なお PostToolUse の prettier(全編集)+ lint-staged(コミット時)+ CI の format:check と、フォーマットは 3 重に掛かっている — 各層は安価なので優先度は低いが、認識はしておくとよい。

該当: .claude/scripts/lint-on-edit.sh / .claude/settings.json PostToolUse

未完C-2: econ モードの効果測定が回っていない

delegation-policy.md は「閾値は初期値であり実測で上下させる」と宣言しているが、週枠寿命の比較測定は decisions.jsonl に「未実施」と記録されたまま(mode-b-weekly-budget-baseline-followup)。委託粒度の損益分岐(design.md を書き切るコスト vs 実装ループのコスト)を検証するデータが揃わないと、閾値調整のループが空転する。次に econ モードでチケットを消化するタイミングで /usage の記録を忘れないよう、リマインドの仕掛け(econ モード注入文への 1 行追記など)を検討。

該当: .harness/decisions.jsonl / .claude/rules/mode/econ.md

軽微C-3: スケールで効いてくる箇所(手当済みだが監視対象)

  • forbidden_snapshot() は run record の蓄積で前後 2 回のハッシュコストが線形増 — 50 件警告 + 手動 prune で手当済み。妥当
  • SessionStart の司令塔ルール注入は毎セッション約 12 KB。「キャッシュ対象を小さく保つ」方針自身が監視ポイントと言っており、lead ルールを太らせるときはこの注入コストに跳ねることを意識する
  • record-hygiene は edited / labeled でも発火するが、5 分 timeout の軽量ジョブ + concurrency 打ち切りで問題なし

4. 構成の適正化が可能な個所

推奨O-1: CHANGELOG 検査の対象に .github/workflows/ が入っていない

check-record-hygiene.sh の CHANGELOG_TRIGGERS は .claude/ / .husky/ / .codex/ / AGENTS.md の 4 つだが、template-manifest.json では 5 本のワークフロー(ci.yml / claude.yml / claude-code-review.yml / record-hygiene.yml / template-update-check.yml)も owned = テンプレート同期対象。ワークフローだけを変更した PR は CHANGELOG 未更新でも緑になり、「/sync-template で取り込む側が [manual] 項目に気づけない」というこの検査が塞ごうとした穴がそのまま残る。トリガーに .github/workflows/ を足すだけで閉じる。

該当: .claude/scripts/check-record-hygiene.sh CHANGELOG_TRIGGERS / .claude/template-manifest.json

再検討O-2: rec_field() の二重実装は既に乖離コストが顕在化している

delegate-codex.sh と codex-run.sh に同一実装をコピーし「2 箇所・十数行のため共有ファイルは作らない」と注記されているが、decisions.jsonl の記録によれば sed フォールバックの末尾カンマバグ(Critical: jq 不在環境で再入防止がフェイルオープン)を両方で直した実績が既にある。判定ロジックを 1 箇所に集約する方針(check-protected-branch.sh / harness-mode.sh / latest-steering.sh)とも不整合。.claude/scripts/lib-record.sh のような共有ファイルに切り出して source する形が、このリポジトリ自身の設計原則に合う。切り出す場合はそのファイルも委託禁止領域に足すこと(S-3 のディレクトリ単位保護を採るなら自動的に含まれる)。

該当: .claude/scripts/delegate-codex.sh / .claude/scripts/codex-run.sh

提案O-3: SIGINT 後の「改ざん基準化」を安価に検出できる

S-4 で触れた空振り条件(割り込みで出口検査に到達しなかった委託の後、次回の BEFORE スナップショットが改ざん後を基準に取る)への安価な緩和策: 禁止領域の汎用項目はほぼすべて git 追跡ファイルなので、委託の起動時に「running のまま残った record がある場合、禁止領域を git diff HEAD -- <paths> で確認し、dirty なら警告を強める(または止める)」を機械化できる。現在は文言での注意喚起(§12.6 への誘導)のみで、人間が読み飛ばすと検出機会が失われる。

該当: .claude/scripts/delegate-codex.sh 入口検査 5-5 の警告分岐

現状維持が適正O-4: あえて変えない方がよい箇所

  • delegate-codex.sh の 1,043 行単一ファイル: 分割すると「唯一の入口」原則と自己コピー保護(コピーは 1 ファイルしか運ばない)が壊れる。内部は検査番号つきの区画に整理されており可読性は保たれている。現状維持を推奨
  • 3 モードの手動切替(.harness/mode は人間が書く): Claude が自分で降格・復帰しない設計は、モード詐称の防止と責任分界の両面で正しい
  • 保護ブランチ検査のフェイルオープン: コミット不能に倒さない判断と、その代わりに「黙って素通ししない」(全層で stderr 警告)+ CI 最終検証という補償の組み合わせは一貫している
  • run record の自動削除をしない(prune は人間の明示操作のみ): 未検収 record = 検収キューという意味づけが明確で、警告閾値 50 件も妥当

5. 対応の優先順位(まとめ)

#項目種別工数目安効果
1 S-3: FORBIDDEN_PATHS に .claude/scripts/ / .claude/hooks/ / .claude/settings.json を追加(AGENTS.md §4・CLAUDE.md と 3 箇所同時) セキュリティ小 CI 判定の無効化・検収偽装・hook 定義改ざんの経路を一括で閉じる
