01

何を解こうとしているか

トークンを最も食うのは「実装 → テスト → エラーを読む → 修正」のループ。実測では消費の 72% が 150k 超のコンテキストで発生しており、その主因がこのループのログ蓄積にある。この区間だけ外に出せれば、Claude の枠は大きく空く。

同じ問題に Cursor 併用案が取り組んで保留になった。理由は「Composer をプログラム起動できず、受け渡しに人間の中継が必要」。Codex CLI は codex exec でヘッドレス起動できるため、この欠点が無い — これが Codex を採る決定的な理由。

前提の限界

認証は ChatGPT Plus サブスク。Codex 側にもレート制限があるため、両方枯れれば止まる。Codex 単独稼働(モード C)は恒久解ではなく数日しのぎであり、枠の実効寿命を伸ばす主力はモード B に置く。

3 モードを貫く不変条件

実装者(Codex / Sonnet fork)は会話履歴を持たない。根拠は design.md と tasklist.md だけで、報告フォーマット(完了 / 判断待ち / 失敗)も共通。だからチケットの途中でも実装者を差し替えられる — Codex が 2/3 タスク目で上限に殺されても、Sonnet fork が 3 番目から続けられる。これは「あれば便利」ではなく満たすべき要件として扱う。

3 モード運用

モードは推測させず .harness/mode を単一ソースとし、切替は人間が宣言する(Claude が自動で降格しない)。SessionStart hook が現在のモードを注入する。

実行者・コマンドの一覧は §02 のランブック にある。ここでは各モードの設計判断の根拠だけを扱う。

モード C の出口設計

Codex はブランチ上にコミットを積むだけで PR を作らない。引き継ぎの単一ソースは .steering/[dir]/codex-log.md(変更・コミット範囲・自己チェック結果・設計判断・申し送り)。Claude の枠が回復したら、差分全文ではなくこのログを起点に検収 → PR へ合流する。

モード C を始める前の 3 条件

司令塔がいないので Codex 自身が守る(AGENTS.md に書く)。

#条件理由
1保護ブランチにいたら feature ブランチを切る§06 で追加した .husky/pre-commit が保護ブランチへのコミットを弾く。司令塔がいないため、Codex 自身が切らないと詰む
2コミットに Codex-authored: true トレーラーを付ける上限で殺されると codex-log.md を書けない。各コミットが自分で名乗るので識別手段が中断に耐える。件名の接頭辞にすると Conventional Commits を壊すためトレーラーにする
3Issue 操作(ラベル・コメント)はしないsandbox はネットワーク無効で gh も無い。Claude 復帰時にまとめて行う
設計判断は延期されるが放棄されない

モード C は「設計判断は移管しない」原則への一時的な例外。Codex は下した判断を codex-log.md の「設計判断」欄に列挙し、Claude 復帰時に司令塔が design.md へ反映する。反映箇所は code-reviewer に重点レビュー範囲として渡す。codex-log.md を正のままにしない — 永続ドキュメントと steering の役割分担が崩れるため。

モード C には自動ゲートが無い

ci.yml のトリガは push: [main, develop] と pull_request のみ。モード C は「feature ブランチにコミットを積むが PR は作らない」ので、CI が起動する契機が無い。頼れるのは Codex のセルフチェックだけになる。

緩和案(提案・必須にしない): モード C を始める前に人間が draft PR を先に開くと、以後の push ごとに CI が回る。既存の pull_request トリガに乗るので設定変更が要らない。採らない場合は「モード C の成果物は Claude 復帰時の検収を通るまで一切検証されていない」前提で扱う。

push する主体は人間しかいない。 Codex は sandbox のネットワークが無効で、権限表でも push を禁止している。つまり Codex が積んだコミットは放っておけばローカルに留まり、CI に永久に到達しない。draft PR を開くだけでは足りず、区切りごとに人間が push するところまでが緩和策の中身になる。

モード B は PR を積むがマージしない

モード B は code-reviewer を飛ばす。CI は lint・型・テストしか見ず、スペック整合とアーキテクチャ整合は未検査のまま残る。これを何チケットも続けると、レビューを経ていないコードが main に入る。

モード B 中の PR は draft で積み、枠が戻ってからまとめてレビューしてマージする。「進みは止めないが、未検証のものを本流に入れない」という切り分け。急ぐ場合の例外はユーザーが明示的に判断する。

draft は作法ではなく節約の実体

claude-code-review.yml は if: github.event.pull_request.draft == false を持つため、draft のままなら GitHub Actions の Claude レビューが走らない。非 draft で開くと、モード B が温存しようとしているまさにその枠を PR ごとに消費する。一方 ci.yml の pull_request トリガは draft でも発火するので、機械的検証は受けたままレビューだけを止められる。

枠が戻ったとき ready_for_review に切り替えると types: [opened, ready_for_review] によりレビューが自動起動する。「溜まった PR をまとめてレビュー」はこの機構にそのまま乗る運用で、手動で呼び直す必要はない。

モード B の手順で順序を逆にしない

ci.yml のトリガは push: [main, develop] と pull_request だけで、作業ブランチへの push だけでは CI は走らない。「CI が緑なら PR を作る」は因果が逆で、PR を作るまで CI は一度も動かない。正しい順序は commit → push → draft PR → ここで初めて CI。モード B は検収を CI に丸投げする設計なので、取り違えると検収が丸ごと空振りする。

初版は OpenAI 公式プラグイン(codex-plugin-cc)経由の委託を前提にしていたが、上限対策としては構造的にゼロ点だった — スラッシュコマンドは Claude が生きているときしか呼べない。そこで委託の正の経路を、シェルから叩ける 1 本のスクリプトに移す。

入口検査: design.md の完成マーカー

Claude が計画途中で上限に当たるケースへの備え。書きかけの design.md を実装者が「完成品」として読むと、不完全な設計のまま実装が進み、Codex 側の枠まで無駄に消費する。

<!-- status: draft -->   … 執筆中。実装に渡してはいけない
<!-- status: ready -->   … 実装可能。設計判断は書き切られている

delegate-codex.sh と implement-ticket は ready 以外なら exit 5 で拒否する(2 = タスク起因の失敗 とは別コードにするのが要点 — 回復手段が「司令塔が設計を書き切る」と「原因分析」で全く違う)。ただし強制の強さは非対称 — Codex 側はスクリプトの機械検査、fork 側は SKILL.md の散文であり hook ではない。この非対称は実装漏れではなく設計判断として扱う(段階3 で実測し、fork が draft を踏むようなら機械化を再検討)。マーカーが無いものは検査対象外として通す(「無ければ draft とみなす」に倒さない理由は下の callout)。tasklist.md の <!-- main-edit-ok --> を hook が読む既存の作法と同じ — 散文の規約ではなく機械が読める印にすることで、Claude が突然止まっても状態がファイルに残る。

ただしモード C ではこのゲートは無効化される。 司令塔がいないので Codex が design.md を書いて自分で ready を立てる(自己認証)。塞ぐ手段が無いため、Claude 復帰時の検収で design.md 自体をレビュー対象に含めることで回収する — 入口で検査できない分を出口で見る。

規約の置き場所を間違えない

この計画書がある docs/template-dev/ は、CLAUDE.md が明示的に「読み込み対象外」と宣言しているディレクトリ。ここにしか書かないと司令塔はマーカーの存在を知らないまま毎回拒否される。<!-- main-edit-ok --> は hook のエラーメッセージが自己教育してくれるが、こちらにはその経路が無い。

そこで steering テンプレートの design.md に draft を既定で埋め(作れば必ず印が付く)、steering スキルのモード1 に ready への変更手順を書いた — ロードされる場所に規約を置く。

「無ければ draft とみなす」は既存を全部壊す

当初は「マーカーが無ければ draft とみなす(安全側)」としていた。しかしこのリポジトリの .steering/ 3 件を含め、導入以前の design.md には印が無い。安全側に倒したつもりで「委譲経路が全プロジェクトで沈黙して止まる」ことになる。

正しくは 印があるものだけを検査する。テンプレートが draft を既定で埋めるようになった以降の作業は必ず印を持つので、これで十分。この規則は Codex と Sonnet fork で共通にする — 片方だけがゲートを持つと「同じ計画を渡しても実装者によって結果が違う」状態になり、交換可能性が崩れる。

入口検査: 委託前の実行可能性

ネットワーク無効の sandbox では、依存が未インストールだと Codex は何一つ完遂できない。品質チェックが動かないだけでなく、.husky/pre-commit の npx lint-staged が取得を試みて失敗するため、コミット自体が原因の分かりにくいエラーで死ぬ。「新規依存を追加しない」だけでは足りず、「そもそも依存が入っている」が前提条件になる。

ただし delegate-codex.sh はマニフェスト上テンプレート所有(owned)で、全プロジェクトに配られる。node_modules の有無を決め打ちで見ると Python / Go のプロジェクトで無意味に落ちるため、検査はスタック非依存の形にする — AGENTS.md に書かれた検証コマンドを 1 つ空実行できるかだけ見て、駄目なら委託せず exit 3 で戻す。枠を溶かす前に止めるのが目的。コミットを許すモード C では git config core.hooksPath の設定済みも併せて見る(未設定なら husky が丸ごと無効 = 防衛線が存在しない状態でコミットさせることになる)。

司令塔はこの値だけを見て分岐する(推測しない)。3 と 4 を混ぜないのが要点 — 前者は環境の欠落(恒久)、後者は枠切れ(一時)で回復手段が違う。

上限の検出方法(2026-08-20 に確定)

Codex CLI は上限に固有の終了コードを返さない。代わりに codex exec --json の改行区切りイベントに rate_limit_reached / usage_limit_reached / credits_depleted という構造化された識別子が流れる。これを一次判定にした(文言そのものより変化しにくい)。

二次の保険として文言パターン(rate limit / usage limit / quota / 429)も残す。識別子が改名されたときに上限を「タスク起因の失敗」と誤分類すると、司令塔が原因分析に入ってさらに枠を溶かすため、誤検知より見逃しの方が高くつくという非対称に合わせている。生のエラー 3 行は必ず run record に保存し、検出をすり抜けても人間が判断できる状態にしておく。

送信は事後に回収できない唯一のリスク

.gitignore は守りにならない。 ignore されたファイルもディスク上にあれば workspace-write sandbox は読める(.env が典型)。委託はそれを OpenAI 側へ送りうる。

対策は 2 段。(1) delegate-codex.sh が委託前に .env / *.pem / id_rsa* / credentials* の存在を検査して確認を求める(存在しないのが正常なので普段は無言)。(2) kickoff のガバナンス判断を「使うか / 使わないか」ではなく「どのパスを送ってよいか」まで決めるものに格上げし、その一覧をスクリプトへ渡す。

他のリスクは検収で回収できるが、これだけは送信した時点で終わり。2026-08-20 に確定: Codex にパス単位の読み取り除外は存在しない(sandbox は書き込みの制限であり、読み取りの deny-list は無い)。したがって (1) が唯一の層であり、段階2 で実装済み(CODEX_DELEGATE_ACK_SECRETS=1 が無ければ止まる。.env.example 等は除外)。

このリポジトリの判断(2026-08-23): テンプレート本体は OSS で顧客コード・個人情報・本番シークレットを含まないため、Codex 委託を使う。送信してよいのはトラッキング対象ファイルすべて。送信禁止の一覧は .claude/codex-denylist.txt を単一ソースとし、delegate-codex.sh の入口検査1 がそれを読む(ファイルが無い / 有効パターンが 0 件なら委託を止める = フェイルクローズ)。.harness/ 配下(過去の委託ログ)は検出対象ではなく走査除外で扱う。

Codex へのモード伝達は 2 経路要る

モード別の許可(コミットの可否など)は、Codex が自分のモードを知っている前提で書かれている。AGENTS.md は静的ファイルなので、それだけでは判別できない。

当初は「delegate-codex.sh のプロンプト注入が唯一の伝達路」としていたが、これはモード C を成立させない。 モード C は Codex を直接起動する = delegate-codex.sh を通らないため注入が届かず、既定のモード A に落ちてコミットを拒否する。守りたい当の縮退モードが、伝達手段の依存によって機能しなくなる構造だった。

修正: .harness/mode を Codex も読む単一ソースにし、読む順序を プロンプトの値 > .harness/mode > モード A に固定した。AGENTS.md の起動時手順にファイル読み取りを必ず含める。

委託中に並行してよい作業

Codex とは同一ワーキングツリー・同一ブランチを共有する。委託中の司令塔は委託ブランチのプロダクトコードに触れない作業のみ並行する(docs 執筆・調査・レビューは可)。

委託中に新しい steering ディレクトリを作らない

latest-steering.sh の選定は「日付プレフィックス降順 → 同日は tasklist.md の mtime 降順」。委託中に同日の新ディレクトリを作ると、Codex が委託先の tasklist を更新するたびに「最新」が入れ替わる:

新ディレクトリ B の tasklist を書く    → B が latest
Codex が A の tasklist を [x] に更新   → A が latest   ← 振動
司令塔が B の tasklist を追記          → B が latest

check-implementation-phase.sh のブロック判定と SessionStart の表示が委託中ずっと入れ替わる。Sonnet fork は同期実行で窓が一瞬だが、バックグラウンド委託は窓が委託全体に広がる — Codex 併用が潜在的な競合を顕在化させる。

委託が途中で止まったとき

レート上限で殺された Codex はサマリーも codex-log.md も書けない。run record は running のまま、pid だけ死んだ状態で残る。したがって回復時に読むのはサマリーではなく tasklist.md と git diff。

なぜ乗り換えられるのか

Codex と Sonnet fork は同じ契約(design.md + tasklist.md を唯一の根拠とし、1 タスク完了ごとに - [x] へ更新し、同じ報告フォーマットを返す)で動く。どちらも会話履歴を持たないため、チケットの途中でも乗り換えコストがゼロ。これは副産物ではなく満たすべき設計要件として扱う — tasklist.md の逐次更新が「行儀」ではなく要件なのはこのため。

$ gh api repos/{owner}/{repo}/branches/main/protection
403 Upgrade to GitHub Pro or make this repository public

帰結は 3 つ。Codex にコミット権を渡す(モード C)前に決着させること。

  • --no-verify と main への直接 push に backstop が無い
  • CI を required check にできない → branch-policy / harness-integrity ジョブは赤くなるだけでマージを止められない
  • 「権限境界は GitHub 側で張る」という前提が、このリポジトリでは空手形になっている

選択肢は ①リポジトリを public にする(public なら Free でもルールセットが使える)/ ②Pro・Team に上げる / ③ローカル hook が唯一の層だと認めて上の表を書き換える。③はモード C の前提としては最も弱い。

フェイルオープンのつもりが fail-closed だった(2026-08-19 修正)

husky は .husky/pre-commit を sh -e で実行する(.husky/_/h)。set -e 下では非ゼロを返したコマンドの直後にシェルごと終了するため、当初の

bash "$GUARD"
case $? in 1) exit 1 ;; esac  ← 到達しない

は case に制御が渡らず、内部エラー(bash 不在 = 127・構文エラー = 2・権限落ち = 126)まで全コミットをブロックしていた。設計上の「内部エラーはフェイルオープン」の真逆であり、メッセージは husky - pre-commit script failed (code 127) だけ、回復手段は --no-verify のみ。この節が防ごうとしている「静かな自壊」の最も派手な裏返しになっていた。

修正は終了コードを && / || のリスト内で受ける形(リスト内は set -e が発火しない)。npx lint-staged も lint-staged の直呼びに変えた — husky が node_modules/.bin を PATH に足しているのでローカル解決でき、ネットワーク無効の sandbox(Codex 委託時)で npx がレジストリ取得を試みて死ぬ経路が消える。

ポリシーの空洞化検知(2026-08-19 追加)

保護ブランチ検査の 3 層(PreToolUse hook / .husky/pre-commit / CI の branch-policy)は、いずれも protectedBranches という同じ配列を読む。ここが空になると 3 層が同時に、かつ「正常に動作したうえで素通し」という形で無効化される。呼び出しの有無だけを見る自壊検知では最も静かに層が消えるのがこの経路なので、SessionStart と CI の両方に「protectedBranches が空でないこと」を追加した。

いずれもローカルのガードレールをセキュリティ境界として扱わないという前提で許容している。権限境界は GitHub 側のブランチ保護で張る。

レビューで発見・修正した自作の欠陥

呼び出し側がフェイルオープンになっていなかった。 当初 if ! bash ... と書いており、違反(exit 1)以外もブロックしていた。共有スクリプトが同期漏れ・権限落ちで無いだけで全コミットが止まる状態で、共有スクリプト側は 4 条件でフェイルオープンする設計なのに呼び出し側が fail-closed という不整合だった。case $? in 1) ... esac に修正し、検証を 15 → 20 ケースに拡張。

教訓: 判定を 1 箇所に集約したことで、逆に「呼び出し側が終了コード契約を誤読する」新しい失敗モードが生まれていた。フェイルオープン設計は共有スクリプト側だけでは完結しない。

守っていたのは「コミットを作る操作」の一部だけだった(2026-08-19)

保護ブランチ上での各 git 操作を実測したところ、pre-commit フックが発火するのは git commit と git commit --amend だけで、git revert と git cherry-pick では発火しないことが分かった。Claude 側の check-branch-policy.sh も git commit にしかマッチせず、CI は PR の base とブランチ名しか見ない。つまりこの 2 操作は 4 層すべてを素通りしていた。

「main の悪いコミットを revert して」はエージェントに最も自然に発生する指示であり、モード C では Codex がコミット権を持つ。層の名前(「保護ブランチへの直接コミットを止める」)と実際の守備範囲がずれていた。

.husky/prepare-commit-msg を追加して塞いだ。.git/MERGE_HEAD の有無で出所が分かるため、取り込み(= git merge / git pull)だけは通せる — ここを塞ぐと保護ブランチで pull すらできなくなる。第 2 引数では判別できない点に注意(git revert -e / git cherry-pick -e も merge を渡してくる)。副次効果として git commit --no-verify も塞がった: --no-verify が無効化するのは pre-commit と commit-msg だけで、このフックは迂回できない。

教訓: 「どの操作を守るか」をフック名ではなく実測で確かめる。pre-commit という名前は「コミット前」と読めるが、実際に守るのは git commit というコマンドであって、コミットという結果ではない。

その修正自体が、実行環境によって無効化されていた(2026-08-19)

上の修正で入れた case $? in 1) exit 1 ;; esac は、.husky/pre-commit では機能しなかった。husky がこのファイルを sh -e で実行するため、bash "$GUARD" が非ゼロを返した時点でシェルごと終了し、case に制御が渡らないため。PreToolUse hook 側(set -e 無し)では同じコードが正しく動いていたぶん、発見が遅れた。

教訓: 「判定の実体を 1 箇所に集約する」は正しいが、呼び出し側のシェルオプションまでは共有されない。同じ 3 行を 2 箇所に写しても、set -e の有無で意味が反転する。共有スクリプトの終了コード契約を書くときは、呼び出し側がどのシェルでどう起動されるかまでを契約に含める必要がある。

発見2: exit 0 は「タスクが成功した」を意味しない(終了コード契約の穴)

上の委託は何一つ達成していないのに exit 0(= 完了)を返した。run record も "status": "completed" / "error": null で、機械的には成功と区別がつかない。

  • explore / review では成果物が散文なので機械判定が難しい。サマリーを必ず人間か司令塔に見せる現在の作りを維持し、「exit 0 = 内容も妥当」と読み替えないことを運用側の前提として明記する
