1セキュリティ懸念

脅威モデル: 委託先(Codex)がプロンプトインジェクション等で悪性化した場合、および機密がワークツリー経由で送信される経路。

高サンドボックス脱出の連鎖: 委託先が「ホストで実行されるファイル」を書けるのに、委託後の機械検査がない

impl 委託(workspace-write)中の Codex は AGENTS.md・.husky/*・.claude/scripts/* を書き換えられる。このうち AGENTS.md の <!-- verify-probe: ... --> は、次回の委託時に delegate-codex.sh がホスト上で bash -c によりサンドボックス外で実行する(入口検査2・3)。つまり「サンドボックス内で 1 行書く → 次回起動時にサンドボックス外で任意コマンド実行」という脱出経路が成立する。.husky/* や .claude/scripts/* も同様にホスト・Claude セッションで実行される。

現状の防御は AGENTS.md §4 の散文(「触れずに停止せよ」)と検収レビューのみ。指示に従わない・従えない委託先に対する機械的な層が無い。

対策: delegate-codex.sh の impl 完了後に git diff --name-only(+ untracked)を禁止パスリストと突き合わせ、該当があれば status=failed で exit 2 にする後置検査を追加する。検査対象は現行の禁止領域 3 項目に加えて AGENTS.md と .github/workflows/(下記参照)。入口検査群と対で「出口検査」として置くと設計の対称性も良い。

高denylist はワークツリーしか見ておらず、環境変数とホームディレクトリの資格情報が素通しになる

計画 §13 #7 で「Codex sandbox に読み取りの除外機能は無い」と自ら確定させている通り、read-only / workspace-write のどちらでも読み取りはワークツリーの外に及ぶ。codex exec は親プロセスの環境変数をそのまま継承し、devcontainer のホームには ~/.config/gh/hosts.yml(gh CLI の OAuth トークン)や ~/.claude/ の資格情報が置かれている。入口検査1(denylist)は find . でリポジトリ内しか走査しないため、これらは検査対象にすらならない。

対策: (1) codex exec の起動を env -i PATH=... HOME=... 相当の許可リスト方式に変える(Codex CLI が必要とする変数だけ通す)。(2) ホーム配下の資格情報は sandbox 設定では守れないことを denylist ファイルの冒頭コメントと計画 §10.2 に明記し、「唯一の層」という記述を「ワークツリー内の唯一の層」に修正する。

中denylist のパターン網羅が Node スタックの実態に対して不足している

現行は .env*・鍵類・credentials*・settings.local.json のみ。テンプレート既定が npm スタックであるにもかかわらず、認証トークンの定番置き場である .npmrc(_authToken)が入っていない。ほかに .netrc / .git-credentials / *.tfstate / *-service-account*.json / .pypirc / *.sqlite・dump*.sql(実データ入り DB ダンプ)も一般的な漏洩源。

対策: 上記を .claude/codex-denylist.txt に追加する。フェイルクローズ機構自体は正しく動いているので、パターン追加だけで済む。

中禁止領域リストに AGENTS.md と .github/workflows/ が入っていない

AGENTS.md は委託先自身の「憲法」であり、かつ verify-probe というホスト実行経路を持つ(指摘 1)。.github/workflows/ は、非 fork PR では CLAUDE_CODE_OAUTH_TOKEN にアクセスできるワークフローの定義そのものであり、Codex 由来のコミットにワークフロー改変が混ざると、CI 実行時にシークレットを持ち出す経路になる。どちらも「委託先が自分を縛る層を書き換えてはならない」という codex-denylist.txt と同じ論理が成立するのに、リスト外に置かれている。

対策: CLAUDE.md「委託禁止領域」と AGENTS.md §4 の両方に AGENTS.md(検査マーカー行を含む)と .github/workflows/ を追記し、指摘 1 の出口検査の対象に含める。

低CODEX_DELEGATE_ACK_SECRETS=1 は全件一括承認で、司令塔が自力で付けて再実行できる

機密検出時の承認は環境変数 1 個の全件一括承認であり、ファイル単位の判断ができない。また「入口の人間確認が唯一の層」とコメントされているが、実際には Claude(司令塔)が Bash から CODEX_DELEGATE_ACK_SECRETS=1 を付けて再実行できてしまい、人間確認になる保証は permission prompt 頼みになる。

対策: 少なくともコメントの「人間確認」を「承認付き再実行」に改める。強化するなら、検出ファイル一覧のハッシュを承認値に要求する(ACK=当該一覧のハッシュ)と「前回と違う機密が増えたのに古い承認で通る」事故も防げる。

低run record と .harness/mode は委託先が書き換え可能

.harness/ は workspace-write の書き込み範囲内。Codex が codex-runs/*.json の accepted を立てる・.harness/mode を degraded に書き換える、という改竄は機械的には可能。モードは委託開始時に読み込み済みのため当該セッション内の影響は無いが、次回セッションの SessionStart 注入と検収判断はこれらを信頼する。

対策: 優先度は低い(検収レビューが前提のため)。指摘 1 の出口検査に .harness/mode の変更検知を含めれば実質カバーできる。

2コストパフォーマンス

実測に基づく最適化が既に効いている領域。指摘は 1 件のみで、残りは維持すべき良い点。

中explore / review の run record が永久に「未検収」のまま、毎セッション注入され続ける

write_record は全モードで accepted: false のレコードを作るが、「検収して accept する」という概念は impl にしか無い。explore / review の完了レコードは誰も accept しないため、codex-run.sh pending が SessionStart のたびに注入し続け、7 日後に「古い記録」へ降格しても消えはしない。読み取り専用の委託を重ねるほど、毎セッションの固定コンテキストコストが単調増加する — コンテキストを削るための委託が、コンテキストを太らせる形。

対策: read-only モード(explore / review)は completed 時に accepted: true で書く(サマリーは標準出力で司令塔に渡り、成果物の検収対象が存在しないため)。または cmd_pending で mode != impl を除外する。前者の方が「record = 検収キュー」という意味論が保てる。

良維持すべき最適化(実測で裏付けあり)
  • サマリー返し: 生ログ 66〜92KB に対し司令塔へ返るのは約 50〜60B(実測 0.09%)。参照渡し原則と合わせ、委託の主目的であるコンテキスト削減が数字で成立している
  • 事前フェイル: codex login status・依存プローブ・draft 検査を実行前に落とすため、失敗する委託が枠を消費しない
  • レビューの発火制御: main 向け PR の opened / ready_for_review のみ + draft 除外 + concurrency キャンセル。モード B の「draft で積む」と正しく噛み合っている
  • lead ルールの SessionStart 注入: サブエージェント spawn ごとの課金を避ける設計が cost-model.md の実測と紐付いている

補足: lead ルール注入は毎セッション約 10KB 強。現状は妥当だが、今後 lead/ が肥大するなら「常時注入(モデル運用・ブランチ)」と「必要時ロード(レビュー方針等)」の二層化が次の削減余地になる。

3構成の適正化

正しさに直結する軽微な穴と、構造として妥当な判断の確認。

低impl の target が .steering/ 配下に限定されていない

入口検査 5-1 は「design.md と tasklist.md を持つディレクトリ」しか見ないため、.steering/ 外の任意ディレクトリ(例えば細工されたフィクスチャ)でも通る。run record の steering フィールドや SessionStart の現在地判定は .steering/ 前提なので、通ってしまうと状態管理が静かにずれる。

対策: 5-1 に case "$STEERING" in .steering/*) ;; *) exit "$EX_FAIL" ;; esac を 1 行足す。

低再入防止が「同一ステアリング」しか見ておらず、運用ルール「並行 1 本」を機械化していない

delegation-policy.md は「並行数は 1 本まで(同一ワーキングツリーを共有するため)」と定めるが、入口検査 5-5 は同じ steering への二重起動しか止めない。別 steering への並行 impl 委託は素通りし、ツリー競合(片方の lint が他方の編集を巻き込む等)は防がれない。

対策: 5-5 のループで「steering を問わず mode=impl かつ status=running(プロセス実在)」を検出したら止める。判定部品は既に揃っており、条件を 1 つ外すだけで済む。

低rec_field / write_field の 2 箇所コピーは現状妥当だが、増殖の閾値を決めておく

delegate-codex.sh と codex-run.sh の重複は「2 箇所・十数行のため共有ファイルは作らない」と明文化されており、現時点では正しい判断。ただし既に一度、片方だけ修正されて挙動が食い違う事故(sed フォールバックの末尾カンマ)を検収で踏んでいる。3 箇所目が生まれた時点、またはもう一度片側だけの修正が起きた時点で .claude/scripts/lib/ への共通化に切り替えるのが安全。

良構造として妥当と確認した判断
  • フェイルオープン/クローズの非対称: 保護ブランチ検査(止めるとコミット不能)はオープン、委託入口検査(止めても fork で継続可)はクローズ。各所のコメントで根拠が言語化されており一貫している
  • 自己コピー exec(#15): 逐次読み込みハザードの対策として正攻法。exec 失敗経路・シグナル時の後始末・環境変数の子プロセス漏洩まで詰めてある
  • sandbox をフラグで明示: untrusted プロジェクトで .codex/config.toml が読まれない仕様を踏まえ、設定ファイルを防衛線にしない判断が正しい
  • ガードレールの多層 + 自壊検知: protectedBranches 空洞化・フック呼び出しのコメントアウト・実行権限落ちまで、SessionStart / CI の両系統で検知される。MERGE_HEAD による revert -e / cherry-pick -e のすり抜け対策も実測ベース
  • claude.yml の起動条件: @claude メンション + author_association(OWNER/MEMBER/COLLABORATOR)の二重ゲートで、公開リポジトリでの枠消費とインジェクションを絞れている
