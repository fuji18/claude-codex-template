総評

計画文書と実装の対応は非常に良く、脅威モデル(「サンドボックスの中で書かれたものが、後でサンドボックスの外で実行される」)の把握も的確です。 入口検査 5 系統・出口検査 2 系統・ナンス付き標識ブロック・自己コピー exec・許可リスト方式のプローブ形式検査は、 どれも一般的なテンプレートの水準を大きく超えています。#56〜#72 の一連の修正で、 「注入される実体」「実行される実体」「全層が読む判定データ」という 3 系統の整理に到達しているのも妥当です。

そのうえで、今回の指摘の中心は 1 点です ― 禁止領域の列挙が「git 追跡下のファイル」を暗黙の前提にしており、 .gitignore 済みだがホストが実行する経路が丸ごと抜けています。 最も重いのが .husky/_/(= core.hooksPath の実体)で、 ここは出口検査・git diff・check-guard-integrity.sh・CI のすべてが同時に素通しします。

1. セキュリティ

HighS1. .husky/_/ が禁止領域から抜けている(ガードレールの無音化 + ホストコード実行)
.claude/scripts/delegate-codex.sh:271-272(FORBIDDEN_PATHS)
事実

このリポジトリの core.hooksPath は .husky/_ です。git が実際に起動するのは .husky/_/pre-commit であり、それが .husky/_/h を source し、h が最後に sh -e ".husky/pre-commit" を呼びます。つまり守られている .husky/pre-commit は チェーンの末端で、実際の入口は .husky/_/ の側です。 

$ git config --get core.hooksPath
.husky/_
$ cat .husky/_/pre-commit
#!/usr/bin/env sh
. "$(dirname "$0")/h"
$ cat .husky/_/.gitignore
*                          # ← .husky/_/ 配下は丸ごと git 追跡外
なぜ全層が素通しするか
層結果理由
出口検査 forbidden_snapshot()素通しFORBIDDEN_PATHS は .husky/pre-commit と .husky/prepare-commit-msg の 2 ファイルのみ。.husky/_/* は列挙されない
git diff / git status / tree_snapshot()素通し.husky/_/.gitignore = * で追跡外。--untracked-files=all でも出ない
check-guard-integrity.sh D1素通しcore.hooksPath は .husky/_ のまま = .husky/* の case に一致して健全判定
同 検査 3・4素通し.husky/pre-commit は存在し、check-protected-branch.sh も呼んでいる(呼ばれなくなっただけ)
同 D2素通し見るのは物理 .git/hooks/ のみ
CI harness-integrity素通しfresh checkout に .husky/_ は存在せず、npm ci が再生成する。ローカルの改変は CI に一切現れない
成立する 2 つの攻撃
  1. ガードレールの無音化 — impl 委託中に .husky/_/pre-commit を exit 0 の 2 行に置き換える。以後、保護ブランチへの直接コミットを止めるベンダー非依存の層(Codex・手動 git に効く唯一の層)が消えるが、check-guard-integrity.sh は健全と報告し続ける。
  2. ホストコード実行 — .husky/_/h は人間や Claude が git commit を叩くたびにホスト上・ネットワーク有効・サンドボックス外で実行される。1 行足せば恒久的な実行経路になる。package.json のライフサイクル警告(§9)が塞ごうとしているのと同じ性質の穴が、警告すら無い状態で残っている。
根本原因

CLAUDE.md は「個別列挙はスクリプトが増えるたびに漏れるのでディレクトリ単位で禁止する」と .claude/scripts/ について明言しています。 その原則が .husky/ にだけ適用されていません。 さらに CLAUDE.md の「3 系統」の説明では実体を .husky/* と書いており、 散文(ディレクトリ)と配列(2 ファイル)がすでに食い違っています。 check-forbidden-paths-doc.sh は「配列 → CLAUDE.md」の片方向しか見ないため、この乖離は検出できません(D1 参照)。

修正案
# delegate-codex.sh の FORBIDDEN_PATHS
-  ".husky/pre-commit"
-  ".husky/prepare-commit-msg"
+  ".husky/"

forbidden_files() の */) 分岐は find .husky -type f なので gitignore を無視して列挙し、 git hash-object は追跡外ファイルにも効きます。1 行の変更で S1 は閉じます(追加で約 20 ファイルのハッシュ。#65 のバッチ化後は誤差)。 併せて check-guard-integrity.sh に「.husky/_/pre-commit が h を source しているか」の検査を足すと、 委託経路を通らないモード C / 手動改変も拾えます。

HighS2. 検証プローブ P2 形式のホスト実行に、実効する代償措置が無い
.claude/scripts/delegate-codex.sh:487-493(コメント)/ :657(env -i ... bash -c "$PROBE")/ AGENTS.md:2
事実

入口検査3 は許可形式の npx --no-install <pkg> --version をホスト上で実行します。 現在のマーカーは npx --no-install eslint --version = node_modules/.bin/eslint を解決して実行します。 node_modules/ はワークツリー内なので workspace-write の委託先が書き換えられ、 その改変は「次回の委託の入口検査」でホスト実行されます(サンドボックス内で書く → 次回起動でサンドボックス外実行)。

コメントに書かれた代償措置が実在しない

スクリプトのコメントはこう書いています:

「ワークツリーの完全性は出口ハッシュ検査・check-guard-integrity.sh degraded が
  受け持つ別の層。」

どちらも node_modules/ を見ていません。 出口ハッシュ検査は FORBIDDEN_PATHS に列挙されたパスだけを走査し、node_modules/ は入っていません(入れれば数万ファイルのハッシュで現実的でない)。 degraded 検査は git log 起点で、node_modules/ は gitignore 済みです。 つまり「別の層が受け持つ」という前提だけが記述されていて、その層は存在しない状態です。 S1 と同じ「gitignore 済みだがホストが実行する経路」の系統です。

修正案(推奨は 1)
  1. プローブから exec を無くす。 このプローブの仕事は「依存が入っているか」の確認であって、コードの実行ではありません。マーカーに非実行形式を足し、ホスト側は [ -x node_modules/.bin/eslint ] 相当の stat だけで判定する: 
    <!-- verify-probe: exists node_modules/.bin/eslint -->
    形式検査は現行の文字集合検査をそのまま流用でき、ホスト実行の経路自体が消えます。既存の P1〜P3 は後方互換として残せます。
  2. 実行を残すなら指紋を取る。 P2 のとき解決先(node_modules/.bin/<pkg> とその実体)を git hash-object し、前回値と違えば警告する。追跡外ファイルにも効きます。

なお npm / npx を許可コマンドに残していること自体は、.npmrc が denylist にあり 入口検査1(フェイルクローズ)が検査3 より先に走るため、.npmrc 経由の乗っ取りは塞がれています。順序は正しいです。

MediumS3. .claude/settings.local.json が禁止領域に入っていない
.claude/scripts/delegate-codex.sh:258-273 / .gitignore:52

.claude/settings.json は禁止領域にありますが、.claude/settings.local.json はありません。 このファイルも hooks と permissions を定義でき、.gitignore 済みなので git diff にも出ません。 委託先がこれを新規作成すると、次に人間が Claude セッションを開いた瞬間に SessionStart hook としてホストコマンドが走ります。

緩和はあります ― denylist に .claude/settings.local.json が入っているため、次回の委託は入口検査1 で止まります。 ただし止まるのは「次の委託」であって「次のセッション開始」ではありません。時間順ではセッション開始のほうが先に来ます。

修正案
  ".claude/settings.json"
+ ".claude/settings.local.json"

S1 の修正(.claude/ 配下は既にディレクトリ単位が原則)と同時に入れるのが自然です。

MediumS4. モード C の監査が、監査される側の自己申告に依存している
.claude/scripts/check-guard-integrity.sh:299,341(D3 / D4)

D3(禁止領域への差分)と D4(package.json 変更)は、いずれも git log --grep='Codex-authored' で対象コミットを選びます。 このトレーラーは Codex 自身が付けるものなので、付けなければ両検査の対象から外れます。 設計としては「上限で殺されても各コミットが自分で名乗る」という可用性の要件から来たもので、その目的には適合していますが、 敵対的な相手に対する識別子としては機能しません。

修正案(安価)

モード C では定義上 Claude はコミットしません。したがって範囲内の全コミットがトレーラーを持つのが正常です。 逆向きの検査 ― <base>..HEAD でトレーラーを持たないコミットを列挙して報告する ― を D3 の直前に足せば、 「名乗らずに紛れ込んだコミット」を検出できます。既存の git log の引数を変えるだけで、 D3 / D4 のループ本体には手を入れずに済みます。

2. 動作上の欠陥

MediumB1. explore / review の並行実行が impl の出口検査を誤爆させる
.claude/scripts/delegate-codex.sh:273(.harness/codex-runs/)/ :1137-1157(forbidden_files)/ :1424
連鎖
  1. .harness/codex-runs/ が FORBIDDEN_PATHS に含まれる。
  2. forbidden_files() は find .harness/codex-runs -type f で全 run record を列挙し、除外するのは今回の委託自身の 3 ファイルだけ($REC / $LOG / $LAST)。
  3. 一方 delegation-policy.md は「read-only の explore / review はこの検査(5-5)を通らず並行できる」と明記しており、これは意図された運用。
  4. impl の実行中に explore / review を 1 本起動すると、そちらが .harness/codex-runs/ に新しい .json / .log / .last.txt を作り、.log は実行中ずっと成長する。
  5. impl の FORBIDDEN_AFTER が FORBIDDEN_BEFORE と一致しなくなる。
帰結

impl が正常に完了していても status=failed / exit 2 になり、 「委託禁止領域が変更されました」というセキュリティ違反の見た目で返ります。 同じことは、impl の実行中に人間が codex-run.sh accept <id> や set-status を叩いた場合にも起きます。

実害は失われた作業と枠だけではありません。この層は「鳴ったら本物」であることに価値があります。 運用上ありうる操作で偽陽性が出ると、次に本物が鳴ったときに無視されます ― セキュリティ層としては最悪の壊れ方です。

修正案

.harness/codex-runs/ を内容ハッシュ比較の対象から外し、別の軸で守るのが筋です。 このディレクトリで守りたいのは「委託先が自分の結果を accepted: true に書き換えないこと」であって、 「ファイルが 1 バイトも変わらないこと」ではありません。 

# 案: forbidden_snapshot() は BEFORE 時点に存在した record だけを対象にし、
#     かつ .log を除外する(ログは実行中に成長するのが正常)。
#     accepted / status の書き換えは rec_field で個別に突き合わせる。

最小の応急処置としては、forbidden_files() の除外を「自分の 3 ファイル」から 「BEFORE スナップショット取得時に存在しなかったファイルすべて + 全 .log」に広げるだけでも誤爆は止まります。

check-forbidden-paths-doc.sh が見るのは「一覧にあって CLAUDE.md に無い」方向だけです。 逆向き ―CLAUDE.md にあって一覧に無い― は検出されません。 S1 がまさにこの穴です: CLAUDE.md は「3 系統」の説明で実体を .husky/*(ディレクトリ)と書いているのに、 配列は 2 ファイルしか持っていません。片方向の検査では永久に気づけません。

細部として、--print-forbidden の出力に重複と非パスが混ざります (AGENTS.md のバックティック抽出由来で delegate-codex.sh や <!-- verify-probe: ... --> が出る)。 消費側が実在検査で落とすため無害ですが、check-guard-integrity.sh の is_forbidden() は コミット × 変更ファイル × 一覧行の三重ループでこの雑音を毎回舐めます。出力側で sort -u + 実在検査をしておくのが素直です。

コメント率の高さ自体はこの種のセキュリティ層では正しい判断です(「なぜこの形でないと駄目か」を実測付きで残さないと、次の変更で必ず戻される)。 問題は 1 ファイルに入口検査 5 系統・出口検査 2 系統・プロンプト構築・環境許可リスト・record I/Oが同居していることで、 今回のような監査で「どの層がどこを守っているか」を追うのに全文読解が要ります。

分割を阻んでいるのは自己コピー exec です。共有ファイルのコピーがファイル名でハードコードされています: 

cp "$_self_dir/lib-record.sh" "$_copy_dir/lib-record.sh" 2>/dev/null

ここを lib-*.sh のグロブに一般化すれば、lib-forbidden.sh(禁止領域の配列と forbidden_*())・ lib-probe.sh(プローブ形式検査)を切り出せます。lib-*.sh は既に CI(非実行 + shebang 無し)と SessionStart hook が機械検査する規約を持っているので、新しい約束事は要りません。 これは今回の指摘の中で唯一「壊れていないもの」への提案なので、S1 / B1 の後で構いません。

5. 妥当と確認した設計判断(変更不要)

  • OKフェイルクローズ / フェイルオープンの非対称 — 委託経路は止める側(fork がある)、保護ブランチ検査は通す側(止めるとコミット不能)。判断が明示され、各所で一貫しています。
  • OK自己コピー exec(#15) — --print-forbidden だけ短絡し、かつ CODEX_DELEGATE_NO_SELF_COPY=1 の無効化を必ずログに残す形は正しい。「明示的な無効化だけが黙って通るのは非対称」という理由付けも妥当です。
  • OK環境変数の許可リスト(env -i) — CODEX_DELEGATE_* を除外し、特に ACK_SECRETS の事実を委託先から観測させない配慮まで入っています。compgen -e(-v でない)の選択も正しい。
  • OKレート上限判定の範囲限定(#62) — 「成功時は判定しない」「構造化識別子はトップレベルのエラーイベント行だけ」の 2 段は、自己参照リポジトリの誤判定という実測に基づいた正しい修正です。
  • OKナンス付き標識ブロック(#61)+ ホスト警告の分離(#72) — ナンスを本文確定後に生成する順序、emit を全 8 終端経路の共通位置に置く設計、ESC / CR の除去理由まで正確です。
  • OKプローブ形式検査の許可リスト方式 — yarn / mvn / pnpm を実測で外し、裸の version と -v を拒否し、python3 -I を必須にした判断はすべて正しい。形式検査の設計自体には問題がありません(S2 は形式検査ではなく、実行してよいかという上位の問題)。
  • OKGitHub Actions — pull_request(pull_request_target でない)、author_association による絞り込み、permissions: contents: read、シークレット未設定時の ::warning:: 可視化。いずれも妥当です。
  • OK.husky/* を sh -e で実行する制約への対応 — 終了コードを必ず && / || のリストで受ける形と、その理由のコメントは正確です。prepare-commit-msg で $2 ではなく .git/MERGE_HEAD を見る判断も実測に裏付けられています。
