## 0. 位置づけと使い方

- このドキュメントは **「何を良しとするか」の基準(北極星)**。実装スタックに依存しない
- UI を作る前・レビューする前に、該当節を参照する
- 判断の優先順位(上が強い):
  1. **ユーザーの明示的な指示**(特定のトーン・色・参照を指定されたら、それが最優先)
  2. **プロジェクト既存のデザインシステム**(トークンファイル・テーマ・既存コンポーネント)
  3. **この規約**

### 2層構造

```
┌─ 第1層:デザイン原則(§1〜§5)……… スタック非依存・固定 ─┐
│  treatment判定 / デザインプラン / 余白・タイポ・カラー /  │
│  状態デザイン / AI回避リスト / アクセシビリティ            │
├─ 第2層:実装への翻訳(§7)……… プロジェクト毎に /kickoff で確定 ─┤
│  コンポーネントライブラリ選定 / トークンの実装形式         │
└──────────────────────────────────────────────┘
```

---

## 1. 最初に treatment(度合い)を見極める

作るかどうかではなく、**どの程度の演出で出すか**を先に決める。

| treatment | 対象例 | 方針 |
|-----------|--------|------|
| **実用系** | 管理画面・ダッシュボード・設定・メモ・計画 | 過度に飾らない。正しい階層・余白・パレットだけ。巨大なヒーローは作らない |
| **エディトリアル系** | LP・オンボーディング・共有したくなるツール | 大胆な視点を1つ。リスクは1箇所だけに集中させる |

> 迷ったら「よく整った控えめなページ」が正解。**過剰デザインは失敗になりうる。**
> UI(操作するもの)は読み物ではない。タイポより **情報設計**(要約を先に、状態を形で表す)を優先する。

---

## 2. 実装前に「デザインプラン」を書く(必須ステップ)

いきなりコード/CSS を書かない。**先に小さなトークン設計を言語化**し、以降の全ての色・書体決定をここから導出する。

- **Color**: 4〜6個の命名済み hex 値でパレットを記述(例: `bg` / `surface` / `text` / `muted` / `accent`)
- **Type**: 2役以上の書体(特徴的なディスプレイ / 読みやすい本文 /(必要なら)データ用)+ タイプスケール(例: 12/14/16/20/24/32)
- **Layout**: レイアウト構想を1〜2文で

このプランをコード上ではトークン(CSS変数・テーマ設定・デザイントークンファイル等、スタックに応じた形式)に落とし、**全画面で再利用**する。

## 3. デザイン原則(スタック非依存)

### 3.1 余白(最重要)
- **4px / 8px グリッド**に揃える(padding・margin・gap をすべて4の倍数に)
- 関連要素は近く、無関係な要素は遠く(近接の原則)
- **迷ったら余白を増やす。** 素人UIの崩れは9割が「余白不足・不揃い」

### 3.2 タイポグラフィ
- 書体は1〜2種類まで。サイズはタイプスケールで段階を固定
- 本文 line-height は 1.5〜1.7、見出しは 1.2 前後
- 強弱はウェイトで(太字を多用しない)。本文の1行は約65文字幅を目安に
- **日本語 UI の補足**:本文は **16px 以上**、行間は欧文より広めの **1.7〜1.8**、見出しはやや太めにすると可読性が上がる(漢字仮名交じりは字面が詰まりやすいため)

### 3.3 カラー
- **ベース(ニュートラル)60% / メイン30% / アクセント10%**
- **アクセントは1色だけ。** 多色使いは安っぽくなる
- ニュートラルは"選ぶ":純粋な中間グレーは「考えてない」に見える。アクセント寄りにわずかに色味を持たせる
- **セマンティックカラー(good / warning / critical)はアクセントとは別物**。状態表現に使い、アクセント枠を消費しない

### 3.4 整列
- 左端・ベースラインを揃え、視覚的なガタつきを消す

### 3.5 状態デザイン(手を抜かない)
画面/コンポーネントごとに、以下を**必ず**設計する:

- [ ] hover
- [ ] focus(キーボードで見える focus を必ず)
- [ ] disabled
- [ ] loading
- [ ] **empty(空の状態)**
- [ ] **error(何が起きたか + どう直すか)**

> empty / error の作り込みが、素人と玄人の差になる。

### 3.6 コンポーネント化と一貫性
- ボタン・入力欄・カードを毎回書かず、**再利用可能なコンポーネント**にする
- 角丸・影・境界線のルールを1つに統一

### 3.7 両テーマ(light / dark)
- パレットをトークンで定義し、light/dark **両方を同等の質**で設計する
- 単純な色反転にしない。両方でコントラストとアクセントが機能することを確認
- 意図的に片テーマへ振り切る場合は「選択」として明記(omission にしない)

### 3.8 コピーも design material
- 能動態。コントロールは起きることを名乗る(「公開」→ トーストで「公開しました」)
- システム都合の名前ではなく、人が認識する名前で(× webhook 設定 / ○ 通知)
- エラーは謝罪や曖昧さではなく「原因 + 直し方」

### 3.9 構造は情報
- 番号(01 / 02 / 03)・区切り・ラベルは、**内容の真実を符号化するときだけ**使う
- 順序が意味を持たないのに番号を振らない(装飾で構造を足さない)

## 4. 「AIっぽいデザイン」回避リスト

指定が無い限り、以下の"定番の逃げ"に着地しない(= 平凡の正体):

- クリーム地(#F4F1EA)+ セリフ見出し + テラコッタのアクセント
- ほぼ黒地に、アシッドグリーン/バーミリオンを1点だけ
- 細いヘアライン罫の新聞風・過密カラム
- 紫→青グラデのヒーロー(白背景)
- Inter / Space Grotesk を「無難だから」で選ぶ
- 絵文字を見出しマーカーに使う
- 何でも中央寄せ
- 何にでも `rounded-lg`(角丸)
- 角丸カードに左端のアクセントバー/レール

> ユーザーがこれらを**明示的に指定**した場合は、その指示が最優先(従う)。
> 「自由に決めてよい部分」をこの定番に費やさない、というルール。

---

## 5. アクセシビリティ最低ライン(WCAG AA)

- 本文コントラスト比 **4.5:1** 以上(大きい文字は 3:1)
- キーボードフォーカスに可視状態を必ず与える
- `prefers-reduced-motion` を尊重(過剰アニメを抑制)
- 色だけで情報を伝えない(形・ラベルを併用)

---

## 6. UIレビュー用チェックリスト

実装後、`/design:critique`(Design プラグイン)または `code-reviewer` subagent に以下を**機械的に**当てる。

> **Design プラグインは画面作成があるプロジェクトのときだけ導入する**(`/kickoff` フェーズ1.5 で判断)。未導入・画面が無いプロジェクトでは `code-reviewer` にこのチェックリストを当てればよい。

- [ ] treatment は適切か(実用系なのに過剰演出になっていないか)
- [ ] デザインプラン(§2)の通りにトークンが使われているか
- [ ] 余白はすべて4の倍数か
- [ ] アクセントは1色に収まっているか
- [ ] 状態(§3.5:hover/focus/disabled/loading/empty/error)は揃っているか
- [ ] light/dark 両テーマで破綻していないか
- [ ] §4 の「AIっぽい定番」に逃げていないか
- [ ] コントラスト比 4.5:1 を満たすか(§5)

---

## 7. 実装への翻訳(`/kickoff` 時に確定)

第1層(原則)を、プロジェクトの実装スタックに翻訳する。**`/kickoff` のスタック整合フェーズで以下を埋め、この節を更新する。**

| 項目 | 決定内容(プロジェクト開始時に記入) |
|------|------------------------------------|
| UI フレームワーク | 例: React / Vue / SwiftUI / … |
| コンポーネントライブラリ | 例: shadcn/ui + Tailwind / PrimeVue / Mantine / …(**自前CSSを減らすほど品質が安定**) |
| デザイントークンの実装形式 | 例: CSS変数 / Tailwind config / テーマオブジェクト |
| アイコン | 例: lucide / … |
| 参照デザイン(トーン) | 例: 参考URL・スクショ・キーワード |

> **コンポーネントライブラリの採用は、実装品質の最大の単一レバー。** スタック確定時に必ず決める。

## 8. Figma を使う場合の導線(design-first の将来オプション)

現状は **code-first**(仕様から直接UIを起こす)を基本とし、この規約(§1〜§6)がそのまま基準になる。
将来 **Figma で先にデザインを作る運用(design-first)**に移行する場合は、以下に切り替える。

### 8.1 切り替えの判断

```
デザインを先に Figma で作る?
├─ NO (code-first / 現状) → §1〜§6 が基準。トークンはコード側で定義
└─ YES (design-first)     → 基準の"源泉"を Figma 側に移す(下記)
```

### 8.2 design-first に移行したときの運用

- **トークンの源泉を Figma Variables に置く**:§2 のデザインプラン(color/type/layout)を Figma の Variables / Styles として定義し、そこを単一の真実とする
- **Figma MCP(公式)で design→code**:レイアウト・コンポーネント構造・デザイントークンに直接アクセスし、実装の再現度を上げる
- **`/design:handoff`(Design プラグイン)**で Figma から開発向け仕様を生成
- この規約の役割は変わらない:§3〜§5 の原則・§4 の回避リスト・§6 のレビュー観点は Figma 上のデザインにもそのまま適用する(基準は共通)

### 8.3 導入候補ツール(参考)

- **Figma MCP(公式)** — 双方向連携(Design↔Code)。design-first の主軸
- **Design プラグイン** — `/design:critique` `/design:handoff` `/design:accessibility` `/design:ux-copy`(**画面作成があるプロジェクトのとき `/kickoff` フェーズ1.5 で導入判断**。常設はしない)
- **Mobbin MCP** — 実アプリ画面の参照集め(§7 の「参照デザイン」の供給源)
- **magic-mcp(21st.dev)** — 叩き台のUIコンポーネント生成

> どの導線でも、**基準はこのドキュメント(§1〜§6、加点は §9)に一元化**する。ツールは基準を実現する手段。

## 9. 洗練を一段上げる(editorial treatment の加点ルール)

§1〜§6 は「崩れない(平凡でも減点されない)」ための基準。この節は **「加点する(おしゃれ・キャッチー・AIっぽくない)」ための攻めのルール**。共有したくなる画面(LP・オンボーディング・主要ツール)や、印象で差をつけたい画面に適用する。**実用系の管理画面には過剰適用しない**(§1 の treatment 判定に従う)。

### 9.1 タイポで殴る(おしゃれさの最大レバー)
- ディスプレイと本文を**意図的にペア**にする(Inter+Inter をやめる)。特徴のある見出し書体 + 読みやすい本文
- **サイズの落差を極端に**(見出し 48〜96px / 本文 15〜16px)。中間を作らない
- 大見出しはトラッキングを詰める(-0.02〜-0.04em)、小ラベルは開けて大文字(mono ラベルは"スタジオ感")
- ドロップキャップ・巨大な連番・見出しの mix-weight・`text-wrap: balance`

### 9.2 意外な1色 + 選んだニュートラル
- アクセントは定番(紫グラデ・アシッドグリーン)を避け、**くすみ系の意外な1色**に絞る
- ニュートラルに微かな色味を仕込む(純粋グレーは"考えてない"に見える)
- 大胆さは1箇所に集中。周りは徹底して静かに

### 9.3 シグネチャーモーメント(キャッチーさの核)
- 動きは**1つの見せ場に賭ける**(ページロードの stagger / スクロール連動リビール / ホバーの意図)
- **入れすぎると逆にAIっぽくなる**。散らさない。`prefers-reduced-motion` を必ず尊重

### 9.4 レイアウトで冒険する
- 全部中央寄せをやめ、**非対称・主従・余白**で緩急を作る
- 重なり(overlap)/画面外へのはみ出し/余白を"デザイン要素"として使う

### 9.5 ディテールで作り込む
- 微細なグレイン/メッシュグラデ等の**質感**でフラットさを脱する
- 角・境界(影か線か)の言語を1つに統一。カスタムのフォーカス/セレクション色
- **実データ・実コンテンツ・実画像**(Lorem・ストック・絵文字マーカーをやめる = 最大の脱AI)

### 9.6 参照ドリブンで作らせる
- 実プロダクト・Mobbin・スクショ・URL を「このトーンで」と**ブリーフとして渡す**(言葉より効く)
- §2 のデザインプランに加えて「**リスクは1箇所だけ取れ**」と明示する
- 仕上げに `/design:critique` へ「AIっぽい点はどこか」を批評させ反復する

> **判断基準**:自由に決めてよい部分を"定番の逃げ"に費やさない。§4 の回避リストが「引き算」、この §9 が「足し算」。

## 10. ジャンル別スタート・プリセット

§1 の treatment 判定を**具体的な出発点**に落とすための、製品タイプ別の初期スタイル集。**これは「出発点」であって「ゴール」ではない** —— プリセットをそのまま出すと平凡になる。必ず §9(加点)を最低1つ重ね、§4(回避)を外してから仕上げる。

### 10.1 プリセット早見(推奨)

| ジャンル | スタイル | 配色 | タイポ | レイアウトの肝 |
|---|---|---|---|---|
| ポートフォリオ / ブランディング | **Bold Minimalism** | 白 or ライトグレー地・チャコール文字・鮮烈な1色は**ホバー/ボタンのみ** | 幾何サンス or インパクトある太字 | 全幅の巨大キャッチ、グリッドに縛られない配置、ジャンプ率で魅せる |
| コーポレート / メディア・ブログ | **Editorial Craft** | 生成り・墨/ネイビー・マスタード/ワインの落ち着いたアクセント | 明朝/セリフ(見出しも本文も) | 左右非対称でジグザグ誘導、1px 実線の罫、大写真×極小キャプション |
| EC / ライフスタイル・コスメ | **Warm Organic** | オフホワイト/オートミール・テラコッタ/セージ/くすみピンク・柔らかいブラウン文字(真っ黒は避ける) | 丸みサンス or 上品セリフ | アーチ状の画像切抜き、ウェーブ境界、ノイズ質感 |
| イベント / プロモ LP | **Interactive Kinetic** | ハイコントラスト・ビビッド | 太くて可読性の高いサンス | スクロール連動、カスタムカーソル、3D 背景(WebGL / GSAP) |

**条件付き採用の注意:**
- **Warm Organic**:「クリーム地 + テラコッタ + セリフ」は §4 に挙げた**AI定番の組合せに近い**。アクセント色・書体・質感のどれかで必ず差別化する。
- **Interactive Kinetic**:§9.3「見せ場は1つに賭ける」を守る。**全編アニメ・ネオン多色グラデは逆にAIっぽくなる**。シグネチャーを1つに絞る。

### 10.2 使い方(プリセット → 実装)
1. ジャンルから1つ選び、§2 のデザインプラン(色4–6 / 書体2役 / レイアウト)に落とす
2. §9 の加点を**最低1つ**効かせる(タイポの落差 / 意外な1色 / シグネチャーモーメント)
3. §4 の回避リストを外す(特に:書体の無難化・紫グラデ・全中央寄せ)

### 10.3 反面教師:「Modern Dark & Glow」の罠

SaaS/テックで最も量産される見た目 —— **グラスモーフィズム + ダークネイビー(#0B0F19)+ エメラルド→ブルーのグラデ + ネオンパープル + 巨大グローオーブ + Inter**。

- **なぜ罠か**:これは §4 の「AI生成の定番」のほぼ全部乗せ。完成度は出せても「動くが、どの SaaS とも見分けがつかない」に直行する。**"AIらしくない"を目指すなら既定にしない。**
- **それでもダーク×先進感を出したいなら**(脱・定番の作り方):
  - グローオーブ/グラデを廃し、**質感(グレイン)や1本の鋭いアクセント**で奥行きを作る
  - アクセントを紫/エメラルドの定番から外し、**意外な1色**に(§9.2)
  - Inter 一択をやめ、**見出しに表情のある書体**を(§9.1)
  - グラスモーフィズムを主役にせず、階層は**余白と罫**で作る

### 10.4 普遍ルール(§3 / §9 への補強)
- **余白は"デザインの一部"**:「空いたから埋める」ではなく「要素を目立たせるために作る」。セクション間・カード内を体感 **1.5〜2倍**に(§3.1)
- **不可視グリッドを揃える**:flex / grid で整列(`align-items` / `justify-content`)を徹底(§3.4)
- **心地よいマイクロインタラクション**:ホバーで少し浮く(`translateY(-2px)`)・影が濃くなる等。ただし **`transition: all` は使わない**(意図しない遷移・パフォーマンス劣化)。対象プロパティを明示する:`transition: transform .2s ease, box-shadow .3s ease`(§9.3)

> **出典**:本節は外部のアイデア集(ジャンル別デザイン提案)をレビューし、目的(洗練・AIらしくない)と §1〜§9 に照らして**採用可の項目のみ**を取り込んだもの。Style「Modern Dark & Glow」は AI 定番との衝突のため反面教師として掲載している。

## 11. AIデザイン依頼テンプレート(プロンプト)

「いい感じにして」「おしゃれにして」等の曖昧な指示は出力が大きくブレる。**何を・どんな順で・どんな雰囲気/色で**を具体的に定義して渡すと再現性が上がる。以下は貼って埋めるだけのプロンプト。**素の13観点テンプレートは"無難化"しやすい**ため、本ガイドライン固有の3層(§1 treatment / §4 回避 / §9 加点)を最初から織り込んである。

### 11.1 貼れるプロンプト

> **単体で使うなら** `docs/ui-design-request-template.md`(記入例つき)をコピーする。以下はその本体。

```text
Webサイト/画面のデザインを提案してください。

## 対象サービス
サービス名 / 概要:

## ターゲット(具体的に)
年齢層・利用シーン・抱えている悩み(例:ITに不慣れな個人事業主):

## 目的(この画面のたった1つの仕事)
例:無料登録させる / 世界観を伝える / 問い合わせを増やす:

## treatment(演出の度合い) ← §1
実用系(管理・設定) / エディトリアル系(LP・共有したくなる):

## 希望する印象(2〜3語の組み合わせ)
例:上品 × 親しみやすい × 静か:

## 避けたい印象(必須) ← §4
例:子どもっぽい / 派手すぎ / 情報過多。加えて次の "AI定番" を避ける:
紫→青グラデ、グラスモーフィズム+グローオーブ、Inter一択、全部中央寄せ、
何でも角丸lg、絵文字の見出しマーカー
```

### 11.2 精度を上げるコツ
- **ターゲットと目的は具体的に**(誰に・何のために)。抽象語ほど出力がブレる
- **「避けたい印象」を必ず書く**(§4)。望む印象より効くことがある
- **印象は組み合わせで**(単語1つより「A × B × C」)
- **参照を添える**(§9.6:実プロダクト・スクショ・URL を「このトーンで」)
- **情報の順序**まで指定すると、見た目だけでなく体験設計まで揃う

### 11.3 記事版との差分(なぜこの版か)
元記事の13観点テンプレートに、本ガイドライン固有の3層を追加してある:
- **§1 treatment**:演出の度合いを最初に固定(過剰/不足を防ぐ)
- **§4 避けたい AI 定番**:回避リストをプロンプトに明示的に埋め込み(無難化の防止)
- **§9 加点**:「最低1つ攻める」を必須項目化(平凡からの脱出)

> **角丸16px 等の「柔らかい」指定は treatment 依存**。soft 系ブランドでは有効だが、editorial/硬派ではシャープな角に。印象で選ぶ(§10.1)。
