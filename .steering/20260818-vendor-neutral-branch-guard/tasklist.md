### 学んだこと

**技術的な学び**:

- **判定の実体を 1 ファイルに集約する構造が有効だった。** `latest-steering.sh` を hook・fork・スキルで共有しているのと同型。今回は `check-protected-branch.sh` を `.husky/pre-commit`(ベンダー非依存)と `check-branch-policy.sh`(Claude 専用)の両方から呼ぶ形にした。終了コードの読み替え(1 → 2)を呼び出し側に持たせることで、共有側は用途を知らずに済む
- **フェイルオープン設計は「セキュリティ境界として扱わない」という前提とセット。** ポリシーファイルや `jq` が無い環境でコミット不能にしない代わりに、権限境界は GitHub のブランチ保護に置く。この割り切りを design.md とプラン §8 の両方に明記した
- **ガードレールのメッセージにバイパス手段(`--no-verify`)を書かない。** ブロックしている当の画面で回避策を案内するのは本末転倒。存在自体はドキュメントに残す

**プロセス上の改善点**:

- design.md にスクリプト全文を書き切ったため、実装が機械的な作業になった。fork に渡しても設計判断ゼロで通せる粒度だったが、今回は参照実装として司令塔が直接実装した(`<!-- main-edit-ok -->` の脱出弁を使用)

### レビューで発見・修正した自作の欠陥

**共有スクリプトの呼び出し側がフェイルオープンになっていなかった。**

- 当初の実装は `if ! bash .claude/scripts/check-protected-branch.sh; then exit 2; fi` としていたが、これは**違反(exit 1)以外もすべてブロック**する。スクリプト不在(exit 127)や内部エラーのときに、保護ブランチでなくても全コミットが止まる
- 共有スクリプトは 4 条件でフェイルオープンする設計なのに、**呼び出し側が fail-closed** という設計と実装の不整合だった。テンプレート同期の途中状態・権限落ち・パス解決失敗で開発が止まる事故につながる
- 修正: 両方の呼び出し元で `case $? in 1) ... esac` とし、**exit 1 だけを違反として扱う**
- 検証を 15 → 20 ケースに拡張(不在 × hook/husky、不在かつ保護ブランチ、内部エラー × hook/husky)。全 PASS
- **学び**: 「フェイルオープン設計」は共有スクリプト側だけでは完結しない。**終了コード契約は呼び出し側にも同じだけの責任がある。** 判定を 1 箇所に集約したことで、逆に「呼び出し側が契約を誤読する」新しい失敗モードが生まれていた

### 監査で発見した「自分で作った層」の弱点

**自壊検知そのものがベンダー依存だった。**

- フェーズ7 で追加した「`.husky/pre-commit` が共有スクリプトを呼んでいるか」の検査は SessionStart hook = **Claude 専用**にしか置いていなかった
- ところがこの層が守りたいのは「Claude が居ない期間(モード C)」である。**検知が必要な期間に検知役が動かない**という構造で、「層が無いことより気づけないことの方が悪い」という自分の論理がそのまま跳ね返っていた
- 修正: 同じ検査を CI の Harness integrity にも置いた。SessionStart = 早期警告 / CI = クライアント非依存の最終検証、という二層に整理
- **学び**: ベンダー中立な層を作るときは、**その層の監視役もベンダー中立か**を必ず確認する。守る対象だけを中立化しても、監視が依存していれば実効性は監視側の可用性に落ちる

### 発見した既存の不具合(スコープ外・要別対応)

**`check-branch-policy.sh` の `CMD_START` 正規表現が markdown のコードスパンを誤検知する。**

- `CMD_START` はコマンド置換を拾うためにバッククォートを起点文字に含んでいる。そのため文書中のコードスパン(バッククォートで囲んだ PR 作成コマンドなど)が「コマンド位置のコマンド呼び出し」と誤判定される
- **今回この振り返りと `requirements.md` を heredoc で書こうとして実際に 2 回ブロックされた**(Write / Edit ツールに切り替えて回避)
- 影響: PR 作成やコミットのコマンドに言及するドキュメントを Bash 経由で書けない。このテンプレートは自分自身のワークフローを文書化するため、遭遇頻度が高い
- 同ファイル冒頭が「文字列パターンによるベストエフォート」と断っているとおり既知の割り切りではあるが、**バッククォートだけは誤検知の実害が大きい**。起点文字から外すか、対になるバッククォート(コードスパン)を除外する前処理を検討する

### 5 巡目の監査(フェーズ10)で見つかったこと

**同じ失敗が 3 度形を変えて出た: 「検査を守るための条件が、検査そのものを無効化していた」。**

- フェーズ7 で自壊検知を作り、フェーズ8 で「検知役がベンダー依存だった」と直し、フェーズ10 で「**検知の前提条件(スクリプトの存在)が満たされないと検知自体がスキップされる**」と直した。`[ -f script ] && ! grep ...` という形は、**層が完全に消滅した最悪のケースで exit 0** になる
- 一般化すると **「X が壊れていないか」を X の存在を前提に検査してはいけない。** 検査対象の消失は、検査が捕らえるべき事象のうち最も重いものである
- 検証を A〜E の 5 ケースに拡張し、C(スクリプト削除)と D(スクリプト削除・呼び出し残存)が exit 1 になることを確認した

**規約を反転させたとき、写像先の全部を数えていなかった。**

## 8 巡目の監査(フェーズ13)で見つかったこと

**フック名を守備範囲だと思い込んでいた。**

- `pre-commit` という名前は「コミット前」と読めるが、実際に発火するのは `git commit` と `git commit --amend` **だけ**。`git revert` / `git cherry-pick` では発火しない(実測)
- つまりこの層が守っていたのは「コミットという**結果**」ではなく「`git commit` という**コマンド**」だった。層の名前(「保護ブランチへの直接コミットを止める」)と実際の守備範囲がずれていたが、名前が正しく見えるぶん気づけなかった
- Claude 側の `check-branch-policy.sh` も同じ正規表現の作りで `git commit` だけを見ており、**同じ思い込みが 2 層に写っていた**。ベンダー中立化のために「同じ判定を 2 経路へ写す」設計にしたことで、**欠落もそのまま複製されていた**
- **学び**: 「どの操作を守るか」はフック名や直感ではなく**実測**で確かめる。特に判定を複数経路へ写す設計では、写す前の判定が正しいかを先に検証する(誤りも等しく複製される)

**副次的な収穫**: `prepare-commit-msg` は `--no-verify` で迂回できない(`--no-verify` が無効化するのは `pre-commit` と `commit-msg` だけ)。残る穴として割り切っていた 3 件のうち 1 件が、ローカル層だけで塞がった。

**「X の存在を前提に X を検査する」を 3 回繰り返した。**

- フェーズ8: 共有スクリプトが消えると検査がスキップされた → 修正
- フェーズ12: `sh -e` で呼び出し側のフェイルオープンが無効化されていた → 修正
- フェーズ13: **`.husky/pre-commit` ごと消えると検査ブロック全体がスキップされた**
- 同じ構造を 3 回踏んだのは、そのつど「今回の修正対象」だけを見ていたため。**検査を書いたら「この検査自体が実行されない条件」を必ず列挙する**という手順にしないと再発する
- 併せて、呼び出し検査が文字列一致だったため**説明コメントにファイル名があるだけで緑になる**ことも判明した(今回コメントを厚くしたことで自分が踏みかけた)
