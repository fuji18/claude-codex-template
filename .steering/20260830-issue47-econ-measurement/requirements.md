# 要求: econ モードの効果測定を回す(測定設計 + リマインドの組み込み)

- Issue: #47(`ticket` / P2 / `delegate:codex` なし)
- 根拠: Codex 併用ハーネス実装レビュー(2026-08-29)C-2 / 優先順位 8 位

## 背景

`.claude/rules/lead/delegation-policy.md` は委託粒度の閾値について「**上の閾値は初期値であり、この実測で上下させる**」と宣言している。しかしモード B(econ)の週枠寿命の比較は `.harness/decisions.jsonl` の `mode-b-weekly-budget-baseline-followup` に **`"status":"未実施"`** と記録されたまま止まっている。

宣言だけがあって実測が回っていない状態は、#37 が機械化で塞いだ「散文の運用ルールは守られない」と同じ構造。**欠けているのは econ モードの週枠寿命の比較だけ**で、委託自体の効果(生ログ 66,347 B → 司令塔へ約 60 B / 0.09%)は実測済み。

## 要求

1. **何を・いつ・どの粒度で記録するかを先に確定する。** 測る前に決めないと比較不能なデータが溜まる
2. **記録漏れを防ぐリマインドを `.claude/rules/mode/econ.md` に 1 行で入れる。** 注入文は econ モードの全セッションに載るため、行数がそのまま恒常コストになる
3. `mode-b-weekly-budget-baseline-followup` エントリを、確定した測定設計に更新する

## 制約

- **`/usage` は人間しか読めない。** Claude は残枠を取得できないため、測定設計は「人間に 1 行で尋ねる」経路を前提にする。答えが得られないときに作業が止まってはならない
- **モード切替の宣言は人間の担当。** 測定のためにモードを切り替えるようリマインドしない(`.harness/mode` は Claude が書き換えない)
- **`decisions.jsonl` のスキーマは壊さない。** CI(`check-record-hygiene.sh` 検査2)は `"issue": N` の存在だけを見る前提

## スコープ外

- 測定の自動化(hook で `/usage` を叩く等)。機械取得できず、無理に自動化するとコストが測定対象を歪める
- 閾値そのものの変更。データが揃ってからが順序
- `usage` フィールドを CI の必須項目にすること(`/usage` を読めない経路で全 PR が落ちる)
