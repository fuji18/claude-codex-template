# 検証記録・振り返り: running 残置 record の検出時に禁止領域の git diff を機械確認する(Issue #46)

## 1. このチケットの本題(何を塞いだか)

出口検査(禁止領域の内容ハッシュを委託の前後で比べる層)には**到達しない経路**がある。SIGINT / SIGTERM で `codex exec` の途中に死ぬと、検査そのものが走らない。そのとき禁止領域が書き換わっていると、**次回委託の BEFORE スナップショットが改ざん後の内容を「元からあった状態」として取り込み**、以後その改ざんは恒久的に検出不能になる。

手当は入口検査5-5 の警告分岐だけだった。**警告は人間が読み飛ばせる**ので、検出機会は実質失われていた。今回、その警告と同じ場所に**機械検査**(`git diff HEAD` + `git ls-files --others --exclude-standard`)を置き、dirty なら `exit 2` で止めるようにした。

## 2. 設計判断(司令塔が計画時に確定させたこと)

| 判断 | 採った側 | 根拠 |
| --- | --- | --- |
| dirty のときの倒し方 | **止める(`exit 2`)** | 5-5 が「pid 再利用の誤検知は止める側に倒す」既存方針を持つ。同じ検査区画で逆向きの非対称を混ぜない。通したコスト(検出機会の恒久的喪失)>止めたコスト(`set-status` 1 コマンド) |
| 誤爆(司令塔がハーネス層を改修中) | **受容して文書化** | 解除は record を実態に合わせるだけで、差分を捨てる必要がない。むしろ「先に残置 record を始末させる」催促として機能する |
| git 追跡外(`.harness/mode` / `.harness/codex-runs/`) | **対象外と明記** | `.gitignore` 済みで `git diff` にも `ls-files --others --exclude-standard` にも出ない。ここは出口検査の内容ハッシュ比較だけが見る層として残る |
| `forbidden_files()` の再利用 | **しない** | あの関数は `$REC` / `$LOG` / `$LAST`(run record 節でしか定義されない)を参照するため、5-5b の位置では `set -u` で落ちる。関数分割は、この層が見る対象(git 追跡ファイルのみ)の狭さに見合わない |

## 3. 検収(fork 往復 2 回 / レビュー 2 巡)

### 1 巡目: Critical 1 / Major 1 / Minor 1(すべて採用)

**Critical — git magic pathspec による無音のフェイルオープン。** `PROJECT_FORBIDDEN_PATHS` は `AGENTS.md` のバックティック断片を**無検証で抽出したもの**で、それを pathspec にそのまま渡していた。`:(exclude)...` が紛れ込むと**他の一致結果ごと除外**される:

```
git diff HEAD --name-only -- ".claude/scripts/" ":(exclude).claude/scripts/delegate-codex.sh"
→ 出力なし(実際は delegate-codex.sh が dirty)
```

つまり**中断した委託が `AGENTS.md` に断片を仕込んでから死ねば、次回起動でこの検査自身が無効化される**。塞ごうとしている穴を、新設した検査が自ら再現していた。

対処は 2 段(`:` 始まりを正規化で捨てる + `GIT_LITERAL_PATHSPECS=1` で magic / glob 解釈を止める)。片方だけだと「環境変数が効かない git 実装」「`:` 以外の magic 記法の追加」のどちらかで再び無音になる。

**Major** は同じ根から出た別の症状(出口検査 `forbidden_files()` の `case` 規則と git の glob 解釈がずれ、保護対象でないファイルで誤ってブロックしうる)。正規化を `forbidden_files()` と同じ `case` に揃えて閉じた。

### 2 巡目: Critical 0 / Major 0 / Minor 1(不採用)

「`_forb_specs` が空になる分岐は現状到達しない(`FORBIDDEN_PATHS` は固定 10 件でいずれも `:` 始まりでない)ので、コメントに理論上のケースである旨を添えるとより正確」。**不採用** — 分岐自体は将来の変更に対する防御として正しく、空振り条件の列挙としても誤りではない。ハーネス中枢に可読性だけの差分を足すコストの方が高い。

### 実測(司令塔が実ブランチ上でも再現)

| 条件 | 期待 | 結果 |
| --- | --- | --- |
| 残置 record + 禁止領域 clean | 警告のみで通過 | 5-5b の停止メッセージは出ず先へ進む(fork がスタブ `codex` + 使い捨て worktree で確認) |
| 残置 record + 禁止領域 dirty | `exit 2` | 該当パス・残置 id・回復手順つきで停止。`codex` は呼ばれず run record も作られない |
| 上記 + `AGENTS.md` に `:(exclude)...` を注入 | `exit 2`(無効化されない) | `.claude/scripts/delegate-codex.sh` と `AGENTS.md` の両方を列挙して停止 |

## 4. 学び(次のチケットへの申し送り)

1. **「無検証の外部入力をシンクに渡している」箇所は、シンクが増えるたびに再点検する。** `PROJECT_FORBIDDEN_PATHS` の抽出コメントには「実在しない断片は `forbidden_files()` の実在検査で落ちるので無害」と書いてあった。その前提は**その消費者にしか成立しない**のに、コメントは値そのものの性質のように読めた。新しい消費者(5-5b)を足した時点で前提は崩れていた。**同じ配列を読む場所を足すときは、既存の「無害である理由」がその経路でも成立するかを必ず確認する。**
2. **同じ入力を「別のシンク」に渡す変更は、`verify-probe` の先例が既にあった。** `AGENTS.md` 由来の値を `bash -c` に渡す経路には #43 で許可リスト検査を入れている。今回は同じ出所の値を `git` の pathspec に渡す変更で、**構図が完全に同型**だった。過去チケットが「どの入力にどんな検査を課したか」を、同じ入力を触るときの出発点にする。
3. **検査を足すときは「その検査自身を無効化できるか」を一度考える。** 今回の Critical は、新設した検査が自分を無効化される経路を持っていた。ガードレール層の追加では、機能の正しさとは別に**自己防衛の観点**を 1 項目立てる価値がある。
4. **実測の足場をコミット前提にすると実装フェーズと衝突する。** design §5 は「clean ケースの確認にはコミットが要る」と書いたが、実装フェーズはコミットしない方針。fork は使い捨て `git worktree` にコピーして実測するという回避を自分で見つけて完遂した。**計画側で「実装者はコミットできない」制約を織り込んだ検証手順を書くべきだった。**
