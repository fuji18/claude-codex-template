# 要求: 段階6 — チケット統合(`delegate:codex` ラベルと委託導線)

- Issue: #8(P2 / フェーズ6 / depends: #5 = closed)
- 根拠: `docs/template-dev/codex-delegation-plan.md` §11 段階6 / §6 / §10.3 / §8(623 行目の申し送り)

## 背景

段階0〜5 で委託の実行層(`delegate-codex.sh` の 3 モード・終了コード契約・run record・ハーネスモード・モード C のスキル)は揃った。残っているのは**振り分けの層**である。現状「このチケットを委託するか」は司令塔のその場の判断に委ねられており、判定の根拠がリポジトリのどこにも無い。

あわせて、テンプレートをプロダクト側で使うときの導線が 2 つ未着手のまま残っている(§8 の「ブランチ保護が使えるプランか」の確認、§10.3 の委託禁止領域のパス具体化)。

## 要求

1. `delegate:codex` ラベルを `/setup-tickets`(発行時)と `/next-ticket`(選定時)の両方で扱えるようにする
2. §6 の委託粒度・損益分岐・バッチ運用を、司令塔が毎セッション参照できる運用ルールに落とす
3. §10.3 の「委託禁止領域をパスで具体化する」導線を作る(テンプレート側は枠と記入手順、プロダクト側は `/kickoff` で記入)
4. `/kickoff` が「ブランチ保護が使えるプランか」を確認し、使えないなら §8 の 3 択を提示する
5. README に委託運用を記載する

## 受け入れ条件(Issue より)

- [ ] `delegate:codex` が付いたチケットが `/next-ticket` で委託経路に流れる
- [ ] チケット丸ごとの委託が 1 件成立する(§11 の「検証したいこと」)
- [ ] `/kickoff` がブランチ保護の可否を確認し、不可なら 3 択を提示する
- [ ] README に委託運用が記載されている

## スコープ外

- 委託粒度の閾値そのものの調整(§10.7 で実測ベースに委ねる。初期値のまま出す)
- `delegate-codex.sh` の `--background` 実装(段階4 で見送られたまま。§6 の表記に注記を入れるに留める)
- `delegate-codex.sh` の自己編集ハザード(§9)の**実装**。本チケットでは**方針の決定と記録まで**とし、実装は別 Issue に切り出す
