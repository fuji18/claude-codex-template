### 学んだこと

- **最適化は「速い経路」と「正しい経路」を分ける形にすると、性質の保存を証明しやすい。**
  `git hash-object --stdin-paths` は 1 ファイルでも失敗するとその場で die して後続を出力しないため、
  「1 ファイルずつ握りつぶして `UNREADABLE` にする」という既存の性質と両立しない。
  バッチ結果を**出力行数が入力行数と一致したときだけ採用**し、それ以外は旧経路をそのまま
  残す形にしたことで、「正しさは旧経路が持ち、バッチは速いだけ」と言い切れるようになった。
  部分成功でマッピングがずれる懸念も、die して後続を一切出さない挙動を実測して否定できた
- **性能改善の受け入れ条件は「速くなったこと」ではなく「判定内容が変わっていないこと」に置く。**
  Issue の受け入れ条件がもともとその形(前後のスナップショット一致)だったため、
  検証は「旧版と新版の出力 diff」に自然に落ちた。速度の実測は 1 つも取っていないが、
  それで問題ない — このチケットのリスクは遅さではなく判定のすり抜けにあった
- **`git hash-object --stdin-paths` は行頭の `"` を C クォート文字列として unquote する。**
  ファイル名を行区切りで渡す API 全般に共通する落とし穴で、先頭 `"` のパスがあれば
  バッチ自体を諦める形にした。途中の `"`・バックスラッシュ・タブ・先頭 `-` は影響しないことも実測済み
- **同じ懸念を説明するコメントが 2 箇所にあると、片方だけ古くなる。**
  `RUN_WARN_THRESHOLD` の根拠コメントが「前後 2 回のハッシュコストが線形」のまま残り、
  `forbidden_snapshot()` 直前の更新済みコメントと食い違った。design.md がコメント更新の
  対象を 1 箇所しか指定していなかったのが原因。**設計に「この変更で古くなる記述」を
  grep で洗い出す手順を入れる**と防げる(今回は `code-reviewer` が拾った)
