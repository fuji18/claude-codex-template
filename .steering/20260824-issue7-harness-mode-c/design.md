# モード C(縮退)— チケット 1 件を単独で完走する

Claude の枠が尽きている期間の手順です。**あなたが計画から実装・コミットまでを 1 人で担当します。**

縮退モードは行き止まりではなく**キュー**です。あなたはブランチにコミットを積むだけで、PR は作りません。Claude の枠が回復したら、通常フローの検収を経て PR に合流します。

> **この手順が特別な理由**: モード A・B の委託は `delegate-codex.sh` を経由し、そこで機械的な入口検査が掛かります。**モード C はその経路を通らない唯一の経路**です。同じ検査をあなた自身が実行する必要があります。飛ばさないでください。

## 0. 入口検査(必ず最初に、この順で)

4 つすべてを通してから作業を始めます。**1 つでも通らなければ作業を始めずに人間へ報告して停止してください。**

### 検査1: 自分がモード C で動いているか

```bash
cat .harness/mode 2>/dev/null || echo "(未設定)"
```

`degraded` **以外**(未設定を含む)なら、この手順を続けないでください。モード A・B は司令塔がいる前提の運用で、**コミットが禁止されています**。人間に「`.harness/mode` を `degraded` にするか、通常の委託経路(`delegate-codex.sh`)を使うか」を確認して停止します。

### 検査2: 保護ブランチにいないか

```bash
git branch --show-current
cat .claude/branch-policy.json
```

現在のブランチが `protectedBranches` に載っている場合、**自分で作業ブランチを切ってください**。モード C では司令塔がいないため、切らないと `.husky/` の git hook がコミットを弾いて詰みます。

```bash
git switch -c feature/[作業名]
```

接頭辞は `allowedPrefixes` に従います。

### 検査3: git hook が有効か

```bash
git config --get core.hooksPath
```

`.husky/` が存在するのに、この値が**空** または**実在しないディレクトリ**を指している場合は、作業を始めずに人間へ報告して停止してください。husky が丸ごと無効 = 保護ブランチへのコミットを止めるベンダー非依存の層が存在しない状態です。sandbox はネットワーク無効なので、あなた自身では復旧できません(`npm ci` が必要)。

> 値を `.husky` と決め打ちで比較しないでください。**husky v9 が設定するのは `.husky/_` です。**

### 検査4: 依存がインストール済みか

`AGENTS.md` の機械可読マーカーからプローブコマンドを取り出して、1 回実行します。

```bash
sed -n 's/^[[:space:]]*<!--[[:space:]]*verify-probe:[[:space:]]*\(.*[^[:space:]]\)[[:space:]]*-->[[:space:]]*$/\1/p' AGENTS.md | head -1
```

出力されたコマンドを実行し、**失敗したら停止して人間へ報告してください**。ネットワーク無効の sandbox では依存を自分で入れられないため、この状態で進めても何も完遂できません。

### 検査の結果を報告する

4 つ通ったら、1 行で報告してから次に進みます。

```
入口検査 OK: mode=degraded / branch=feature/xxx / hooksPath=.husky/_ / probe=pass
```

## 1. 作業単位を決める

**`gh` は使えません**(sandbox はネットワーク無効)。Issue の本文を自分で取得することはできないので、**要求は人間がプロンプトで渡します**。

- 要求が渡されていなければ、**推測で始めずに人間に聞いてください**
- 既存の作業を再開する場合は、未完了の `tasklist.md` を探します

```bash
ls -1d .steering/*/ | tail -5
```

未完了(`- [ ]` が残っている)ステアリングがあれば、新規に作らず**その続きから再開します**。

## 2. 計画を書く(steering 3 点)

```bash
date +%Y%m%d
```

`.steering/[YYYYMMDD]-[短い名前]/` を作り、3 ファイルを置きます。

| ファイル | 内容 |
| --- | --- |
| `requirements.md` | 人間から渡された要求・スコープ・受け入れ条件 |
| `design.md` | 実装方針。**冒頭に `<!-- status: ready -->` を書く** |
| `tasklist.md` | `- [ ]` のチェックリスト。**1 タスク = 1 コミットの粒度**にする |

> **モード C では設計もあなたが書きます。これは例外運用です。** 通常「設計判断は移管しない」のが原則で、モード C はそれを**延期しているだけ**です。あなたが書いた `design.md` は、Claude 復帰時に**それ自体がレビュー対象**になります。

## 3. 実装ループ(1 タスクずつ)

`tasklist.md` の項目を**上から 1 つずつ**片付けます。1 タスクごとに次の 5 手順を回してください。

1. **実装する**
2. **変更したファイルだけに** lint / フォーマットを掛ける
3. 型チェックと関連テストを通す
4. `tasklist.md` を `- [x]` に更新する
5. コミットする

> **`npm run format`(全体フォーマット)を回さないでください。** 人間や司令塔が並行して `docs/` を書いている可能性があり、その編集を書き潰します。範囲を絞るのは行儀ではなく競合回避です。

> **`tasklist.md` の逐次更新と、コミット前の品質チェックは行儀ではなく要件です。** あなたがレート上限で強制終了されたとき、サマリーは書けません。`tasklist.md` が唯一の進捗記録になり、壊れたコミットが残る確率を下げるのが品質チェックです。**まとめ更新・まとめコミットは禁止です。**

### コミットメッセージ

件名は Conventional Commits(`feat:` / `fix:` / `docs:` / `chore:` / `refactor:` / `test:`)に従い、日本語で書きます。**本文の末尾に必ずトレーラーを付けてください。**

```
feat: ○○を追加する

- 変更点の要約

Codex-authored: true
```

件名に `[codex]` のような接頭辞を付けないでください(Conventional Commits の規約を壊します)。このトレーラーは、あなたが強制終了されて `codex-log.md` を書けなかったときに**各コミットが自分で名乗る**ための識別手段で、Claude 復帰時に `git log --grep 'Codex-authored'` で回収されます。

### 途中で判断が必要になったら

- **設計判断**: モード C ではやむを得ず下して構いません。ただし **`codex-log.md` の「設計判断」欄に、何を・なぜ・代替案を必ず書いてください**(書かないと Claude 復帰時に回収されず、設計ドキュメントと実装が食い違ったまま残ります)
- **同じエラーの修正に 2 回連続で失敗したら**、同じアプローチを繰り返さないでください。原因の仮説を書き出してから別のアプローチを取ります
- **スコープ外のことをしない**: 優先度が付いている場合は P0 以外を実装しません。要求・`design.md` に書かれていない機能を足さないでください

## 5. やらないこと

| 項目 | 理由 |
| --- | --- |
| **PR を作る** | モード C はキューとして設計されています。PR は Claude 復帰後に検収を通してから作られます |

## 8. 追記(2026-08-24): `.codex/` は Codex 自身が書き込めない

### 判明した事実

初回の実装委託(run `20260824-123036-70876`)がタスク1で失敗した。Codex の報告:

> 失敗: `.codex/` が read-only のためタスク1の SKILL.md を作成できません / 絶対パス・相対パス・workdir 指定の apply_patch を試行(変更なし)

**裏取りした結果、これは Codex 側の正しい報告である。**

| 確認 | 結果 |
| --- | --- |
| 作業ツリーの変更 | **ゼロ**(`git status` は本ステアリングの未追跡ディレクトリのみ)。取り繕わずに停止しており、報告は信用できる |
| ファイルシステムの権限 | **無関係**。`.codex/` は `vscode:vscode` の `drwxr-xr-x` で、Codex も `vscode` として動く |
| Codex バイナリ内の権限モデル | `PermissionProfile` / `FileSystemSandboxEntry` と並んで `.agents` / `.codex` を含む保護パスの文字列が存在する |
| 過去の委託実績 | Issue #12 の委託では `.steering/` 配下を問題なく書き換えている。**ドットディレクトリ一般が不可なのではなく `.codex/` 固有** |

**結論: `--sandbox workspace-write` でも `.codex/` はエージェントの書き込みから保護されている。** エージェントが自分の sandbox 設定を書き換えられないようにする設計と考えられ、合理的な挙動である。

## 9. 追記(2026-08-24): `.git` も既定では書き込めない — モード C の起動方法を確定する

### 判明した事実(実機検証)

計画ドキュメント §9 が「モード C の設計では段階5(#7)で成立条件を必ず検証する」と指定していた項目を検証した。**前提は崩れていた。**

使い捨ての git リポジトリで `codex exec --sandbox workspace-write` を実行した結果:

| 起動方法 | 結果 |
| --- | --- |
| `--sandbox workspace-write`(既定) | ❌ **`COMMIT_NG`。`git add` の時点で失敗**(`.git` が読み取り専用) |
| `--sandbox workspace-write -c 'sandbox_workspace_write.writable_roots=["<絶対パス>/.git"]'` | ✅ `COMMIT_OK` |
| `--sandbox workspace-write -c 'sandbox_workspace_write.writable_roots=[".git"]'` | ✅ `COMMIT_OK`(**相対パスで動く**) |

**既定のままではモード C は成立しない。** Codex が 1 コミットも積めず、縮退モードがキューとして機能しない。

### 決定(ユーザー承認済み / 2026-08-24)

| # | 論点 | 決定 |
| --- | --- | --- |
| 11 | `.git` 書き込み許可の置き場 | **モード C の起動時に人間がコマンドラインで渡す。`.codex/config.toml` には書かない** |
| 12 | 理由 | `.codex/config.toml` に書くと**全モードに効く**。モード A・B はコミット禁止の運用であり、そこで `.git` を書けるようにすると sandbox レベルの担保を失う。**モード A・B ではコミットが sandbox によっても不可能**という二重の守りを維持する |
| 13 | 渡し忘れへの備え | **skill の入口検査に 5 つ目を足す**。skill 本文は Codex 起動後に読まれるため、起動フラグ自体は skill に書けない。代わりに「`.git` に書けるか」を検査させ、書けなければ**作業を始めずに起動し直しを促して停止**させる |

### モード C の起動コマンド(確定)

```bash
codex --sandbox workspace-write -c 'sandbox_workspace_write.writable_roots=[".git"]'
```

起動後、Codex に「`degraded-mode-ticket` スキルを使って作業して」と指示する。

### 追加の作業(タスク10〜12)

- **タスク10**: `.codex/skills/degraded-mode-ticket/SKILL.md` に**入口検査5**を追加する(司令塔が担当。`.codex/` は委託不可)

  検査内容は次のとおり。**実際に書き込みを試すのではなく、`git` に判定させる**(空コミットを作らない安全な方法):

  ```bash
  git stash list >/dev/null 2>&1 && touch .git/.probe 2>/dev/null && rm -f .git/.probe && echo "GIT_WRITABLE" || echo "GIT_READONLY"
  ```

  `GIT_READONLY` なら次を人間に伝えて**停止する**:

  > `.git` に書けないためコミットできません。次のコマンドで起動し直してください:
  > `codex --sandbox workspace-write -c 'sandbox_workspace_write.writable_roots=[".git"]'`

  併せて §0 の「検査の結果を報告する」の 1 行に `git=writable` を足す。

## 11. 振り返り(申し送り)

### この作業で確定した事実(すべて実機検証)

| 検証項目 | 結果 | 影響 |
| --- | --- | --- |
| `.codex/skills/` の project スコープ | ✅ 動く(発見・本文ロードとも) | `docs/playbook/` への降格が不要になった。§13 #4 が決着 |
| `.codex/` への書き込み(agent) | ❌ **不可**(`workspace-write` でも保護) | `.codex/` 配下は Claude / 人間が保守する |
| `.git` への書き込み(既定) | ❌ **不可**。`git add` から失敗 | **モード C が既定では成立しない。**起動時に `writable_roots` が必須 |

### 学び

1. **「未確認」と書いてある前提は、その段階で必ず潰す。** §9 の「段階5 で成立条件を必ず検証する」を実行した結果、モード C の中核(Codex がコミットを積む)が既定では動かないと判明した。**これを見逃していたら、Claude の枠が尽きた最悪のタイミングで発覚していた**
2. **sandbox の制約は「やってみるまで分からない」。** `.codex/` も `.git` も、公開仕様の読解では出てこなかった。バイナリの文字列走査でも決定打は得られず、**実際に書かせてみる**のが唯一の確定手段だった
3. **計画の更新対象を列挙で限定すると、同一ドキュメント内の整合が漏れる。** §5 で 4 箇所を指定した結果、他 5 箇所に古い記述が残り、レビューで P1 として検出された。**「この用語を含む記述を全部見る」という指定の仕方**にすべきだった
4. **委託先の「できません」報告は裏を取る価値がある。** 今回 Codex の失敗報告は正確で、しかも**設計の欠陥を 1 つ暴いた**。作業ツリーが無変更であること(取り繕っていないこと)が信頼の根拠になった
