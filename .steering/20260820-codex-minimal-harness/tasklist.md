### 学んだこと

**「フェイルクローズ」と宣言した層が、依存コマンドの欠落で静かにフェイルオープンしていた。**

機密ファイル検査は `find ... | grep -Ev ...` で書いており、`grep` が無い環境では**「何も見つからなかった」と同じ形**(空文字列)になる。`set -o pipefail` は付けていたが、結果を条件式ではなくコマンド置換で受けていたため終了コードが捨てられていた。

- 発見の経緯は偶発だった。jq 不在を再現するために PATH を絞ったテスト環境を作ったところ、たまたま `grep` も落ちて `grep: command not found` が出た
- **この作業のテストが検出したのではなく、テスト環境の不備が露呈させた**。つまり V1〜V20 は全部緑のまま、この穴は残っていた
- 段階1 で 3 回繰り返した「**X の存在を前提に X を検査する**」と同じ構造。今回は X が外部コマンドだった
- **学び**: 検査を書いたら「この検査が**空振りする条件**」を列挙する。「検査が実行されない条件」(段階1 の学び)よりさらに手前に、「**実行はされるが常に何も見つけない条件**」がある。後者のほうが緑に見えるぶん質が悪い

**公開仕様での確定は、実機検証の代わりにならない。**

§13 の 7 件のうち 4 件が公開ドキュメントで確定し、そのぶん設計が具体的になった(exit 4 の判定材料が文言マッチから構造化識別子に格上げされたのは実質的な改善)。ただし確定したのは「**ドキュメントに書かれた仕様**」であって、`delegate-codex.sh` が実際に Codex を駆動できるかは何も分かっていない。

- 段階2 のスタブ検証は、自分が書いたスタブが自分が書いた契約を満たすことしか見ていない。**両方を自分が書いている以上、一致するのは当たり前**
- したがって「段階2 完了」と「段階2 の価値が確認できた」は別物であり、後者は段階0(契約 + インストール)の後にしか判定できない。計画文書と HTML の両方にこの区別を明記した

**「誤検知より見逃しの方が高くつく」は状況依存だった(レビュー P0)。**

上限検出の二次パターンを広く取ったのは「上限を見逃すと司令塔が原因分析に入ってさらに枠を溶かす」という非対称の判断からだった。この判断自体は正しいが、**見逃しが静かに起きることを暗黙の前提にしていた**。

- `codex exec` が exit 0 で完走したときはサマリーが標準出力に出るので、仮に上限に触れていても司令塔の目に入る = **見逃しても静かではない**。前提が成り立たない
- 逆に誤検知の側は静かではないどころか**成功した委託を丸ごと握りつぶす**。しかも `--json` のログには Codex が読んだファイルの引用が入るため、**このスクリプト自身やハーネスの計画文書をレビュー対象にすると必ず誤爆する**(レビュアーが実測で再現)
- **学び**: 「A より B が高くつく」と書いたら、**その非対称が成り立つ条件**を併記する。条件を書かないと、条件が変わった場所にも同じ結論を適用してしまう。今回は「成功したとき」と「失敗したとき」で向きが逆だった
- 併せて、**検索対象の範囲**も設計判断として扱うべきだった。「何のパターンで探すか」は詰めたが「**どこを探すか**」を詰めておらず、ログ全体を対象にしていた

**計画に書いた前提が誤っていたケースが 1 件あった(§9)。**

「`.codex/config.toml` が唯一の防衛線」は、設定解決順を確認したら成り立っていなかった(CLI フラグに負ける・untrusted では読まれない)。**防衛線だと思っていたものが防衛線でなかった**わけで、実装前に確かめたから設計を変えられた。段階1 の 9 巡目で学んだ「素通し分岐の入力値は実測する」の一般化 — **「この層が守る」と書いたら、その層が実際に効く条件を確かめるまで割り切りは成立していない**。
