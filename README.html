スペック駆動開発・ハーネスエンジニアリング・Codex 併用委託をひとつにした Claude Code プロジェクトテンプレート。

スペック駆動開発

永続ドキュメント(docs/)で「何を作るか」を決め、作業単位のステアリングファイル(.steering/)で「今回何をするか」を計画してから実装する。

ハーネスエンジニアリング

hooks / permissions / git hooks / CI で「必ず起こすべきこと」を仕組みで保証する。散文の運用ルールに頼らない。

役割別のモデル運用

司令塔は Opus 固定。実装フェーズは Codex 委託(既定)か Sonnet の fork(フォールバック)に切り出し、ユーザーもモデルも手で切り替えない。

このリポジトリはテンプレート本体です。ここから作ったプロジェクトでは、/kickoff フェーズ5 が docs/template-dev/ とテンプレート由来の .steering/ を削除し、この README をプロダクトの README に書き換えます。

ハーネスの判定はほぼ全部シェルなのに、機械的な検査が bash -n(構文エラーだけ)しかなかった。実行経路を .claude/scripts/check-shell.sh の 1 本に集約し、CI の harness-integrity が呼ぶ。devcontainer に shellcheck が入り、/check も同じコマンドを回すので手元と CI の結果が一致する。終了コードは 0 = 指摘なし / 1 = 指摘あり / 2 = 実行できない(CI では非ゼロすべて失敗)。

Step 0: リポジトリの準備

  1. GitHub で Use this template から新規リポジトリを作成する(配布側は Settings → General で Template repository を有効化しておく)。
  2. Settings → Secrets and variables → Actions に CLAUDE_CODE_OAUTH_TOKEN を設定する。未設定の間、PR 自動レビューと @claude メンションの Actions はスキップされる(失敗はしない)。スキップしてもジョブは success を返すので、緑のチェックはレビュー通過を意味しない。機械的な品質ゲート(ci.yml)はシークレット不要で常に走る。

Step 3: 実装計画の分割(任意)

/setup-spoke-standards    # スポーク公開向けの構成ルールを生成(必要な場合のみ・先に実行)
/setup-tickets            # 永続ドキュメントを実装チケットに分割 → GitHub Issues に発行

順序は固定 — /setup-spoke-standards を使う場合は /setup-tickets の前に実行する。構成ルールの MUST 項目(セキュリティヘッダ・SEO・レジストリメタデータ等)がチケットの受け入れ条件になるため、後から生成すると発行済みチケットを作り直すことになる。

  • 実行する場所はハブ側のリポジトリ。ハブのレジストリスキーマ・ドメイン規約・既存の _headers などを読んでルールを具体化する
  • 生成物は docs/playbook/spoke-development-standards.md と、そこへの参照を CLAUDE.md に追記したもの
  • スポーク側リポジトリでは実行しない。 スポークは 1 リポジトリ = 1 サブドメインで、このルールを読んで従う側になる
  • ハブ&スポーク構成でないプロジェクトでは実行不要

チケットは GitHub Issues(ticket + 優先度ラベル)で管理する。ステータス更新のコミットが不要になり、PR の Closes #N でマージ時に自動クローズされる。並行作業でもチケット状態が競合しない。

Step 4: ハーネス層の追加 — /harness-setup

検証コマンド(lint / typecheck / test)が確定したら実行する。スラッシュコマンドではなくスキルとして提供されているが、呼び出し方は同じ。

  • CLAUDE.md への「ハーネス」節追記(検証コマンド・必須ルール・委譲ルール)
  • settings.json の統合(危険コマンドの permissions.deny・PostToolUse の整形/lint hook は既定で導入済み)
  • worker subagents(既定の 5 体は導入済み。security-reviewer 等を必要に応じて追加)
  • Agent Teams の有効化(任意・experimental)と .harness/ の整備

Agent Teams を有効化した場合は、/config で Default teammate model を Sonnet に設定し、Claude Code を再起動して環境変数を反映する。

2.3 運用上のポイント(外すと高くつく作法)

  • 広範囲のコード探索は組み込みの Explore サブエージェントに委譲し、司令塔は結論だけ受け取る
  • 実装フェーズの委譲は hook で強制される。 最新 .steering/ の tasklist.md に未完了タスクがある状態で司令塔が実装コードを Edit/Write しようとすると check-implementation-phase.sh がブロックする(.steering/ / docs/ / .claude/ / .github/ / .husky/ への編集は通る)
    • 検査対象は Edit / Write ツール。sed -i 等の Bash 経由の書き込みまでは見ていない(逸脱を止めるガードレールであって、サンドボックスではない)
    • 「最新の .steering/」の判定は latest-steering.sh に集約してある。自前で ls | sort しないこと
    • テンプレート自体の改修など司令塔が実装すべき作業では tasklist.md に <!-- main-edit-ok --> を書いて解除する(プロダクト側に残さない)
  • 共通ルールは 2 層。 .claude/rules/*.md は CLAUDE.md 経由で全サブエージェントにも毎回ロードされるため、実装者・レビュアーにも要る内容だけを置く。司令塔だけが使うルールは .claude/rules/lead/*.md に置き、SessionStart hook がメインセッションにのみ注入する
  • /clear・resume 後は SessionStart hook が現在地を自動注入する(ブランチとベースの乖離・未コミット変更・in-progress Issue・最新 .steering/ の未完了タスク・未検収の Codex 委託)。チケット完了ごとに /clear が、トークン消費の最大の削減ポイント
  • コンテキストは小さく保つ。 150k を超えたら区切りで /compact、タスクが変わったら /clear。相談・調査と実装を同じセッションに混ぜない

2.5 GitHub Projects でサイクルを見る(任意)

開発サイクルを GitHub Projects の board で追える。board は表示専用で、チケットの状態の正は Issue のラベルと PR のまま(autopilot-next.sh の判定は REST だけで動く必要があり、GraphQL しか無い Projects v2 は判定経路に入れない)。未設定なら何も起きず、CI も赤くならない。人間向けの資料は 2 つあり、どちらもブラウザで開く —— しくみは .claude/docs/project-sync-guide.html、どの画面でどのボタンを押すかは .claude/docs/project-sync-setup.html(導入作業はこちらを見ながら進める)。

board の Status そうなる条件
Todo ticket ラベルがあり、まだ着手していない
In Progress in-progress ラベルがある(/next-ticket が着手時に付ける)
In Review Closes #N で紐づく open PR がある(draft も含む)
Done Issue が closed(PR マージで自動クローズ)

イベント種別ではなく Issue の現在の状態から決めるので、イベントの取りこぼしや順序の入れ替わりで board がずれない。fork の PR は本文に Closes #N と書いても紐づけない(autopilot-next.sh の信頼境界と同じ)。

  • GitHub で Project を作り、Status に Todo / In Progress / In Review / Done を用意する(Priority に P0 / P1 / P2 を作れば優先度も入る。無くてもよい)
  • classic PAT(project + repo scope)を PROJECT_SYNC_TOKEN として Actions シークレットに登録する。GITHUB_TOKEN は Projects にアクセスできないため別途必要
  • Variables に PROJECT_URL を登録する。リポジトリに固定でよければ .claude/project-sync.json の projectUrl に書いてもよい
  • 列名が既定と違う(日本語の board など)場合は .claude/project-sync.json の候補を足す
  • Actions タブから Project Sync を手動実行すると、既存のチケットがまとめて board に載る(backfill)

進行中のプロジェクトに後から入れてよい。Status は Issue の現在の状態から毎回決め直すので、過去のイベントを再生する必要がない。手順 5 の手動実行で include_closed にチェックを入れると closed のチケットも Done 列に載る(= backfill --all)。REST を全ページ辿るので 100 件を超えても全部入り、addProjectV2ItemById が冪等なので何度流し直しても重複しない。すでに着手済みのチケットは in-progress ラベルが付いていなければ Todo に入る(PR が開いていれば In Review)。テンプレートから作ったプロジェクトなら /sync-template でファイルが入る。

後入れで詰まるのは次の 2 つ。どちらも .claude/docs/project-sync-setup.html に手順を書いてある。

  • ticket / in-progress ラベルがそもそも無い(既存プロジェクトをあとからハーネスへ移行した場合)。backfill は「ticket ラベルの Issue が無い」と言って正常終了するので失敗に見えない。gh label list で確かめる
  • baseBranch が develop のプロジェクトでは、取り込みの PR をマージしても既定ブランチ(main)にワークフローが無い。手動実行のボタンが出ないだけでなく、issues イベントも動かない(既定ブランチ側の定義で動くため)。リリースを出すか、releasePrefixes の接頭辞で main 向けに先行投入する

確認とトラブルシュート: bash .claude/scripts/project-sync.sh --check(書き込まない。board の列名とスクリプトの対応を表示する)。

5.5 実装フェーズを司令塔から切り離す理由

トークン消費が最も大きいのは「実装 → テスト → エラーを読む → 修正」のループで、ここを司令塔の外で回すのが上限消費を減らす最大の手段になる。手動で /model を切り替える運用は、切替前の /clear を忘れると膨らんだコンテキスト全体がキャッシュミスとなり全額課金されるという失敗モードを持っていた。

そこで実装フェーズを委託に切り出している。委託先が変わっても司令塔の分岐(完了 / 判断待ち / 失敗)は同じであることが設計要件。

  • Codex 委託: 実装ループは別プロセスで回り、司令塔には終了コードとサマリーだけが返る。Claude の枠を消費しない
  • Sonnet fork: context: fork + model: sonnet で subagent が実装する。司令塔は Opus のまま。長いログは fork 側で完結し、サマリー 20 行だけが返る
  • fork は会話履歴を持たず design.md / tasklist.md だけを読む。計画の粒度がそのまま往復コストになる。 1 チケットで往復が 2 回を超えたら粒度不足のサイン
  • 司令塔が委譲を迂回して自分で実装しようとすると、PreToolUse hook がブロックする
  • 参照実装は司令塔が書く。 P0 の基盤や新パターンの 1 例目は品質のレバレッジが最大。2 例目以降の横展開が委託の主戦場

5.6 レビューの使い分け

  • 実装中(主レビュー): code-reviewer subagent(read-only / Sonnet)。docs/ とのスペック整合もここで確認する
  • PR 時(最終ゲート): main 向け PR のオープン時 / ready_for_review 時に 1 回だけ自動で走る。push ごとの再レビューは無い。必要なときは @claude にメンションする
  • 200 行以上 かつ 重要変更(認証・決済・データ移行・アーキテクチャ変更): 既定は delegate-codex.sh review。read-only で司令塔が自分で起動でき、別ベンダーの第二意見にもなる。判断の単一ソースは review-policy.md
    • /code-review ultra はユーザー起動 + 課金で司令塔からは起動できない。提案するのは (1) その差分自体を Codex が書いた場合、(2) Codex が使えない場合の 2 つだけ。既定と併用しない
  • UI/画面: docs/ui-design-guidelines.md §6 のチェックリストを code-reviewer に当てる

判断の根拠と実測値は docs/template-dev/cost-model.md、委託設計の根拠は docs/template-dev/codex-delegation-plan.md、実測の記録方法は docs/template-dev/econ-measurement.md。

7.2 仕組みの要点

  • 所有権の分離: 共通ルールは .claude/rules/(テンプレート所有・上書き対象)。全エージェント共通のものは CLAUDE.md が @ インポートし、司令塔専用のもの(lead/)は SessionStart hook が注入する。プロジェクト固有の追記は CLAUDE.md の「プロジェクト固有ルール」節に書く(同期で失われない)
  • 同期対象の単一ソース: .claude/template-manifest.json の owned(上書き)/ merge(3-way マージ)/ never(触らない)。パスが複数に該当するときは最も具体的な(長い)エントリが勝ち、同じ長さなら owned > merge > never。syncedAt に前回同期したテンプレート側の commit SHA を持ち、そこからの差分だけを見る
  • 変更の伝達: テンプレート側の docs/template-dev/CHANGELOG.md に [auto] / [manual] を明示する。/sync-template はリモートから直接読むため、docs/template-dev/ を削除済みのプロジェクトでも機能する
  • 3-way マージ: テキストは git merge-file(ignore 系は行の和集合)、JSON はキー単位の構造マージ。プロジェクト側の追記(allowlist・ignore 行・Flutter 対応など)を保ったままテンプレート側の変更が入り、両側が同じ箇所を変えたときだけ競合になる
  • 自動 PR: 月次ワークフローが同期スクリプトを流して PR を作る(Claude は起動しないため枠を消費しない)。競合がある・.github/workflows/ が変わる・リポジトリ設定で Actions からの PR 作成が無効、のときは Issue で知らせる。PR 作成には Settings → Actions → General の Allow GitHub Actions to create and approve pull requests を有効にする。Actions が作った PR では CI が自動で走らないので Close → Reopen で起動する
  • ドリフト検出: node .claude/scripts/sync-template.mjs --check-drift で、owned なのに書き換えてあるファイル(次の同期で失われる変更)を列挙できる
  • プロジェクト側で同期を止める: 更新されたくないファイルは manifest の never に足す(区分の判定で最優先される)

⚠️ .claude/rules/(lead/ を含む)を直接編集しないこと。次回の /sync-template で上書きされる。共通ルールを変えたい場合はテンプレート側を直すか、CLAUDE.md に例外を書く。

同期未対応のプロジェクトを追いつかせる(初回ブートストラップ)

.claude/template-manifest.json が導入される前のテンプレートで始めたプロジェクトは、同期の起点を手で刻んでから /sync-template に載せる。/kickoff の再実行はしないこと(ドキュメントとチケットを作り直す流れのため)。

作業ツリーをクリーンにしてから、プロジェクト側リポジトリで実行する。 

git switch -c chore/sync-template-$(date +%Y%m%d)
git remote add template <テンプレートリポジトリの URL>
git fetch template main --quiet
git checkout template/main -- .claude/commands/sync-template.md .claude/scripts/sync-template.mjs .claude/template-manifest.json

取り込んだ manifest の syncedAt に、そのプロジェクトが出発点にしたテンプレート側の commit SHA を書く(null のままだと差分抽出が全ファイル比較になる)。分からない場合はプロジェクトの最初のコミット日以前で最も近いテンプレート側のコミットを使う。templateRepo が以降の同期元になるので、値が正しいかもここで確認する。

あとは Claude Code を再起動して /sync-template を実行する。古い出発点ほど [manual] が積み上がっており、特に次が取りこぼしやすい。

  • CLAUDE.md のルール分離: 共通ルールがインラインなら、該当節を @.claude/rules/spec-driven.md の 1 行に置き換える
  • 手動 /model sonnet 運用の削除: 実装フェーズは委託に変わった
  • AGENTS.md の検証プローブ: <!-- verify-probe: ... --> は exists <リポジトリ相対パス> 形式が既定。旧形式はホスト上で実行される経路が残る
  • 委託禁止領域の .husky/ 統合: §4 に個別記述が残っていれば .husky/ の 1 行に置き換える
  • .claude/settings.json(merge 対象): hooks と permissions.allow の追加分を自分の配列に足す

最後に chmod +x .claude/hooks/*.sh .claude/scripts/*.sh → /check → /commit → PR。hooks / scripts / settings.json が入れ替わるため、反映には Claude Code の再起動が必要。
